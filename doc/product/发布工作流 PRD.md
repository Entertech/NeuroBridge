# NeuroBridge 发布工作流 PRD

- **文档状态**：内部需求与实现依据；自动化验证及现场验收分别记录
- **适用范围**：Windows 10/11 x64、银河麒麟 V10 及 GitHub Actions
- **版本依据**：`neurobridge/version_registry.toml`

## 1. 目标

Windows 与麒麟独立管理软件版本、构建、发布和验收。任一平台的修复无需等待另一平台同步发版。最终交付必须包含两平台；总包版本与 commit 标识这一次组合，清单说明各平台实际版本和来源。协议与文档发布规则继续遵守台账。

## 2. 功能需求

### 2.1 版本与门禁

- Windows 安装包版本读取 `platform_releases.windows.version`；麒麟读取 `platform_releases.kylin.version`。
- `[application].version` 是源码分发及交付总包版本，不控制两个平台安装包，不要求每次平台修复跟随升版。
- 采用 MAJOR.MINOR.PATCH；递增、清零和影响证据分别登记 `platform_release_changes` 与 `application_release_changes`。禁止版本回退及无依据跳级。
- PR 相对目标分支校验：平台专属产品变更要求对应平台升版，共用业务/运行依赖/网页/发布工具要求两平台升版；内部文档、测试及生成的版本变更记录不要求升版。
- 正式构建分别以对应公开平台 Release 为基线；标签/draft/缺少资产不能作为成功发布。首次独立版本从实际旧统一安装包版本迁移，不从被忽略的旧字段开始。

### 2.2 Windows 包

- Windows 10/11 x64 共用一份 MSI 和一份 Burn EXE；构建目标仅两个，两种原生格式必须完整。
- EXE 与 MSI 是两种安装入口，部署时二选一。保留已有固定升级身份，避免合并目标产生重复产品或降级。
- 兼容系统在清单中列为 10/11；两个系统分别完成真实安装、升级、卸载、自启、USB 采集与故障恢复验收。共用包不等于两系统已验收。
- Windows 7、32 位和 ARM 不在当前交付范围。

### 2.3 麒麟包

- 麒麟交付一个 V10 引导 DEB all，携带源码与锁定离线输入，在实际安装机生成匹配 CPU/ABI 的运行时。
- 保持无耳机可安装、热插入授权、事务升级/回滚/卸载及日志导出；各架构候选与验收门禁见后文。

### 2.4 独立平台发布

- 各平台只在自身版本需要发布时构建，并分别发布 `windows-v<version>`、`kylin-v<version>`；一个平台失败不撤销另一平台的成功结果。
- 平台资产为 `<platform>-v<version>.zip`，包含完整格式、平台清单与验证日志，供长期不可变保存和后续复用。
- 先上传 Actions Artifact并按 ID 回下载核对上传前摘要、清单与内容，再创建注释标签和 draft Release；资产上传复验后公开。禁止覆盖、移动或删除已有发布资产/标签。
- 自动发布在默认分支 Test 成功后运行；手动分支构建只生成候选 Artifact。Windows 输入可显式指定 Run ID，未指定时只查找相同提交及分支的成功原生输入运行，找不到则阻断 Windows。

### 2.5 完整总交付

- 总包必须同时包含 Windows 与麒麟；Windows 必须有一份 MSI 和一份 EXE，麒麟必须有一个 DEB。缺平台、缺格式、空目录、摘要或版本不符均阻断总包。
- 未更新平台从对应公开 Release 获取台账版本的原始包，验证检查点、SHA-256、ZIP 成员、原生格式、平台版本、日志和标签提交。保留该平台原始提交，不能写成本次总包提交。
- 总包名 `neurobridge-v<交付版本>-<commit前12位>.zip`；交付标签 `delivery-v<交付版本>-<commit前12位>`。清单记录完整 commit、两平台版本、各平台源码提交和复用依据。
- `windows/windows.zip` 与 `kylin/kylin.zip` 内分别用平台软件版本命名下一层 ZIP；Windows 不再产生 10/11 两份目录。
- 已有相同版本组合的完整交付时跳过；平台已公开而总包失败时，重试只复用原资产。相同提交的 draft 重试恢复原始校验 ZIP；不同提交占用平台版本时必须提升该平台版本。
- Actions Artifact 保留 30 天，Release 长期保存；当前不签名，不将源码/模拟测试标成现场验收通过。

### 2.6 目录说明与文档边界

根目录必须有 `bundle-directory-guide.pdf`，根据真实清单生成，说明总包版本、两平台软件版本、源码提交、各层 ZIP、解压顺序、安装包/指南/日志工具与校验资料位置。中文字体、表格、长字段和 JSON 必须完整可读，CI 渲染全部页面供检查，PDF 不提交 Git。

共用和平台部署指南继续按台账 delivery 策略路由。历史 SSH/有线网络指南不纳入当前交付。实现改动默认只记未发布变更，不回写已发布指南、北向协议或其日期/摘要。本次只改实现、内部文档与测试，不触发打包或远程发布。

### 2.7 系统与 CPU 架构支持表

引导包为一个 `Architecture: all` DEB；`all` 表示共用安装入口，运行时仍必须匹配实际架构。系统固定为银河麒麟 V10，七个源码适配 Profile 如下。既有 x86_64 联调事实不自动成为新版引导安装或其他架构的验收结果。

| 系统 / CPU | 位数与别名 | 依赖选择 | 当前验证状态 |
| --- | --- | --- | --- |
| 麒麟 V10 x86_64 | 64；amd64 | 锁定预编译 Python / CMake | 既有 N100/N150 联调基线；新版安装需复验 |
| 麒麟 V10 aarch64 | 64；arm64 | 本机编译锁定 Python / CMake 源码 | 源码入口与模拟回归；待实际目标机编译和验收 |
| 麒麟 V10 loongarch64 | 64；loong64 | 同上 | 同上；不等同于龙芯 MIPS |
| 麒麟 V10 mips64el | 64；mips64 且小端 ELF | 同上 | 同上；大端及 32 位 MIPS 不接收 |
| 麒麟 V10 sw64 | 64；sw_64 | 同上 | 同上；供应商工具链可能需要独立补丁 |
| 麒麟 V10 x86 | 32；i386/i486/i586/i686 | 同上 | 同上；需验证 32 位资源上限 |
| 麒麟 V10 armhf | 32；armv7l/armv8l，小端硬浮点 ABI | 同上 | 同上；不接收软浮点工具链 |
| Windows 10/11 x86_64 | 64；AMD64 | 既有 EXE/MSI | 保持原发布范围，当前版本仍需目标机验证 |
| Windows 7、Windows 32 位、Windows ARM；其他 Linux 或 CPU | — | 无 | 不支持，拒绝安装或不构建 |

全体麒麟 Profile 共用 Eigen 3.3.7、锁定 SDK/NumCpp 源码与无架构依赖的 pyserial/websockets wheel。当前串口链路不安装 BLE/dbus 原生依赖。配置仍为 serial + local_browser、回环地址、600 ms 批次与禁止耳机录播；不改北向报文。未知发行版/版本/CPU、混合位数、大端、外来编译器、缺输入或摘要错误必须停止，不能回退到 x86_64 文件。

### 2.8 多架构引导与验收要求

1. **选择与输入**：安装前记录 `/etc/os-release`、内核 CPU、用户空间位数、ELF 字节序/位数，按 `config/kylin-bootstrap-inputs.toml` 选依赖；所有输入固定版本/URL/SHA-256。准备阶段可显式下载；正式打包和目标机安装只读取已校验的离线输入。缓存缺失则失败，不在安装器内调用包管理器或下载源码。
2. **本机构建**：非 x86_64 从 CPython 和 CMake 锁定源码编译，再构建 C++17 算法。共用包只声明所有 Profile 必需的系统依赖；Python 的 SSL/sqlite/bzip2/xz/ffi/zlib 开发库仅在源码 Profile 要求，x86_64 随包 Python 不要求它们。选择 Profile 后、构建或修改旧部署前逐项编译/链接探针，缺项须列出具体库、编译器输出、目标环境与管理员补齐/重试命令；维护脚本不得调用包管理器。32 位内存限制、供应商编译器、老 glibc 和 SDK 数值差异须独立验证。不能承诺所有供应商 V10 镜像自动编译成功；失败报告中必须保留阶段、命令输出和退出码。
3. **运行时隔离**：生成文件名与 manifest 使用真实架构；复用归档必须同时匹配 Kylin V10 与 CPU，再验证 SHA-256、Python 位数/字节序及必要模块。跨 CPU 运行时在账号和服务修改前拒绝。保留已有部署的原子替换与失败回滚，未接耳机仍允许安装并等待接入。
4. **交付规模**：发布矩阵仍是一个麒麟引导 DEB 与两个 Windows 包，共三个目标；新增源文件和 wheel 增加单引导包大小，而不新增每架构预编译包。可生成手工 RPM noarch，但不纳入当前正式矩阵；RPM 系统库依赖仍须供应商确认。
5. **真机准入**：逐架构完成编译、算法输入/结果比对、安装/升级/失败回滚/卸载、冷启动 E1、停止 E0、USB 拔插、服务/整机重启、浏览器恢复及长稳。存在历史录制的离线耳机仍不得录播。缺真机证据保持 candidate，不标记现场通过；不同架构结果不能相互替代。

本轮只修改源码和文档、执行本地自动化检查，不打包、不推送，不触发依赖准备或发布 Workflow。

### 2.9 安装与运行诊断的版本和环境

Windows 与麒麟的安装/运行导出均须携带独立诊断上下文：Windows 为 `diagnostic-context.json`（安装导出添加唯一时间后缀），麒麟为 `diagnostic-context.txt`。安装未成功、服务未创建或 Python 不可运行时仍须生成；无法读取的字段明确写 `unknown`，不能填入正在导出工具所在仓库的版本作为已安装版本。

| 信息 | 字段与来源 |
| --- | --- |
| 诊断时间及类型 | `generatedAtUtc`、`diagnosticScope=installation/runtime` |
| 磁盘上的软件身份 | `applicationVersion` 来自部署目录版本台账，`sourceCommit` 来自随部署保存的 `build-info.txt`；源码部署可读取自身 Git HEAD |
| 本次安装包身份 | `packageApplicationVersion`、`packageSourceCommit` 来自引导包或 Windows 交付目录的 `build-info.txt`；运行导出没有安装包时为 `unknown` |
| 系统版本 | Windows 名称、版本、OS 构建号；麒麟发行版名称/ID、版本、发行构建标识与内核版本 |
| 环境架构 | 系统 CPU 架构、系统位数；Windows 额外记录导出进程位数，避免把 32 位 PowerShell 误判为 32 位系统 |
| 执行环境 | Windows PowerShell 版本；麒麟 Bash/glibc 版本；两者的部署 Python 版本和 Python 位数 |

版本字段描述磁盘上部署文件，不宣称正在运行的旧进程已加载新版本；服务状态另行导出。Windows 安装摘要保存安装开始时的上下文，导出时另采集当前上下文，升级失败可据时间及两个版本字段区分旧部署与新安装包。麒麟安装日志保留本次包版本/提交，导出同时读取当前部署和引导包身份。OS 查询失败应保留原因，不能因此丢弃已有安装错误日志。只采集这些必要字段，不导出全部环境变量、配置正文、令牌、密钥或人体录制数据。

## 3. 验收标准

1. 单平台业务变更未提升对应版本时门禁失败；正确提升后仅构建该平台。共用业务变更要求两个平台分别提供升级依据。
2. 总包版本变更可以只重新组合已发布平台资产，不改变安装包版本。禁止平台、总包与协议版本互相隐式传递。
3. Windows 仅两个共享 x64 包目标；麒麟仅一个引导 DEB；安装包版本、文件名、部署诊断与清单一致。
4. 一个平台失败时另一平台仍可独立发布；最终总包因缺平台或格式而失败，不伪装成完整交付。
5. 旧包复用与发布重试保留原始字节、源码提交及验证记录；错误版本、摘要、标签、危险成员路径或缺少日志必须阻断。
6. 总包含两平台，名称含交付版本和 commit，清单列各平台不同版本；上传回下载通过后才能创建相应发布标签。
7. 单元测试、工作流静态检查、版本台账与历史文档锁定门禁通过；Windows 10/11 和各麒麟架构仍各自完成现场验收。
