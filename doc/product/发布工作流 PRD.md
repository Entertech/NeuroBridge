# NeuroBridge 对外发布工作流 PRD

- **文档状态**：需求评审稿
- **适用范围**：Windows 软件、银河麒麟系统 V10 软件、对外说明文档、两个网页及 GitHub Actions 发布流程
- **版本依据**：`neurobridge/version_registry.toml`

## 1. 背景与目标

当前仓库已有单元测试、北向协议文档 PDF 和部分外部文档打包流程，但缺少统一的应用版本门禁和跨平台发布产物流程。本 PRD 目标是让合入 `master` 的变更可审计、可复现，并避免业务代码变化却沿用旧版本号。

目标：

1. 在 PR 合入 `master` 前，自动识别是否改变对应软件的业务代码并执行版本号规则。
2. 形成 Windows 和银河麒麟系统 V10 两类软件的版本化发布包流程。
3. 统一收集对外说明文档和两个网页，生成可下载、可校验的发布 Artifact。
4. 记录每个产物的版本、来源、校验值、构建环境和发布状态。

## 2. 功能需求

### 2.1 应用版本门禁

- 版本唯一来源为 `neurobridge/version_registry.toml` 的 `[application].version`。
- CI 以 PR 目标分支（默认 `master`）为基线比较版本。
- 业务代码范围由配置维护，至少覆盖 `neurobridge/`、平台部署目录、运行依赖和打包配置；只改文档、测试或网页资源不强制升应用版本。
- 业务代码变化时：PR 版本等于 `master` 版本则失败并提示至少 `master patch + 1`；大于则通过；小于则失败并说明版本回退原因。
- 未改业务代码时版本可不变，但不得低于 `master`。
- Actions summary 必须包含基线版本、PR 版本、变更文件和判定理由。

### 2.2 Windows 发布包

- 按发布配置中的版本矩阵为每个 Windows 目标版本生成独立 Artifact。
- 每个包包含软件文件、依赖锁定信息、启动/卸载说明、版本清单和 SHA-256 校验值。
- 尚未完成可执行包验证时只能标记为 `source-only` 或 `candidate`，不得伪称正式安装包。
- 包名、清单和 Artifact 名称必须含平台、架构和应用版本。

### 2.3 银河麒麟系统 V10 发布包

- 按已确认的银河麒麟 V10 CPU 架构分别建包，不得混用架构。
- 版本和下载来源以麒麟官网或双方确认的官方数据为准，记录来源 URL、抓取时间和校验值。
- 每个包包含安装/升级、依赖检查、服务启动、回滚说明、版本清单和 SHA-256 校验值。
- 未完成目标架构现场验证时只能标记为 `candidate`。

### 2.4 对外说明文档

- 继续以版本台账维护已发布对外 Markdown，PDF 由 CI 生成，PDF 不提交仓库。
- 正式包至少包含当前锁定的北向网络协议、采集包格式说明、SSH 运维操作指南、有线网络配置指南。
- 未发布文档必须先完成版本、摘要和锁定记录；候选包与正式包分开标记。
- PDF 生成后检查中文字体、标题、表格、代码块、页码和长字段换行。

### 2.5 两个网页

发布包同时包含：

1. `web/b-client-test/index.html`：B 端 WebSocket/JSON 联调页。
2. `web/capture/index.html`：采集/录播数据查看页。

两个网页及依赖文件须支持离线打开，不依赖公网 CDN 或运行时外部服务，并在清单中记录入口和校验值。

### 2.6 发布清单

每次正式发布生成 `release-manifest.json`，包含应用/协议版本、Git commit、构建时间、Windows 与麒麟目标的版本/架构/状态/文件名/SHA-256、对外 PDF 和两个网页清单、官网来源及 `candidate`/`published` 状态。

## 3. 工作流与门禁

1. `pull_request -> master`：运行版本门禁、测试、文档校验和候选包构建，不发布正式包。
2. `push -> master`：所有门禁通过后构建正式 Artifact，不自动修改版本台账或对外 Markdown。
3. `workflow_dispatch`：发布负责人选择目标版本、平台矩阵和阶段；正式阶段必须验证来源和人工确认项。
4. 平台构建失败、版本冲突、来源数据缺失、校验值不一致或文档未锁定时，工作流失败并说明原因。

## 4. 非功能要求

- 固定 Python、编译器和依赖版本，保存构建日志，确保可重复构建。
- 每个 Artifact 可反查 Git commit、版本台账和官网来源。
- 不把凭据、私钥、现场配置或人体原始数据写入 Artifact/日志。
- 不改变北向报文 `protocolVersion`，不把 BLE、SDK 或算法内部细节写入对外文档。

## 5. 验收标准

- 业务代码变更且版本不变的 PR 必须失败并提示提升版本。
- 版本高于 `master` 的 PR 通过，低于 `master` 的 PR 失败并说明回退原因。
- PR 构建生成 Windows、麒麟 V10、四份对外文档和两个网页的候选清单，状态与验证事实一致。
- `master` 构建生成带 SHA-256 的 `release-manifest.json` 和正式 Artifact。
- Artifact 可在无公网环境按清单校验，网页可离线打开。
- 现有单元测试、协议检查和 PDF 渲染检查全部通过。

## 6. 待确认事项

1. Windows 最低版本、CPU 架构、安装包格式（ZIP/MSI/EXE）及签名要求。
2. 麒麟 V10 具体发行版、CPU 架构（x86_64/ARM64/其他）和安装包格式（deb/rpm/tar.gz）。
3. 两个平台的官方版本数据来源、允许抓取的 URL、版本选择规则和离线构建要求。
4. “各个版本”是当前支持版本矩阵，还是需要回溯构建历史应用版本。
5. 两个网页的正式名称、是否分别打包及是否需要数据导入/导出能力。
6. 正式发布触发方式、Artifact 保留期限、下载权限和签名/公证要求。

## 7. 后续实施拆分

- PR-1：版本门禁脚本、业务路径配置和 Actions 检查。
- PR-2：Windows 构建矩阵及候选/正式包清单。
- PR-3：麒麟 V10 构建矩阵、依赖检查和现场验证记录。
- PR-4：统一发布清单、两个网页纳入发布包、文档 PDF 质量门禁。
- PR-5：端到端发布演练和正式 Artifact 验收。
