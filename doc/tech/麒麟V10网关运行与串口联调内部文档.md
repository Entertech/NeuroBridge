## 1. 第一次使用：只做三步

### 第一步：插好耳机 USB

先把耳机 USB 插到麒麟电脑。正常检测不需要反复拔插。当前实机曾枚举为 CP2102、`cp210x` 驱动和 `/dev/ttyUSB0`，但程序不会写死该编号：网关会逐个打开 USB 派生候选，先观察是否已有合法 28 字节脑电流；已有流就直接识别，静默时才发送固定 7 字节 ACK 并等待独立 `01`。服务重启不依赖设备主动握手或持久化身份。

### 第二步：在项目根目录启动一个文件

打开终端，进入已经传到电脑上的 NeuroBridge 项目目录，然后运行：

```bash
bash linux/neurobridge-kylin-bootstrap.sh
```

这个启动入口只负责使用电脑上已有的完整代码，启动时不会执行 `git pull` 或访问网络。旧设备缺少 `linux/setup-kylin-gateway.sh` 时，不要只传 bootstrap 文件；应按第 6 节传输单个离线更新文件。

旧设备执行离线更新文件：

```bash
bash neurobridge-kylin-offline-update.run
```

更新完成后会自动打开同一个数字菜单，以后日常运行仍使用 `bash linux/neurobridge-kylin-bootstrap.sh`。

不要在命令前加 `sudo`。助手只会在安装系统依赖、读取系统诊断或确实无法写入 `.runtime` 时单独请求 sudo 密码。日常启动不检查、不修改 Git 写权限；过程日志从入口开始保存在项目 `.runtime/logs/`。

### 第三步：输入 `1`

菜单出现后输入 `1`。`一键准备并启动` 会按顺序完成：

1. 确认项目 `.runtime` 运行目录可写；日常启动不检查或修复 Git；
2. 已有 Python 环境可用时直接跳过，否则自动准备项目 Python；
3. 检查当前已插入的 USB 和串口，不要求拔插；
4. 已有串口配置时直接跳过，否则生成项目配置；
5. 已有可用算法时直接跳过，否则下载或读取离线 CMake、构建算法并自检；
6. 全部成功后直接启动网关。

这项操作可以重复执行。已经完成的耗时步骤会被跳过，不需要区分“首次安装”和“日常启动”。如询问是否安装系统构建依赖，正常联网环境输入 `yes`；不希望修改系统或当前处于离线环境时输入 `no`，然后按第 6 节准备离线包。

启动成功后保持终端窗口打开，用本机浏览器访问：

```text
http://127.0.0.1:8080/
http://127.0.0.1:8080/capture/
```

第二个地址用于查看耳机原始数据。网页只连接当前网关服务，不直接打开串口。网页上的开始/停止只控制当前页面的 WebSocket 订阅，不会停止网关、关闭耳机或影响后台录制。

Capture 页每行对应一帧设备数据，依次显示 `SEQ`、`EEG1～EEG6` 和 `HR`。页面中的“窗口”是网关按本机 Unix 毫秒时间对齐的 600ms 数据聚合范围，页面会转换成本地时分秒显示；原始毫秒值仍可在脱敏 WebSocket 协议日志中核对。页面丢包率按 16 位大端 EEG 序列号计算：`累计缺失包数 / 从首包到最高序列号的累计应收包数 × 100%`，支持 `65535 → 0` 回绕；重复包不增加已收包数，最近 4096 包范围内的乱序补包会重新计算并减少缺失数。

## 2. 菜单怎么选

```text
1. 一键准备并启动（默认开机自启，推荐）
2. 直接启动网关（遵循已保存的自启配置）
3. 联网更新代码（可选，离线不要选）
4. 检查当前 USB/串口（无需拔插）
5. 重新生成 USB 串口配置
6. 修复/重新构建本地算法
7. 导出完整诊断包
8. 查看最近日志
9. 配置自启/非自启
0. 退出
```

普通操作只需记住：

| 目的 | 输入 |
|---|---:|
| 不确定下一步，准备好后直接启动 | `1` |
| 已确认全部配置好，只想启动 | `2` |
| 网络可用且明确需要从远端更新 | `3` |
| 没找到 USB/串口 | `4` |
| 算法构建或启动门禁失败 | `6` |
| 把完整问题信息发给开发人员 | `7` |
| 当场看最近 200 行日志 | `8` |
| 查看自启状态或显式改为非自启 | `9` |

每项执行失败后，助手会同时提示“返回菜单输入哪个数字”和高级人员可直接执行的命令。现场人员优先使用数字，不必复制长命令。

### 2.1 默认开机自启与显式非自启

菜单 `1` 完成环境、串口配置和算法门禁后，默认安装或更新 `neurobridge.service`，立即在后台启动并设为开机自启。菜单 `2` 也遵循同一默认值。成功输出应同时包含 `configuredAutostart=enabled`、`enabled=enabled` 和 `active=active`；随后打开 `http://127.0.0.1:8080/` 或 `/capture/` 验证后台服务。

服务名固定为 `neurobridge.service`，但服务进程使用当前桌面用户运行，不使用 root。配置、算法、录制和日志仍保存在当前项目 `.runtime/`；项目目录不可移动或删除。开机后不需要登录桌面，systemd 会在本地文件系统和 USB 设备管理服务就绪后启动网关，异常退出后 3 秒重试。

再次执行菜单 `1` 或 `2` 时，如果 systemd 服务已经运行，助手只显示浏览器地址，不会启动第二个进程抢占串口或端口。输入菜单 `9` 后选择 `2` 可查看状态；选择 `3` 会先询问 yes/no，再停止服务并把显式非自启偏好写入项目 `.runtime/config/kylin-autostart.conf`。此后菜单 `1`、`2` 以前台方式运行，直到菜单 `9` 选择 `1` 恢复默认自启。停止服务会执行正常采集关闭流程，因此停用后再次启用仍须按第 3 节确认 ACK/数据恢复，不能只看进程状态。

直接命令仅供高级人员使用：

```bash
./linux/setup-kylin-autostart.sh enable
./linux/setup-kylin-autostart.sh status
./linux/setup-kylin-autostart.sh disable
sudo journalctl -u neurobridge.service -f -o short-iso-precise
```

`enable` 会校验麒麟 x86_64、项目 Python、串口配置和项目内算法 bridge，拒绝覆盖不是本脚本管理的同名 systemd 单元，并记录 `enabled=true`。`disable` 记录 `enabled=false`；配置文件不存在时按默认自启处理。更新已有受管单元时会先把旧单元备份到 `.runtime/backups/`。安装成功但立即启动失败时，单元仍保持 enabled 以便排障，脚本返回失败并提示 journal 命令；不得把“已启用”当成“现场运行通过”。

## 3. 正常启动时应该看到什么

USB 串口链路的成功状态顺序如下，这不是蓝牙状态：

```text
not_connected → connecting → validated
```

| 状态 | 判定标志 |
|---|---|
| `not_connected` | 还没有识别到目标串口 |
| `connecting` | 正在遍历 `/dev/serial/by-id/`、`ttyACM*`、`ttyUSB*` 候选 |
| `validating` | 候选已打开，观察窗口内没有合法帧，正在发送 ACK 并等待独立 `01` |
| `validated` | 已观察到合法 28 字节流，或主动 ACK 后收到独立 `01`。两种情况都表示设备验证完成；`E1` 不参与验证 |
| `validation_failed` | 观察窗口内没有合法流，主动 ACK 窗口内也没有独立 `01` |
| `disconnected` | 此前识别的目标串口已经关闭；之后会按配置重新遍历 |

唯一候选或所有已打开候选在 ACK 窗口结束后仍未返回独立 `01` 时，本轮状态保持 `validation_failed`，不会再覆盖成 `not_connected` 或 `disconnected`；下一轮重试开始时才切换为 `connecting`。页面显示“网关已连接”只表示浏览器 WebSocket 已连到网关，不表示耳机已经通过校验。

若打开串口时耳机已经在发送脑电，关键成功日志应依次包含：

```text
Serial existing capture detected ... validFrameBytes=28 ... nextState=validated
Serial target selected ... selectionMode=existing_valid_frame
Serial local algorithm preparation started
Serial existing capture adopted ... commandSent=false ... connectionState=validated
```

这条路径不会发送 ACK 或 `E1`。若候选静默，关键成功日志应依次包含：

```text
Serial active handshake ACK probe started
Serial handshake ACK written ... ackWriteCount=... ackWriteBytes=... writeSuccess=true
Serial handshake ACK response received ... command=handshake_ack ... singleByteHex=01 ... success=true
Serial target selected ... selectionMode=active_ack_probe
connectionState=validated
Serial local algorithm preparation started
Serial capture enable started ... command=E1 responseExpected=false
Serial command sent ... command=start ... responseExpected=false success=true
Serial capture enabled ... connectionState=validated deviceValidationMode=ack_01
```

随后出现 `Serial capture summary`，其中应有 `frames`、`expectedPackets`、`lostPackets` 和 `lossRatePercent`。

网关进程异常退出后，耳机可能仍在发送脑电。程序重启打开串口时先观察：已有合法流就直接 `validated` 并接管，不发送 ACK 或 `E1`；没有流才主动发送 ACK。耳机收到 ACK 后返回独立 `01`，此时立即 `validated`，随后算法就绪再发送 `E1`。因此此前“服务重启后设备不主动发握手、无法恢复”的风险已经关闭。

`validated` 只表示设备身份/协议状态已确认，不保证此刻一定持续出数。`E1` 只是使能命令；发送后没有数据时由正常 `data_timeout_seconds` 超时处理，而不是退回 `validation_failed`。

## 4. 控制应答规则

网关主动发送的固定 ACK 为：

```text
AA 55 01 01 01 01 6F
```

耳机不会主动发送这段握手协议。网关打开每个候选后先完整等待 `handshake_timeout_ms` 观察合法 28 字节流：若已有流，直接进入 `validated` 并接管，不发送 ACK 或 `E1`；只有观察窗口结束仍没有合法帧时，才进入 `validating` 并主动发送这 7 字节 ACK。耳机接受后返回独立单字节 `01`，收到这一字节就立即进入 `validated`，其他候选不再打开。只有这个 `01` 是需要等待的协议响应。

ACK `01` 验证通过后，网关准备本地算法；算法准备好以后发送单字节 `E1` 使能脑电。`E1` 不会收到控制响应，也不是验证指令；命令后的首个合法帧不会再次改变 `validated` 状态。停止采集时发送单字节 `E0`，`E0` 也不会收到响应；它只停止脑电数据，不断开设备。网关异常退出、systemd 重启或串口重开后，优先接管仍在发送的合法流，否则重新主动 ACK 获得 `01`，无需身份文件或设备重新上电。不得把 `E1`/`E0` 后的数据字节当作控制应答。

ACK 等待窗口只接受独立 `01`。整个窗口没有独立 `01`、只有其他内容或发生读写错误时，当前候选失败并继续探测下一个候选。

ACK 失败日志会包含 `success=false`、`totalReadBytes`、`ackWriteCount`、`ackWriteBytes`、`unexpectedBytes` 和耗时，不记录完整生理数据。算法未就绪、`E1` 写入失败或后续数据超时发生在设备已经 `validated` 之后，会记录对应阶段、关闭串口并重试，不应解释为设备验证失败。

## 5. 常见问题直接怎么做

### 5.1 没找到串口

返回菜单输入 `4`。助手会保存 USB、驱动、TTY、权限和占用情况。若显示 `no current TTY`：

1. 确认 USB 已插紧并尝试电脑另一个 USB 口；
2. 不需要先拔插，直接再次输入 `4`；
3. 仍为空时，把菜单 `7` 导出的诊断包发给开发人员。

只有需要判断“USB 插入前后到底新增了什么”时，才使用高级差分诊断：

```bash
sudo ./linux/diagnose-kylin-usb-serial.sh --plug-cycle --timeout 60
```

### 5.2 找到串口，但主动 ACK 没有返回 `01`

典型日志：

```text
Serial handshake ACK response timed out
expectedAck01=true success=false
Serial candidates opened but none returned standalone 0x01 after active ACK
```

这表示串口能打开且网关已经写入固定 ACK，但没有收到设备返回的独立 `01`。重点检查波特率是否为 115200 8-N-1、是否选错转换板接口、电脑 TX → 耳机 RX 方向、TTL 电平和设备固件协议。程序不会用任意非空字节选中设备。

### 5.3 主动 ACK 后收到其他字节

典型日志：

```text
Serial handshake ACK response timed out
expectedAck01=true success=false
```

网关只接受独立 `01`；其他字节仅计数，窗口结束仍无 `01` 时当前候选失败。此时不会准备算法或发送 `E1`。重点核对电脑 TX → 耳机 RX 的发送链路，以及设备固件实际要求的 ACK 字节。若出现 `Serial handshake ACK response received ... singleByteHex=01 success=true`，说明校验已经通过。

### 5.4 发送 `E1` 后没有“响应日志”

这是正常现象：协议没有定义 `E1` 控制响应。应检查 `Serial command sent ... command=start ... responseExpected=false success=true`。`E1` 只是使能采集，设备在此前收到 ACK `01` 时已经进入 `validated`；如果写入失败，会记录 `reason=control_write_error`，写入成功但迟迟没有合法帧则由正常有效帧超时关闭并重连，不进入 `validation_failed`。

### 5.5 网关重启后怎么恢复

设备不主动发送握手协议。网关每次启动会先观察已有数据流，因此应先查找以下任一路径。

耳机仍在发送：

```text
Serial existing capture detected ... validFrameBytes=28
Serial target selected ... selectionMode=existing_valid_frame
Serial existing capture adopted ... commandSent=false
```

耳机静默：

```text
Serial active handshake ACK probe started
Serial handshake ACK response received ... singleByteHex=01
Serial target selected ... selectionMode=active_ack_probe
Serial capture enable started ... command=E1
```

已有合法帧时直接进入 `validated`，不发送 ACK 或 `E1`；没有合法帧时才主动 ACK，得到 `01` 后立即进入 `validated`，算法就绪再发送 `E1`。异常退出恢复的源码和自动化测试已完成，仍需在目标麒麟机现场验证。

### 5.6 算法提示 CMake 版本过低

返回菜单输入 `6`。脚本不会使用或替换系统的 CMake 3.16.3，而是安装项目内锁定的 CMake 3.31.6 到 `.runtime/algorithm/toolchain/`。下载包会校验固定 SHA-256；校验不一致时立即失败，不会解压或构建。

### 5.7 算法提示 Eigen 版本不匹配

麒麟目标环境锁定 Eigen 3.3.7。菜单 `6` 会检查头文件中的实际版本；缺少依赖时可确认使用麒麟软件源安装。检测值不是 3.3.7 时不会继续构建，日志会同时给出 expected 和 detected。

### 5.8 提示 Git 不可用或网络无法拉取

日常运行输入 `1` 或 `2`，不会执行任何 Git 更新。菜单 `3` 只供网络可用且明确需要从远端更新时主动选择；联网更新失败不影响当前版本继续启动。

日常启动也不会再因为 `.git/index` 或源码目录中的缓存文件而询问“修复所有权和 Git 写权限”。历史版本出现重复提示有两个已确认原因：完整诊断脚本在 sudo 下运行 `git status` 时刷新了 `.git/index`，以及串口配置脚本以 root 导入项目代码时生成了 `__pycache__`。当前版本分别使用 Git 只读模式并禁止 root 写 Python 字节码缓存。只有主动选择菜单 `3` 更新代码时，才检查 Git 写权限；若旧版本已经留下 root 文件，执行一次离线更新会统一修复，之后不应重复提示。

现场电脑无法访问 GitHub 时，由开发机生成单文件离线更新包并传到项目根目录：

```bash
# 开发机：提交并测试完成后生成
./tools/build-kylin-offline-update.sh

# 麒麟电脑：只接收生成的这一个文件
bash neurobridge-kylin-offline-update.run
```

离线更新文件内嵌经过 SHA-256 校验的 Git bundle，只从该本地文件快进代码，不访问 `origin`。更新时保留 `.runtime/`、现场配置、算法、日志和录制数据；项目有已跟踪修改、分支无法快进或 bundle 校验失败时会安全停止。

以后不要执行 `sudo git pull`、`sudo git checkout` 或 `sudo git add`。

如果存在 `.git/index.lock`，助手不会自动删除。先确认没有其他 Git 进程，再由开发人员处理。

### 5.9 网页打不开或没有数据

先确认启动网关的终端仍在运行，再检查：

1. 浏览器地址必须是 `http://127.0.0.1:8080/` 或 `/capture/`；
2. 日志是否到达 `validated`；
3. capture 页是否点击了“开始”；
4. 日志是否出现 `Serial algorithm preparation failed after device validation`、`Serial capture enable failed after device validation` 或 `Serial valid-frame timeout`。

不要直接双击 `web/capture/index.html`。页面文件本身是静态资源，但必须由当前网关提供，并通过网关 WebSocket 获取数据。

## 6. 离线电脑怎么准备

### 6.1 离线更新项目源码

开发人员在已提交、测试通过且工作区干净的仓库执行：

```bash
./tools/build-kylin-offline-update.sh
```

生成文件位于：

```text
.runtime/packages/neurobridge-kylin-offline-update.run
```

只把这个 `.run` 文件传到麒麟电脑的项目根目录并执行：

Python 和 CMake 都放在项目目录，不替换麒麟系统运行时。离线材料可由开发人员提前放入：

```text
algorithm-packages/   # 算法构建工具包
```

麒麟 x86_64 的 CMake 离线文件名必须为：

```text
algorithm-packages/cmake-3.31.6-linux-x86_64.tar.gz
```

固定 SHA-256：

```text
5a1133ff103c71eb5120e2cc3de922733e7d8a26a98ae716397e8676adb367bf
```

准备好后仍然只运行入口并输入 `1`。这些目录和 `.runtime/` 已加入 `.gitignore`，不会因日常 `git add` 被误提交。

## 7. 日志在哪里，怎么导出

所有项目运行产物都在仓库目录内：

```text
.runtime/config/       现场配置
.runtime/logs/         助手、安装、算法和运行日志
.runtime/algorithm/    构建结果与项目内 CMake
.runtime/recordings/   内部录制数据
.runtime/diagnostics/  可传给开发人员的诊断包
```

当场查看最近日志：返回菜单输入 `8`。

持续运行日志保存在 `.runtime/logs/neurobridge.log`，默认按 10 MiB 轮转并保留 14 份备份。启动预检及控制台输出在前台终端或 `journalctl -u neurobridge.service` 查看；启动脚本不再复制到无轮转的 `neurobridge-console.log`，旧文件保留但不再追加。

向开发人员提交问题：返回菜单输入 `7`。完成后把 `.runtime/diagnostics/` 下最新的 `.tar.gz` 和同名 `.sha256` 一起发送。诊断会记录系统、USB/TTY、权限、占用、工具链、项目 revision、状态迁移、ACK 与控制分类、有效/非法帧、超时、丢包和重连统计。

诊断包不应包含密码、令牌、私钥、完整 28 字节脑波帧或算法输入。不要把 `.runtime/`、诊断包或人体录制数据提交到 Git。

### 7.1 Windows / 麒麟长时间运行测试

更新源码并重启网关后，默认每 10 秒在运行日志写入一行 `Runtime metrics: {...}`。使用 `INFO` 级别即可；不需要打开 DEBUG 或原始数据追踪。Windows 和麒麟共用这套采集统计，路径以实际配置的 `[logging].directory` 为准。仅新增本机运维日志，不发送网络心跳。

在现有配置的对应节内修改参数（不要重复添加同名节），然后重启服务：

```toml
[pipeline]
metrics_interval_seconds = 10

[logging]
level = "INFO"
rotation_mode = "size"
max_bytes = 10485760
backup_count = 14
```

默认最多保留当前日志与 14 份备份，约 150 MiB。保留时长取决于总日志量，不保证覆盖整个测试；测试中定期另存日志及轮转备份，或提前调整 `backup_count`。已有外部 logrotate 部署须按其轮转方案管理，避免与进程内大小轮转同时操作同一文件。录制文件的磁盘占用独立于运行日志，长测前同时检查录制目录剩余空间。

| 日志字段 / 标记 | 长测用途与含义 |
| --- | --- |
| `gatewayBootId`、`progress.uptimeSeconds`、`progress.sampleSequence` | 区分每次进程运行，运行秒数使用单调时钟；启动标识变化表示发生了重启，不能把重启后的短时统计当成连续长稳 |
| `progress.intervalSeconds`、`progress.delta`、`progress.framesPerSecond` | 距上次采样的实际秒数、计数增量与实测完整帧速率；首条增量从适配器创建时算起，不假定设备采样率 |
| `eventLoopLagMs` | 周期采样任务比计划唤醒时间晚了多少毫秒；仅在事件循环恢复后可观测，永久卡死只能表现为日志中断 |
| `pipeline.last_frame_at_ms`、`last_frame_age_ms` | 最近被应用解析的完整帧接收时间及距解析时刻的单调时钟年龄；尚未收帧为 `null`，断线后年龄继续增长，重连收到新帧才更新 |
| `pipeline.last_window_start_ms`、`last_window_end_ms` | 最近成功发布到网关内部快照的采集窗口起止 Unix 毫秒；不代表浏览器已收到 |
| `pipeline.algorithm_evaluations`、`algorithm_duration_ms`、`algorithm_max_duration_ms` | 已完成算法等待的累计次数、累计耗时与最大耗时（毫秒，包含等待超时）；可用周期耗时增量除以次数增量求平均值 |
| `pipeline.algorithm_valid_results`、`algorithm_invalid_results`、`algorithm_timeout_results` | 累计结果数；无效结果包含队列积压/算法不可用的占位结果，超时是无效结果的子集。迟到结果不重复计入这些计数 |
| `algorithmState`、`dataState`、`recentError`、`errorStage` | 算法与数据状态、最近错误及阶段；最近错误可能保留历史值，应结合本周期增量和状态判断 |
| `lastStorageSuccessAtMs`、`storageState`、`persistenceGaps`、`storage.queueDepth` | 最近成功写入时间、磁盘状态、累计缺口与写入队列深度；配合 `availableBytes` 判断写入停滞或空间不足。写入成功不等于会话已完成封存 |
| `process`、`pipeline.algorithm_queue_depth`、`retained_frames` | 进程 CPU、内存、线程/任务、句柄/文件描述符及队列趋势；平台不支持的指标为 `null`，不可视为零 |
| `clients`、`subscriptions`、`delivery`、`deliveryByStream` | 浏览器连接、订阅和发送统计；没有数据订阅时发送量为零正常，采集与保存仍应继续 |
| `Runtime connection transition`、`reconnections`、`offlineSeconds` | 每次连接状态事件即时记录，不遗漏短于统计周期的断线；`reconnections` 是已连接后进入离线的次数，不是恢复成功次数 |
| `phase="acquisition_shutdown"` | 停止采集时补写最后一段统计；后续还需检查录制收尾日志及 `Process shutdown completed`。断电或强杀可能没有此记录 |

`progress.delta` 只列出选定的进程累计计数；`pipeline` 中队列等字段是当前值，`late_results` 是当前算法会话计数。统计不会写出脑波字节或算法数值。

建议先完成一次短时启停，确认上述日志存在，再保持耳机连接连续运行至少 24 小时，跨越多次录制切段。记录开始/结束时间、源码提交、配置摘要、系统版本、固件与运行方式；过程中检查收帧/发布增量、保存时间、积压、缺口及资源趋势。另行记录耳机拔插、服务重启、浏览器关闭/恢复，以及保留历史录制时耳机离线仍不回放的专项结果，标明人为断线的时间，避免与意外故障混淆。

正常停止后保存 `neurobridge.log` 及同目录的 `neurobridge.log.*`，同时检查测试开始的启动标识是否仍可找到。Windows 可用第 10.5 节 PowerShell 命令跟随日志；麒麟可用 `tail -F .runtime/logs/neurobridge.log`。日志按 UTC 记录时间（末尾 `Z`），北京时间为 UTC+8。先保存测试日志，再重启，防止轮转覆盖开头证据。本节为源码支持的测试方法；自动化回归不代表 Windows 或银河麒麟 24 小时现场验收通过。

## 10. Windows 操作教程（源码联调）

本节用于把耳机直接插到 Windows 电脑，在该电脑运行网关并打开浏览器。链路为：耳机 → USB 派生 COM → Windows 网关 → `127.0.0.1` 浏览器。Windows 浏览器访问自己的 `127.0.0.1` 不会连接另一台麒麟网关；麒麟上的页面应在麒麟本机打开。

当前仓库提供 Windows 一键启动菜单、COM Source、配置模板和 Service 宿主源码。用户已于 2026-09-09 确认上述 Windows x64 电脑运行联调成功；具体系统版本和专项验收记录见本文“已验证环境”。本节入口用于源码联调，也不是正式签名安装包。

### 10.1 一键准备与启动（推荐）

把完整项目放到固定的本地磁盘目录（仅可信人员可写，保留基础 Python 和项目运行环境），插好耳机 USB，双击 `windows\neurobridge-windows-bootstrap.cmd` 即自动准备并启动，不需要选择菜单或输入数字。也可在项目根目录的 PowerShell 直接运行：

```powershell
.\windows\neurobridge-windows-bootstrap.cmd
```

一键流程会：

1. 检查 Windows 10/11 x64，寻找 Python 3.11 x64；缺少时尝试用 winget 为当前用户安装，无 winget 时提示手动安装；
2. 准备项目 `.runtime\windows-venv`，缺少依赖时按 `requirements.lock` 安装，已有依赖通过检查则复用；
3. 首次生成 `.runtime\config\windows-gateway.toml`，将录制、日志与算法路径指向项目 `.runtime`；已有配置只校验，保留 COM、端口和自定义路径；
4. 缺少算法程序或源码变化时，自动下载并校验锁定构建依赖，编译 Windows x64 EXE，通过 DLL 检查和空输入自检后安装；随后检查端口占用和 USB COM；
5. 首次请求 Windows 管理员授权，注册并启动 `NeuroBridgeProject` 开机自启服务，然后打开本机 capture 页面；点击“开始”接收数据。以后开机即启动后台网关，不需要先登录桌面或再次双击。

**算法自动准备：**无需自己准备 exe/DLL。首次联网会下载约 200 MB 的 LLVM-MinGW、CMake、Ninja 和 Eigen，按 `sdk.lock` 校验 SHA-256，再使用仓库中的 SDK/NumCpp 源码构建。工具只在项目内使用，不要求安装 Visual Studio。EXE 通过 x64 格式、系统 DLL 导入和空输入自检后，才放入 `.runtime\algorithm\`；构建失败保留旧程序并显示日志路径，修复后再次双击即可。后续源码和产物摘要一致时直接复用；自定义算法路径只自检、不覆盖。空输入自检不代表真实脑电算法结果已经验证。没有 COM 时程序仍可启动并等待耳机插入。

默认后台服务运行时可以关闭窗口；再次双击仅复用服务并打开页面，不重建算法或启动重复进程。拒绝管理员授权会保留错误窗口，不自动切换前台。菜单 `11` 可关闭自启并正常停止服务，保存此选择后再次双击才以前台方式运行（`Ctrl+C` 停止）；菜单 `10` 恢复自启。自启维护与日志见第 10.6 节。启动前停止其他占用同一 COM/端口的网关；脚本不会自动停止其他进程。

需要检查 COM、查看日志等排障操作时，才打开可选菜单：

```powershell
.\windows\neurobridge-windows-bootstrap.cmd -Action menu
```

| 目的 | 菜单数字 |
|---|---:|
| 一键准备并启动 | `1` |
| 直接启动，不安装依赖 | `2` |
| 检查当前 USB COM，不打开串口 | `4` |
| 创建或校验配置，保留已有设置 | `5` |
| 准备或修复 Windows 算法程序 | `6` |
| 导出诊断摘要 ZIP 和 SHA-256 | `7` |
| 查看最近 200 行运行日志 | `8` |
| 查看开机自启状态 | `9` |
| 启用开机自启并启动 | `10` |
| 关闭开机自启并停止服务 | `11` |
| 退出菜单 | `0` |

双击启动失败时会保留错误窗口，便于查看原因；修复后再次双击即可。可选菜单中的动作失败后返回菜单；已有环境、配置和录制数据保留。菜单中的其他动作如提示缺少环境，可选择 `1` 准备。源码启动不访问 Git。入口只对当前 PowerShell 进程设置执行策略；若组织策略禁止脚本，按组织批准方式处理。

离线电脑使用：

```powershell
.\windows\neurobridge-windows-bootstrap.cmd -Offline
# 或直接一键执行
.\windows\neurobridge-windows-bootstrap.cmd -Action prepare -Offline
```

离线模式不调用 winget，不联网安装 Python 包。环境未准备时，开发人员须提供完整 Python 3.11 x64（含 venv/pip，可放到 `python-runtime\windows\python.exe` 及其配套文件），并将匹配的完整依赖 wheel 放到 `wheelhouse\windows\`。若算法尚未构建，将 `sdk.lock` 的 `windows_algorithm_build.packages` 中四个原名 ZIP 放到 `algorithm-packages\windows\`，脚本会校验后离线构建；缺少时会显示确切文件名，不回退联网。已经构建并通过源码/产物摘要检查后，日常启动不需要重新下载。

下面的分步命令用于手动联调和排障。手动示例使用 `.venv`，一键脚本使用 `.runtime\windows-venv`；使用一键环境排障时，将下文 `.venv\Scripts\python.exe` 替换为 `.runtime\windows-venv\Scripts\python.exe`。两者共享同一项目配置文件。

#### 手动准备电脑与文件

1. 准备可运行 Python 3.11 x64 的 Windows 开发电脑，例如 Windows 10/11 x64，并安装带 Python Launcher 的 Python 3.11 x64。仓库要求 Python ≥ 3.11；Windows 7 无法直接照此安装，最低系统补丁、兼容运行时、浏览器和 pywin32 版本仍待锁定。
2. 将完整项目源码解压到当前用户可写目录，例如 `C:\NeuroBridge`。必须包含 `neurobridge`、`web`、`windows` 和 `pyproject.toml`，不能只复制 `service.py`。
3. 推荐先使用第 10.1 节双击入口自动构建算法。手动环境已完成、配置已生成时，也可运行 `.\.venv\Scripts\python.exe windows\algorithm_build.py`；离线追加 `--offline`。麒麟/Linux 或 macOS 二进制不能复制过来使用。
4. 插入耳机 USB，打开“设备管理器 → 端口（COM 和 LPT）”，记录实际 COM 编号。没有端口或出现黄色感叹号时，根据实际 USB 转串口芯片，从设备厂商提供的渠道安装匹配系统的驱动；不能只因麒麟现场用过 CP2102 就假定所有设备都使用该芯片。

### 10.2 打开 PowerShell，准备 Python 环境

在项目文件夹中打开 PowerShell，或运行下列命令。示例项目目录应替换为自己的实际路径；本节使用普通用户权限，另有标注的服务管理除外。

```powershell
Set-Location 'C:\NeuroBridge'
py -3.11 -c "import sys, struct; print(sys.version); print('bits=', struct.calcsize('P') * 8)"
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\python.exe -m pip check
```

第一条检查应输出 Python 3.11 和 `bits=64`。每条命令成功后再执行下一条；有错误时先处理错误。`pip install` 会安装项目声明的依赖，首次准备需要可访问配置的 Python 包源；离线电脑须由开发人员另行准备匹配 Windows/Python 架构的完整依赖包，不能使用第 6 节的麒麟运行时压缩包。

本节始终使用虚拟环境 Python 的完整相对路径，无需激活 `Activate.ps1`，也无需修改 PowerShell 执行策略。若 `py` 不存在，先修复 Python Launcher 安装，或用已安装的 Python 3.11 x64 `python.exe` 绝对路径代替 `py -3.11`。

### 10.3 检查 COM 与创建配置

先关闭可能占用耳机的串口调试助手或其他网关进程，然后只枚举端口：

```powershell
.\.venv\Scripts\python.exe -m serial.tools.list_ports -v
New-Item -ItemType Directory -Force -Path .runtime\config, .runtime\logs, .runtime\recordings, .runtime\algorithm | Out-Null
if (-not (Test-Path .runtime\config\windows-gateway.toml)) {
    Copy-Item windows\gateway.toml.example .runtime\config\windows-gateway.toml
}
notepad .runtime\config\windows-gateway.toml
```

端口应与设备管理器一致，并具有 USB 的 VID/PID 或 USB 硬件标识。网关只选择 USB 派生 COM；仅看到某个蓝牙虚拟 COM 或主板 COM 并不表示找到耳机。

在记事本中修改复制出的配置，保留其他模板字段。以下为需要核对或替换的字段，**不要整段追加到文件末尾而产生重复节**：

```toml
# 文件顶部
profile = "windows_headset_local"

[data_source]
type = "serial"
window_interval_ms = 600

[access]
mode = "local_browser"

[serial]
device = "auto"
candidate_types = ["COM"]
baud_rate = 115200

[recording]
directory = 'C:\NeuroBridge\.runtime\recordings'
replay_recording_id = ""

[logging]
directory = 'C:\NeuroBridge\.runtime\logs'

[algorithm]
enabled = true
command = ['C:\NeuroBridge\.runtime\algorithm\neurobridge_affective_bridge.exe']
```

这里的单引号是 TOML 字面量字符串，Windows 反斜杠无需再转义。三处绝对路径必须对应实际项目位置；按 UTF-8 保存配置。`device="auto"` 会逐个探测 USB COM；如需固定端口，将其改成设备管理器中实际显示的名称，例如 `device="COM3"`，不要照抄示例编号。115200 8-N-1 由适配器设置，无需在网页设置串口。

保留模板中 `[server]`、`[local_ui]`、`[download]` 的 `host="127.0.0.1"`；模板端口分别为 `8765`、`8080`、`8766`，只作为当前配置示例，现场使用前确认可用。`[network].mode="static"` 不要求 Windows 设置专网静态 IP；当前访问策略仍是 `local_browser`。耳机配置的 `replay_recording_id` 必须留空，不得填写历史录制标识。

保存后检查配置能否读取、bridge 路径是否存在：

```powershell
.\.venv\Scripts\python.exe -c "from neurobridge.configuration.runtime import load_runtime_config; c=load_runtime_config('.runtime/config/windows-gateway.toml'); print(c.profile, c.serial.device, c.access.mode)"
Test-Path .runtime\algorithm\neurobridge_affective_bridge.exe
```

应显示 `windows_headset_local`、配置的端口选择值和 `local_browser`，文件检查应为 `True`。这仅证明配置可解析且文件存在，算法能否运行还要看启动日志。

### 10.4 启动、查看数据与停止

以下为手动前台联调；已通过双击启用服务时，先用菜单 `11` 关闭自启并停止服务，再在同一个项目根目录运行：

```powershell
.\.venv\Scripts\python.exe -m neurobridge --config .runtime\config\windows-gateway.toml
```

保持该 PowerShell 窗口打开，在**这台 Windows 电脑**的浏览器访问 `http://127.0.0.1:8080/capture/`；综合联调页面为 `http://127.0.0.1:8080/`。如果调整了 `[local_ui].port`，地址也要使用相应端口。不要双击 HTML 文件，也不要用 Web Serial/WebUSB 直接连接耳机。

成功判断沿用第 3～4 节的数据规则，但 Windows 增加停止恢复：已有合法帧则直接接管；同一 USB/COM 身份有正常 E0 停止记录时先准备隔离算法并发送 E1，观察不到合法帧再发送 ACK；其他情况先 ACK，超时再试 E1。ACK 仍以独立 `01` 验证，E1 无应答、必须收到合法 28 字节脑波帧才确认恢复。验证后再创建正常采集会话；已恢复出数时不重复发送 E1。页面“网关已连接”仅表示 WebSocket 连接成功，还要核对设备状态和实时帧。Capture 页点击“开始”后检查 `SEQ`、`EEG1～EEG6`、`HR` 和持续到达的数据窗口；每批按 600 ms 聚合，不能据此假定固定样本数。

网页“停止”只取消该页面的数据订阅。停止整个前台网关时，在运行窗口按 `Ctrl+C`，等待 `Process shutdown completed` 或进程退出后再关闭窗口。下次运行同一启动命令即可；不要同时开两个网关抢占 COM 和监听端口。

联调至少记录：正常采集、拔下 USB 后离线、重新插入后恢复、网关停止/重启、浏览器断开/恢复，以及存在历史录制但耳机离线时仍不回放。串口未就绪的数据请求应得到不可用错误，不能输出 `mode="replay"`；单纯页面可打开不代表这些检查通过。

### 10.5 查看日志与常见故障

另开一个 PowerShell，进入同一项目目录后执行：

```powershell
Get-Content .runtime\logs\neurobridge.log -Tail 200 -Wait
```

`Ctrl+C` 结束日志跟随，不会停止另一个窗口中的网关。路径以 `[logging].directory` 为准；持久日志使用模板中的大小轮转配置。配置解析等发生在日志初始化前的错误，应保留启动窗口中的完整报错。

| 现象 | 操作 |
|---|---|
| `No module named serial` / `websockets` / `win32…` | 确认使用 `.venv\Scripts\python.exe`，重新执行同一 Python 的 `-m pip install -e .` 和 `-m pip check` |
| 找不到目标 COM | 对照设备管理器与 `serial.tools.list_ports -v`，检查 USB 线缆、驱动及 USB 硬件标识；重新插入后核对编号是否改变 |
| 打开 COM 报 Access denied / PermissionError | 关闭占用端口的串口助手、其他网关或已安装的 NeuroBridge 服务；不要靠重复启动进程处理 |
| 重启后 COM 可打开，但 ACK 一直接收 0 字节；拔插后恢复 | 更新到支持 ACK/E1 恢复的源码，正常停止旧网关后再启动；查看 `Serial restart probe` 的探测顺序与 `Serial E1 recovery validated by live frame`。停止提示保存在录制目录 `.windows-serial-resume.json`，只决定顺序；若两种方式均失败，保留未拔插时的日志，继续检查设备固件/串口链路，不把打开 COM 当作验证成功 |
| ACK 超时、没有独立 `01` | 按第 5.2～5.3 节检查实际接口、115200 8-N-1 和设备固件；任意非空字节都不能代替正确应答 |
| 算法准备或自检失败 | 查看 `.runtime\logs\windows-algorithm-build.log`；检查下载、磁盘及报错，修复后重新双击。菜单 `6` 可单独准备/修复算法；自定义 `algorithm.command` 指向的外部程序仍由部署人员维护，不自动覆盖 |
| 编译完成后报 `KeyError: 'SystemRoot'` | 这是旧启动器把 Windows 环境变量复制到普通字典后的大小写处理缺陷；使用已修复的完整源码后重新双击。无需重装编译器或手动设置另一份同名环境变量；本地下载缓存可复用 |
| 每约 10 分钟出现 `Bad file descriptor`，随后 `flush of closed file` | 旧版录制索引用只读句柄调用 `fsync`，在 Windows 切段时失败。修复版使用可写句柄同步，切段失败后保留可恢复文件并隔离关闭句柄。先正常停止服务/前台网关，保留整个录制目录，再更新源码并重启；核对跨越至少两次分段周期后不再报错且持久化缺口计数不增长。历史缺口不会因升级自动补齐，不能只凭页面连续有数据判定录制完整 |
| `WinError 10048` 或网页打不开 | 核对启动窗口、配置端口和已有进程；用下方命令查询占用，再处理已确认的进程 |
| Origin 被拒绝或网页连接失败 | 使用网关提供的 `http://127.0.0.1:<页面端口>/`，不要改用 `localhost`、`file://` 或另一台电脑的地址 |

```powershell
Get-NetTCPConnection -State Listen | Where-Object { $_.LocalPort -in 8080, 8765, 8766 } | Select-Object LocalAddress, LocalPort, OwningProcess
# 将 1234 换成上一步实际输出的 PID，只查询进程身份
Get-Process -Id 1234
```

Windows 菜单 `7` 会在 `.runtime\diagnostics\` 生成诊断摘要 ZIP 和同名 `.zip.sha256`，包含应用/系统/Python 版本、架构、配置校验摘要和 USB COM 候选，不包含配置正文、日志正文或录制数据。它不等同于麒麟完整诊断包。提交问题时使用第 8 节模板，并补充 Windows 版本/系统内部版本、Python 版本和位数、COM 编号、USB 驱动版本、前台或服务运行方式、报错时间及对应日志片段。发送前检查内容，排除凭据和原始人体数据；不要直接打包整个 `.runtime` 或 `recordings`。

### 10.6 开机自启服务与维护

双击入口安装的是 **`NeuroBridgeProject`**，使用当前项目的虚拟环境、`.runtime\config\windows-gateway.toml`、算法及录制目录；开机只运行已准备好的文件，不联网安装、不重新编译，也不打开桌面浏览器。服务以 **LocalSystem** 运行，项目源码、算法及 Python 因而必须来自可信来源，所在目录只允许可信人员写入。保留固定本地路径及基础 Python，不能移至网络/映射盘；脚本不自动放宽目录权限。

在项目根目录运行（也可使用菜单 `9` / `10` / `11`）：

```powershell
# 查看状态，不需要管理员权限
.\windows\neurobridge-windows-bootstrap.cmd -Action autostart-status
# 关闭自启并正常停止，按需请求管理员授权
.\windows\neurobridge-windows-bootstrap.cmd -Action autostart-disable
# 恢复开机自启并立即启动，按需请求管理员授权
.\windows\neurobridge-windows-bootstrap.cmd -Action autostart-enable
```

状态中 `state=4` 表示运行、`state=1` 表示停止，`automatic=true` 表示服务配置为开机自动启动。关闭操作会将服务改为手动启动并保存项目偏好，之后双击使用前台运行。更新源码/依赖或重建算法前先关闭自启，等服务停止再修改；完成后重新启用。不要通过直接结束进程代替正常停止采集。

后台日志：

```powershell
Get-Content .runtime\logs\windows-service.log -Tail 200
Get-Content .runtime\logs\windows-service-control.log -Tail 200
Get-Content .runtime\logs\neurobridge.log -Tail 200
```

前两份分别记录宿主启停/异常和管理员设置错误，各按 1 MiB 轮转并保留 3 份；最后一份是默认运行日志，实际路径以配置为准。若连宿主日志都没有，查看 Windows 事件查看器“Windows 日志 → 系统 / 应用程序”，检查 Python/pywin32 是否完整、文件是否可由 SYSTEM 读取。服务异常退出后，Windows 服务管理器等待 3 秒重启；一直失败时应先关闭自启并根据日志修复。

如果同名服务已属于其他项目目录，脚本会拒绝覆盖或停止。迁移/删除旧目录前，在旧项目关闭自启，再在管理员 PowerShell 执行 `sc.exe delete NeuroBridgeProject`；迁移后修正配置中的绝对路径并重新双击。仅停止服务不解除旧目录的注册关系。

**本次新增自启待实机验证：**此前 Windows 10 专业版 22H2 的用户成功反馈不包含本次服务。重启电脑后不要双击启动器，先在服务列表核对 `NeuroBridgeProject` 已自动运行，再打开本机页面核对采集；结合服务启动日志与登录时间确认启动不依赖登录。还需核对无 USB 开机后插入恢复、USB 拔插、浏览器断开/恢复、服务正常停止及异常恢复、有历史录制但耳机离线时不回放。自动化服务测试不替代这些现场记录。

#### 已安装候选包服务（高级人员）

候选包服务名是 `NeuroBridge`，与上述项目自启服务不同。

只有开发人员已经安装包含完整运行时的 Windows 候选服务时，才在**管理员 PowerShell** 使用以下命令，按需逐条执行：

```powershell
Get-Service -Name NeuroBridge
```
