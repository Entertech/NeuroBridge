# 头环网关多传输数据源接入技术方案

状态：内部实现基线

日期：2026-09-02

适用范围：NeuroBridge Linux/PC 网关设备接入、算法兼容、内部录制与运维诊断

需求来源：[头环网关多传输数据源接入 PRD](头环网关多传输数据源接入_PRD.md)

## 1. 结论与实施边界

首期正式链路为：

```text
耳机 ──USB 物理线──> 麒麟内核 USB/串口驱动 ──/dev/tty*──> SerialAdapter
     ──28 字节设备帧──> DevicePacket ──> Gateway ──> 算法/录制
                                             └──────> 本机 WebSocket ──> 浏览器
```

系统通过 `data_source.type` 一次只创建一个设备适配器：

| 配置值 | 适用条件 | 当前交付状态 |
|---|---|---|
| `serial` | USB 接入后枚举为 `/dev/ttyACM*` 或 `/dev/ttyUSB*` | 源码支持，自动化测试覆盖；目标 N100/N150 麒麟实机 POC 和现场验收待完成 |
| `bluetooth` | 使用已确认 Flowtime BLE profile | 兼容源码保留并有自动化回归；目标麒麟真实设备回归待完成 |
| `usb` | 设备以 HID、Bulk 或 Interrupt 端点通信且不枚举 TTY | 仅保留策略值和可操作错误；协议与硬件信息未确认，禁止启用 |

“源码支持”只说明仓库已有实现和自动化证据，不等同于“POC 已验证”或“现场验收通过”。原生 USB、电气连接、DTR/RTS/HUP 的真实设备影响、算法真实数据结果、麒麟驱动和长稳均不能由单元测试替代。

本方案不改变北向 WebSocket 消息、已发布采集包格式或报文版本。传输来源和完整串口设备帧只写入内部记录，不向浏览器或兼容 B 端新增字段。

## 2. 设计目标

1. 设备侧传输可替换，但 Gateway、算法、录播和北向协议不出现 BLE/串口库分支。
2. 未选中的策略不导入驱动、不扫描设备、不打开端口、不声明 USB 接口。
3. 设备适配器在接收边界记录时间，统一交付通道、原始字节、来源类型和接收时间。
4. 串口严格使用已确认的握手、控制、分帧和序列规则，不猜测校验、采样率或响应内容。
5. 完整 28 字节串口帧可追溯，同时保持现有 EEG/HR 算法输入和已发布导出包不变。
6. 现场没有 Codex 时，运维人员仅通过一键配置、持久日志和诊断包即可确认主要运行状态。

## 3. 架构与职责

| 模块 | 职责 | 禁止事项 |
|---|---|---|
| `neurobridge/device/strategy.py` | 按配置从注册表创建唯一设备策略 | 不执行扫描、协议解析或业务处理 |
| `neurobridge/device/packet.py` | 定义跨传输统一事件 `DevicePacket` | 不解释设备字节 |
| `neurobridge/ble/flowtime.py` | BLE 扫描、连接、通知、启停和重连 | 不直接调用算法或北向发送 |
| `neurobridge/serial/adapter.py` | USB 派生 TTY 发现、握手、控制、分帧、丢包统计和重连 | 不推断原生 USB 端点，不修改脑波字节序 |
| `neurobridge/business/gateway.py` | 接收统一事件，组织窗口、算法、状态、录制和北向发布 | 不依赖 Bleak、pyserial 或 USB 库对象 |
| `neurobridge/business/recording.py` | 保存公开会话数据与内部设备边界数据 | 不把内部帧混入已发布采集包或录播 |
| `neurobridge/algorithm_setup.py` | 对新 bridge 执行无人体数据进程自检，成功后原子启用项目配置 | 不判定算法精度，不记录输入或结果数值 |
| `neurobridge/northbound/` | 本机或兼容有线访问策略、WebSocket 契约 | 不感知设备传输类型 |

依赖方向固定为：

```text
设备库/操作系统
      ↓
BLE / Serial / future USB adapter
      ↓ DevicePacket
Gateway business core
      ├─> AlgorithmRunner
      ├─> RecordingStore
      └─> Northbound WebSocket
```

## 4. 策略选择与配置

配置加载只解析和校验选中策略的必需参数。休眠策略配置允许保留，便于修改 `data_source.type` 后通过服务重启切换；休眠参数不会触发驱动导入或设备访问。

策略注册表示意：

```python
_STRATEGIES = {
    "bluetooth": create_bluetooth,
    "serial": create_serial,
    "usb": reject_unconfirmed_native_usb,
}
```

`usb` 是产品配置词汇的一部分，但当前工厂会明确报告缺失 VID/PID、接口、端点、传输类型和 Linux 驱动契约。若设备枚举为 TTY，操作员必须选择 `serial`，不能选择 `usb`。

配置变更不热加载。systemd 重启后，新进程只构造新选择的适配器，旧进程停止时先尽力发送停止命令并关闭句柄。

### 4.1 串口参数

| 参数 | 默认值/约束 | 用途 |
|---|---|---|
| `device` | `auto` 或绝对设备路径 | 自动遍历或固定候选入口 |
| `candidate_types` | `ttyACM`、`ttyUSB` 的非空组合 | 限制只探测 USB 派生 TTY |
| `baud_rate` | 固定 115200 | 已确认协议参数 |
| `handshake_timeout_ms` | 默认 1000，可配置范围受校验 | 单候选完整握手等待时间 |
| `command_response_timeout_ms` | 默认 1000，可配置范围受校验 | 回写 7 字节握手 ACK 后等待单字节 `0x01` 的时间；`0xE1`/`0xE0` 不使用该超时 |
| `data_timeout_seconds` | 默认 5 | 无有效帧时触发重连 |
| `reconnect_delay_seconds` | 默认 3 | 同一串口策略重新枚举间隔 |
| `stats_interval_seconds` | 默认 10 | 丢包和接收汇总日志周期 |
| `max_buffer_bytes` | 默认 65536，受上限校验 | 防止非法字节流无限占用内存 |
| `dtr`、`rts` | 默认 `false` | 在打开端口前设置调制解调器控制线状态 |

DTR/RTS 默认关闭是软件侧的保守实现，不代表设备方已确认其电气影响。HUP、USB 转串口芯片默认电平、内核打开/关闭瞬态仍需用最终硬件测量和验证。

回写完整 7 字节握手 ACK 后只读取一个字节，且只接受 `0x01` 作为 ACK 校验成功。日志在不记录完整原文的前提下输出分类：`single_byte_0x01`、`partial_handshake` 或 `other_single_byte`；单字节额外记录 `singleByteHex`。`AA` 会被归为仍在重复握手并拒绝，不得把周期握手误判为 ACK 校验成功。`0xE1`、`0xE0` 都是无响应单字节指令，只记录写入耗时与成功/失败，不读取串口响应。进入数据流后仍出现完整固定握手时另行累计 `streamHandshakeFrames`，并在有效帧超时和周期汇总中输出。

## 5. 统一设备事件

适配器向 Gateway 发送不可变 `DevicePacket`：

```text
transport       bluetooth | serial | future usb
channel         ff31 | ff32 | ff51 | serial.frame | future channel
value           未改写 bytes
received_at_ms  适配器通知/读帧边界的 Unix 毫秒时间
```

时间在适配器边界生成，避免进入异步队列后由业务层补时间造成偏差。同一串口帧产生的 `serial.frame`、`ff31` 和 `ff51` 使用同一个接收时间。

Gateway 的处理规则：

1. 所有事件先尝试写入当前会话的内部设备记录；未开始录制时安全忽略。
2. `serial.frame` 和 `ff32` 不进入现有算法窗口；前者用于内部追溯，后者同时更新佩戴状态。
3. `ff31` 映射现有 EEG 原始流，必须为 20 字节。
4. `ff51` 映射现有心率原始流，必须为 1 字节。
5. 其他通道记录受限长度的元信息告警，不记录原始内容，也不退出进程。

为了兼容仓库内旧测试和受控调用，Gateway 暂时保留 `(channel, bytes)` 包装入口；生产适配器只使用 `DevicePacket` 入口。

## 6. 串口发现与目标识别

### 6.1 候选集合和稳定顺序

自动发现只读取 `/dev/serial/by-id/*`、配置允许的 `/dev/ttyACM*` 和 `/dev/ttyUSB*`。每个路径必须能解析为允许类型的真实 TTY。相同真实设备去重，优先保留 `/dev/serial/by-id/` 别名。`ttyS*`、主板控制台、蓝牙 RFCOMM 和其他系统 TTY 不进入候选集合。

排序键依次为：是否为 by-id、USB 父设备、接口号、物理 sysfs 路径、候选路径。这样多接口设备和内核 TTY 编号变化时仍能形成可解释的稳定顺序。

对每个候选尽力读取并记录原路径、解析路径、VID、PID、USB 序列号、USB 父设备 sysfs 路径、接口号、驱动和 TTY 物理路径。系统缺少某字段时记录为空，不以此拒绝候选。找到目标后再输出一条目标身份汇总。日志不记录完整原始数据帧、握手 ACK 响应内容或生理数据。

### 6.2 串行探测状态机

```text
not_connected（未连接）
  ↓ 开始一轮遍历
connecting（连接中）：发现并稳定排序候选
  ↓
按 115200 8-N-1、无流控、配置的 DTR/RTS 打开一个候选
  ↓
只读取，等待完整 AA 55 01 01 01 01 6F
  ├─ 所有候选超时/错误 → not_connected → 下一轮遍历
  └─ 匹配 → 停止遍历并保留端口 → connected（已连接）
                                      ↓
                 validating（校验中）→ 立即回写相同 7 字节 ACK
                     ├─ 超时/非 0x01/读写错误 → validation_failed
                     └─ 单字节 0x01 → ACK 校验成功 → 初始化干净算法会话
                                              ├─ 失败 → validation_failed，不发送 E1
                                              └─ 成功 → 无响应写入 E1
                                                           ├─ 写失败 → validation_failed
                                                           └─ 写成功 → validated → 数据流
                                                                    ↓
                                                     端口关闭/拔出/有效帧超时
                                                                    ↓
                                                         disconnected（断开）
```

遍历严格串行；握手前不允许发送 `0xE1`、`0xE0` 或其他控制字节。第一台完整握手匹配设备立即停止遍历，此时“找到设备”就是 `connected`，但还不代表设备可出数。网关立即回写相同握手 ACK，并在 `validating` 中等待设备返回独立单字节 `0x01`；这是握手 ACK 的校验结果，不是 `0xE1` 响应。ACK 校验成功后才初始化算法，只有算法进程存活并报告可用后才无响应发送 `0xE1`；写入成功并进入 `validated` 后，串口适配器才进入数据流，网关才启动实时录制并允许串口 EEG/HR 进入北向消息。`0xE0` 同样只写不读。本期部署约束为只连接一台目标耳机，不实现多目标消歧。

## 7. 数据分帧与算法兼容

| 偏移 | 长度 | 处理 |
|---|---:|---|
| 0 | 3 | 必须为包头 `AA AA AA` |
| 3 | 1 | 必须等于固定总长度 28 |
| 4 | 2 | 无符号大端序列号 |
| 4～23 | 20 | 原样投影为现有 `ff31` 算法输入，包含序列号和 18 字节 EEG |
| 24 | 1 | 原样投影为现有 `ff51` 心率输入 |
| 25～27 | 3 | 必须为包尾 `BB BB BB` |

解析器处理半包、粘包、前导垃圾和损坏帧。无包头时仅保留可能构成下一包头的末尾字节；长度或包尾不合法时逐字节重新同步。缓冲超过上限时丢弃最旧字节并记录计数。任何单帧错误均不得导致主进程退出。

算法继续接收与 BLE profile 相同的 `ff31` 20 字节和 `ff51` 1 字节，不重采样、不缩放、不改变字节序。算法分组和结果正确性必须用真实设备录制数据比对；源码投影正确不能代替算法 POC。

## 8. 序列号与丢包统计

序列号使用无符号 16 位大端值，并扩展为跨回绕的单调序列。首帧建立基线，`0xFFFF` 后的 `0x0000` 属于顺序包。

```text
expectedPackets = extendedHighestSequence - baseSequence + 1
lostPackets = max(0, expectedPackets - receivedUniquePackets)
lossRatePercent = lostPackets / expectedPackets × 100%
```

重复包不增加唯一接收数；有限窗口内收到缺失旧包时归类为乱序补包，可降低累计丢包数；超过窗口的旧包归类为迟到，不再改写累计唯一数。周期汇总还以相邻累计快照计算区间期望、唯一接收、丢包和丢包率。

这是设备到网关串口帧的序列丢包率，不等同于 USB 总线错误率、WebSocket 丢包率、算法有效率或无线信号质量。

## 9. 持久化设计

现有会话目录继续保存 EEG/HR 原始投影和算法结果，供既有导出与录播使用。`serial.frame`、传输类型和内部诊断字段不写入该目录，不修改 manifest，不进入 ZIP，不改变录播。

完整设备事件写入：

```text
<recording-root>/internal-device/<recordingId>/packets.jsonl
```

每行包含 `sessionId`、`transport`、`channel`、`receivedAtMs`、`byteLength`、`encoding` 和 `bytesBase64`。这满足完整 28 字节串口帧原样持久化以及来源追溯，同时与录制会话和时间关联。

内部记录包含生理原始数据，必须继承录制根目录的最小权限和保留策略，不得加入运行日志、诊断包、Git、普通网页下载或现有对外采集包。若未来需要对外交付这些字段，必须新建外部文档版本并走发布门禁。

## 10. 北向、错误与运维

设备策略和前端访问策略相互独立。`local_browser` 与 `wired_b_side` 都复用同一个 Gateway 和 WebSocket 请求处理；设备传输来源不进入北向状态、数据事件或错误字段。

| 阶段 | 失败处理 | 可观察信息 |
|---|---|---|
| 配置 | 启动失败，不访问设备 | 参数名、允许范围、策略值 |
| 原生 USB 选择 | 启动失败，不声明接口 | 未确认 VID/PID、接口、端点和驱动契约 |
| 发现 | 保持离线，延时后重试 | 尝试次数、候选数、模式、超时，by-id/ttyACM/ttyUSB 节点数量、固定路径是否存在、下次重试间隔 |
| 打开/握手 | 关闭当前候选，继续串行遍历 | 候选序号、路径、错误类型、受限错误文本；分开记录“无任何握手字节”和“有字节但无有效握手” |
| 错误握手 | 不识别为目标，窗口结束后继续下一候选 | 读取次数、非空读取次数、收到/丢弃/缓冲字节数、缓冲截断次数、最长握手前缀匹配长度和耗时；不记录载荷 |
| 握手 ACK 校验 | 超时、非 `0x01` 或读写错误则关闭目标端口并重连 | ACK 字节数、响应字节数、耗时、脱敏分类、成功/超时；不记录响应原文 |
| 算法初始化 | 关闭目标端口，进入重连且不发送 `0xE1` | 阶段、算法状态和受限错误原因 |
| `0xE1` | 写失败则关闭并重连；协议不等待响应 | 命令名、命令字节数、写入耗时、`responseExpected=false` 和成功/失败 |
| 数据流 | 无有效帧超时则关闭并重连 | 已读字节和有效帧数，非法长度/包尾计数，重同步丢弃字节、缓冲溢出、待解析字节和丢包统计 |
| `0xE0` | 写异常仍关闭，不阻塞退出；协议不等待响应 | 命令名、命令字节数、写入耗时、`responseExpected=false` 和失败原因 |

握手和数据流的非法输入日志不包含原始十六进制、Base64 或解码载荷，并显式记录 `payloadLogged=false`。丢弃字节首次及每跨越 4096 字节记录一次；非法帧记录前 3 次及之后的 2 的幂次，计数器始终累加。这样可以区分“没数据”和“一直有错误数据”，同时避免日志风暴和原始生理数据泄露。

首次设备识别直接使用 `linux/diagnose-kylin-usb-serial.sh`，耳机保持连接，无需拔插。默认模式立即保存当前 USB/TTY、接口和驱动快照；存在 `ttyACM*`、`ttyUSB*` 或 by-id 节点即返回候选成功，但不据此断言它是目标设备，最终仍由网关逐个读取固定握手确认。当前没有 TTY 时返回明确的 `current_tty_not_detected` 并保留诊断包。只有排查接线、枚举时序或偶发拔插问题时才显式使用 `--plug-cycle --timeout 60`：该模式保存拔出基线并跟踪内核 journal、`dmesg`、udev 和网关 journal，通过 sysfs/TTY 集合差区分新 USB、新 TTY 和超时。两种模式都保存过程日志、`tar.gz` 和 SHA-256，且不打开串口、不读取握手或生理载荷。

识别成功后，部署入口继续使用 `linux/setup-kylin-serial.sh` 一键备份配置、应用串口策略、补充最小组权限、验证配置和重启服务。如果执行配置时仍无 TTY，配置脚本输出上述识别命令提示。项目启动入口在打开串口前检查实际读写权限；账号已加入 TTY 所属组但当前登录会话尚未激活时，通过 `sg` 自动以该组重启一次，仍失败则立即给出注销重登/重启提示，不进入误导性的握手重试。串口候选全部打开失败时保留最后一次路径、异常类型和受限原因；只有至少一个候选成功打开但固定握手不匹配时才归类为握手失败。详细日志、诊断包导出与脱敏规则以[麒麟 V10 网关运行与串口联调内部文档](麒麟V10网关运行与串口联调内部文档.md)为准。

USB 快照优先使用 `lsusb -nn`；银河麒麟所带旧版 `usbutils` 不支持该参数时自动回退到 `lsusb`，并在快照文件中记录回退原因。设备差分仍以 sysfs 的 VID/PID、接口和驱动信息为依据，不依赖 `lsusb` 的可选格式。

### 10.1 麒麟本地算法构建与启用门禁

`linux/setup-kylin-algorithm.sh` 必须以普通用户在项目根目录运行。它校验银河麒麟 V10、x86_64、项目 Python、`sdk.lock` 和仓库内 SDK/NumCpp。麒麟软件源提供的 CMake 3.16.3 低于 SDK 要求，因此脚本使用 SHA-256 锁定的官方 Kitware CMake 3.31.6，在线时下载到项目 `.runtime/`，离线时从忽略提交的 `algorithm-packages/` 读取，并仅在本次项目构建的 `PATH` 中生效，不替换系统 CMake。系统依赖只包含 C++17 编译器、Eigen3 3.3.7 及下载工具，缺少时仅在用户输入 `yes` 后通过当前系统的 apt/dnf/yum 安装。

每次构建先写入 `.runtime/algorithm/attempt-*`，避免失败尝试破坏已有产物。构建成功后，`neurobridge.algorithm_setup` 向 bridge 发送不含人体数据的合成请求，验证进程可启动、退出码、单行 JSON 和 `algorithm` 响应对象，同时记录 bridge SHA-256、响应字段名和 stderr 字节数，不记录原始数据或算法数值。

只有自检成功才将 bridge 原子安装为 `.runtime/algorithm/neurobridge_affective_bridge`，对 `.runtime/config/gateway.toml` 生成唯一备份，再原子写入 `algorithm.enabled=true` 和项目内 bridge 命令。`linux/start-kylin-gateway.sh` 在串口模式下再次校验这些条件：算法关闭、命令越出 `.runtime/algorithm/`、文件不是普通可执行文件时均拒绝启动。运行时仍先完成握手 ACK 的 `0x01` 校验，再初始化算法；算法未就绪不会发送无响应 `0xE1`。

此门禁解决的是“当前麒麟主机能否启动并调用 bridge”，不是“真实头环算法是否正确”。真实数据的字节序、窗口分组、指标单位/范围、延迟和性能仍须在目标 N100/N150 麒麟主机上完成 POC 与现场验收。

udev 或 systemd 权限不得放开全部 USB 设备。当前串口方案只赋予服务账户访问实际 TTY 所需的最小串口组权限；取得稳定 VID/PID 后，应进一步收紧 udev 匹配。诊断包不得收集完整配置、环境变量、内部原始记录或生理数据。

## 11. 测试与验收

自动化测试覆盖配置单选、握手/ACK 校验、无响应启停写入、分帧、丢包回绕、统一事件、内部原帧保存和既有北向/录播回归。目标机 POC 还必须：

1. 记录最终系统构建号、内核、USB 控制器、TTY 路径和驱动。
2. 验证 VID/PID、USB 序列号、父设备、接口和稳定排序。
3. 在设备方见证下验证 DTR/RTS/HUP 不导致复位或误动作。
4. 验证多候选探测、握手 ACK 后 `0x01`、无响应 `0xE1`/`0xE0`、拔插重连和断电恢复。
5. 用真实数据比对 28 字节原帧、20 字节 EEG、1 字节心率和算法结果。
6. 连续运行并记录 CPU、内存、磁盘增长、非法帧和丢包率。
7. 验证本机浏览器、录制、录播、日志和诊断包导出。

只有上述证据进入验收记录后，对应项才能从“源码支持”提升为“POC 已验证”；只有交付现场按最终接线和配置复测后，才能标为“现场验收通过”。

## 13. 原生 USB 后续门禁

原生 USB 开发前必须取得并评审：VID/PID 与完整描述符、接口类和端点、传输方向/类型/包长/超时、握手与控制响应协议、内核驱动绑定规则、多设备唯一标识、最小 udev 权限，以及拔插和重新枚举样例。

信息不完整时不得通过遍历全部 USB 设备、声明未知接口、解除内核驱动或放宽全局权限来“尝试兼容”。
