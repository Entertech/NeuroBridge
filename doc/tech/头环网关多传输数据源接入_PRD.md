# 头环网关多传输数据源接入 PRD

状态：内部评审草案

日期：2026-08-27

最后更新：2026-08-31

适用范围：NeuroBridge Linux/PC 网关设备接入层

目标运行环境：麒麟系统电脑（具体版本与 CPU 架构待确认）；现有 Ubuntu LTS on x86_64（N100/N150）作为兼容与回归基线

## 1. 背景

当前网关通过 BLE 连接 Flowtime 头环，负责设备扫描、连接、通知订阅、原始数据持久化、算法调用、录播和北向 WebSocket 服务。部分部署现场可能禁用蓝牙，或设备可能提供串口、USB 等有线通信方式，因此网关需要在不改变北向业务契约的前提下支持多种设备侧传输。

本需求将设备接入方式扩展为以下三种互斥策略：

1. 蓝牙（Bluetooth Low Energy，简称 BLE）；
2. 串口（系统表现为串行字符设备，包括板载 UART、USB CDC ACM 和 USB 转串口）；
3. 原生 USB（通过 HID、Bulk 或 Interrupt 等 USB 接口通信，不表现为串口）。

一次网关进程只能选择并运行一种设备数据源。网关不得同时连接多种传输，也不得在运行时自动从一种传输切换到另一种传输。

### 1.1 首期已确认场景

- 目标耳机通过 USB 与麒麟系统电脑进行物理连接。
- 耳机在操作系统中以串口形式提供数据，因此首期配置选择 `serial`，不按原生 USB HID/Bulk 接口开发。
- 同一电脑可能存在多个串口，目标串口不能仅凭 `/dev/ttyACM*` 或 `/dev/ttyUSB*` 的编号确定。
- 网关需要枚举 USB 派生的候选串口并读取握手数据；只有握手帧校验通过后，才能判定该串口属于目标设备。
- 目标设备上电后每 200 ms 发送一次 7 字节握手帧 `AA 55 01 01 01 01 6F`；上位机返回完全相同的 7 字节 ACK 后，设备停止重复握手。
- 网关确认唯一目标串口后，向目标串口返回握手 ACK；设备停止重复握手。算法会话初始化成功后，网关发送 `0xE1` 使能脑电；停止采集时发送 `0xE0`。
- 串口参数已确认为 115200、8 数据位、无校验、1 停止位、无流控（115200 8-N-1）。
- 脑电心率数据包固定为 28 字节，包括 3 字节包头、1 字节包长、2 字节序列号、6 个 3 字节脑电值、1 字节心率和 3 字节包尾。
- 设备收到上位机 ACK 并执行 `0xE1` 使能脑电后发送脑电和心率原始数据，网关完成解析、算法计算和持久化，再通过既定北向协议分发给软件或网页。
- 设备方确认以串口形式接收数据；但接线图显示系统中存在 USB HOST、USB DEVICE/耳机和 TTL 串口三组接口，麒麟电脑实际读取的是哪一组接口及其对应设备节点仍需现场确认。
- 如果麒麟电脑接入的转换板接口已经生成可读写的 TTY 设备节点，则不需要再增加电脑侧 USB 转串口模块；如果电脑只连接 USB HOST、而 TTL 串口由其他控制器读取，则网关必须按实际数据路径配置，不能假定 USB HOST 侧直接提供 TTY。

协议依据：[军工耳机脑电串口协议](https://entertech.feishu.cn/docx/UwtYdp2RzoZQA4xTx8ccXwwQnOc?from=from_copylink)，读取修订号 178，读取日期 2026-08-31。

## 2. 产品目标

### 2.1 目标

- 允许部署人员通过本地配置明确选择 `bluetooth`、`serial` 或 `usb`。
- 支持在多个 USB 串口中通过握手协议自动发现唯一目标设备。
- 保证三种传输在业务层呈现一致的设备连接、数据接收、错误和停止语义。
- 保留设备原始字节、接收时间戳和采集会话关联，不因传输适配而改写原始数据。
- 保持现有算法、录制、录播和北向 WebSocket 行为稳定。
- 设备或所选传输不可用时，网关主服务继续运行；B 端请求数据时按现有规则使用录播。
- 为后续设备协议 POC、驱动验证、现场部署和故障定位提供清晰的验收边界。

### 2.2 非目标

- 本期不支持同时连接多个头环。
- 本期不支持蓝牙、串口、USB 并行采集、合流或去重。
- 本期不允许 B 端通过 WebSocket 选择或切换设备传输。
- 本期不做传输间自动故障转移，例如蓝牙失败后自动切到 USB。
- 本期不改变 B 端北向报文版本、请求动作、数据字段或录播规则。
- 本期不假定串口或原生 USB 的帧格式、采样率、校验算法、启停命令或算法输入分组。
- 本期不把 USB 蓝牙适配器视为“USB 数据源”；它仍属于蓝牙传输的硬件实现。
- 本期不通过遍历波特率、校验位等参数猜测串口配置；串口参数必须由设备协议明确给出。
- 本期不把握手帧当作身份认证或安全凭据；它只用于识别协议兼容的目标设备。

## 3. 名词与边界

| 名词 | 定义 | 判定示例 |
|---|---|---|
| 蓝牙数据源 | 网关经 BLE GATT 与头环通信 | 板载蓝牙或 USB 蓝牙适配器 + BlueZ/Bleak |
| 串口数据源 | 操作系统将设备暴露为串行字符设备 | `/dev/ttyS*`、`/dev/ttyUSB*`、`/dev/ttyACM*` |
| 原生 USB 数据源 | 网关直接访问 USB 接口或端点，不经 TTY | HID、Bulk、Interrupt；具体类型待设备协议确认 |
| 传输适配器 | 封装一种设备连接方式，并向网关核心提供统一生命周期和原始包回调 | BLE、Serial、USB Adapter |
| 设备协议 | 规定原始字节的分帧、字段、字节序、校验和启停命令 | BLE 已确认部分以 Flowtime 协议为准；串口握手、参数和基础帧结构已确认，字段编码与响应细节待确认；原生 USB 待确认 |
| 候选串口 | 由 USB 设备派生、允许网关进行握手探测的 TTY | `/dev/serial/by-id/*`、`/dev/ttyACM*`、`/dev/ttyUSB*` |
| 握手识别 | 网关只读候选串口并校验握手帧，以确定是否为目标设备 | 握手格式、周期和超时待协议确认 |
| 录播 | 从已保存的原始数据和算法结果回放 | 不属于第四种物理数据源，也不参与互斥配置 |

串口与原生 USB 的分类以操作系统接口为准。即使物理线缆使用 USB，只要设备在 Linux 上呈现为 `/dev/tty*`，产品配置仍选择 `serial`。

USB/udev 的 VID、PID、序列号、驱动和物理路径用于缩小候选范围；通过校验的应用层握手是目标设备的最终判定依据。不得只凭易变化的 `/dev/ttyUSB0`、`/dev/ttyACM0` 等编号认定设备。

## 4. 用户与使用场景

### 4.1 部署人员

部署人员根据现场设备和驱动条件选择唯一传输方式，填写该传输所需参数，安装服务并完成设备读写权限配置。

### 4.2 运维人员

运维人员通过服务状态和日志确认当前选择的传输、连接状态、最近数据时间范围以及错误原因，不需要读取敏感原始数据。

### 4.3 B 端客户端

B 端仍只连接网关的 WebSocket 服务，不感知设备使用蓝牙、串口还是 USB。B 端继续使用 `getStatus`、`getLatest`、`subscribe` 和 `unsubscribe`。

### 4.4 开发与测试人员

开发和测试人员可以为不同传输注入模拟设备数据，验证相同原始包经算法、录制和北向链路产生兼容结果。

## 5. 核心产品规则

### 5.1 单选规则

- 部署配置必须使用一个枚举字段选择传输类型，不使用三个可独立开启的布尔开关。
- 合法值只有 `bluetooth`、`serial`、`usb`。
- 一次进程只创建所选传输的适配器，不初始化、探测或占用其他传输资源。
- 未选择、选择未知值或所选传输缺少必需参数时，配置校验必须明确失败并给出可操作的错误原因。
- 传输切换属于部署配置变更，需由运维人员修改本地配置并重启服务后生效。
- B 端请求、网页操作或设备异常都不得触发传输切换。

### 5.2 不自动跨传输降级

所选传输连接失败、设备拔出或数据非法时，网关只重试当前传输。不得扫描或连接其他传输上的设备，也不得把另一个已接入设备当作替代数据源。

当所选设备不在线时：

- 网关北向服务继续监听；
- `getStatus` 返回现有设备离线/异常状态语义；
- B 端发起 `getLatest` 或 `subscribe` 时，网关按现有规则自动使用录播；
- 设备恢复并完成初始化后，网关停止录播并恢复实时模式；
- 旧的 B 端订阅与重连规则保持现有协议定义。

### 5.3 原始数据原则

- 适配器必须保存设备协议定义的全部原始字节，不得只保存解析后的数值。
- 网关接收时间戳由数据进入适配器后的统一边界产生，使用毫秒时间戳。
- 分帧、校验和控制字节属于设备协议层；适配器不得为迁就旧 SDK 示例而自行重编码。
- 算法输入必须保留已确认的字节序和完整分组。
- 串口和 USB 数据在真实录制数据完成比对前，不得假定与 BLE 通知具有相同分帧边界。

## 6. 功能需求

### 6.1 配置与启动

| 编号 | 需求 | 优先级 |
|---|---|---|
| DS-001 | 配置提供唯一的设备传输选择项，取值为 `bluetooth`、`serial` 或 `usb` | P0 |
| DS-002 | 启动时只校验所选传输的必需参数；未选择传输和参数冲突须输出明确错误 | P0 |
| DS-003 | 未选择的传输不得初始化驱动、扫描设备、打开端口或声明设备接口 | P0 |
| DS-004 | 修改传输类型必须重启服务后生效，不支持热切换 | P0 |
| DS-005 | 示例配置须解释 USB 串口与原生 USB 的分类差异 | P1 |
| DS-006 | 日志须记录当前传输类型，但不得记录设备敏感数据或完整原始包 | P0 |

建议的配置形态如下，仅用于表达产品语义；字段名和具体参数在实现设计评审中确定：

```toml
[data_source]
type = "serial" # bluetooth | serial | usb，三选一；首期已确认使用 serial

[bluetooth]
# BLE 设备匹配、扫描和重连参数

[serial]
# auto 表示从 USB 派生的候选 TTY 中通过握手识别唯一目标
device = "auto"
candidate_types = ["ttyACM", "ttyUSB"]
# 可配置 VID/PID、USB 序列号等范围以减少误探测，但最终仍须校验握手
baud_rate = 115200
data_bits = 8
parity = "none"
stop_bits = 1
flow_control = "none"
# handshake_timeout_ms、reconnect_delay_ms、max_frame_bytes、max_buffer_bytes
# 超时、重试和缓冲上限仍须经设备实测确认

[usb]
# vendor_id、product_id、interface、endpoint 等
# 实际字段必须来自已确认的原生 USB 协议和 Linux 驱动验证
```

### 6.2 统一适配器生命周期

三种适配器必须向网关核心提供等价的生命周期语义：

| 能力 | 产品要求 |
|---|---|
| 启动 | 打开所选传输，寻找或等待目标设备 |
| 连接中 | 报告 `connecting`，但不提前声明实时数据可用 |
| 初始化 | 完成必要订阅、端点声明、参数设置和采集启动命令 |
| 就绪 | 算法会话初始化成功后才能报告 `connected` |
| 数据 | 输出设备协议通道、未改写的原始字节和接收时间 |
| 异常 | 报告可观察错误，释放不完整连接，再按配置重试当前传输 |
| 停止 | 尽力发送设备停止采集命令，并关闭连接、端口或 USB 句柄 |

### 6.3 蓝牙传输

| 编号 | 需求 | 优先级 |
|---|---|---|
| BLE-001 | 保持已确认的 Flowtime BLE profile：`FF31`、`FF32`、`FF51` 通知及 `FF21` 启停 | P0 |
| BLE-002 | 保留现有扫描、设备匹配、连接、订阅和断线重连行为 | P0 |
| BLE-003 | 本次抽象改造不得新增 `FF52` 或改变已定义包长和字节序 | P0 |
| BLE-004 | 蓝牙回归测试须覆盖真实模式、录播回退、断连与恢复 | P0 |

### 6.4 串口传输

| 编号 | 需求 | 优先级 |
|---|---|---|
| SER-001 | 支持 `auto` 发现模式，从 `/dev/serial/by-id/` 及 USB 派生的 `/dev/ttyACM*`、`/dev/ttyUSB*` 中枚举候选串口 | P0 |
| SER-002 | 首期串口参数使用协议确认的 115200、8-N-1、无流控，不遍历尝试其他串口参数 | P0 |
| SER-003 | 串口打开失败、权限不足、设备消失、读超时和帧校验失败须转换为可观察状态 | P0 |
| SER-004 | 设备拔出后关闭失效句柄，并按配置间隔重新枚举同一串口传输下的候选设备 | P0 |
| SER-005 | 连续字节流必须使用已确认的分帧和校验规则处理半包、粘包和损坏帧 | P0 |
| SER-006 | 必须限制接收缓冲区和最大帧长，非法流量不得导致内存无限增长或主进程退出 | P0 |
| SER-007 | 识别阶段只允许读取和校验握手；握手未通过前不得发送订阅、停止或其他设备控制指令 | P0 |
| SER-008 | 不得探测主板控制台、调试串口、蓝牙串口或其他非 USB 派生的系统 TTY | P0 |
| SER-009 | 同一 USB 复合设备的多个串口必须按 USB 父设备和接口号分组；允许并行只读探测候选串口 | P0 |
| SER-010 | 必须完成当前候选集合的握手探测后再决策：0 个有效目标保持离线，1 个有效目标建立连接，多个有效目标报告歧义且不订阅 | P0 |
| SER-011 | 选中目标后应优先记录并复用 `/dev/serial/by-id/`、USB 序列号或受控 udev 别名，不长期绑定易变化的 TTY 编号 | P0 |
| SER-012 | 打开串口时的 DTR、RTS、HUP 和流控行为必须由设备方确认，避免候选探测导致设备复位或误动作 | P0 |
| SER-013 | 唯一目标握手通过后立即返回同值握手 ACK；算法会话就绪后再发送 `0xE1` 使能脑电；在协议未定义 `0xE1` 响应前，以首个完整有效数据帧作为实时数据已启动的证据 | P0 |
| SER-014 | 停止服务、设备断开或协议要求停止采集时，应尽力发送 `0xE0` 关闭脑电并关闭串口 | P1 |
| SER-015 | 握手阶段必须识别完整的 7 字节 `AA 55 01 01 01 01 6F`，不得用部分前缀或单个字节认定目标 | P0 |
| SER-016 | 设备每 200 ms 发送握手；探测超时必须覆盖至少一个完整发送周期并留出调度余量，最终值经麒麟系统实测后配置化 | P0 |

#### 6.4.1 首期串口发现与订阅流程

```text
耳机通过 USB 接入麒麟系统电脑
  → 操作系统加载 CDC ACM 或 USB-Serial 驱动并生成一个或多个 TTY
  → 网关枚举 USB 派生的候选串口
  → 按 USB 父设备、VID/PID、序列号、驱动和接口号进行分组与初筛
  → 使用已确认的同一组串口参数打开候选端口
  → 读取到完整握手帧后立即返回同值 ACK；握手前不发送 0xE1/0xE0 或订阅指令
  → 使用有界滚动缓冲解析半包、粘包和非法帧
  → 完成当前候选集合的握手探测
      ├─ 0 个有效目标：关闭候选端口，保持离线并等待重试
      ├─ 1 个有效目标：保留目标端口，关闭其他端口
      └─ 多个有效目标：报告目标不唯一，关闭候选端口，不发送 0xE1/0xE0 或订阅
  → 恰好一个有效目标：保留目标端口，进入算法会话初始化
  → 设备停止每 200 ms 重复握手
  → 初始化新的算法会话
  → 通过目标串口发送 0xE1 使能脑电
  → 在未定义指令响应前，等待首个完整有效的 28 字节数据帧
  → 接收脑波和心率原始数据
  → 解析、持久化并调用算法
  → 通过既定北向协议向软件或网页分发
```

候选串口可以并行探测以避免每个端口串行等待一个完整握手周期，但必须限制最大并发数、单轮探测时长、读取缓冲区和日志频率。当前目标处于正常 `connected` 状态时不得继续扫描并切换到其他串口。

#### 6.4.2 已确认的握手与控制指令

| 项目 | 已确认定义 | 仍需确认 |
|---|---|---|
| 握手发送条件 | 设备上电后、尚未收到有效 ACK | 串口重开、电脑重启或异常恢复时是否自动回到握手状态 |
| 握手周期 | 每 200 ms 一次 | 允许的周期误差和上位机探测超时 |
| 握手帧 | `AA 55 01 01 01 01 6F`，共 7 字节 | 各字节字段含义及 `0x6F` 是否为校验值 |
| 上位机 ACK | 与握手帧完全相同 | ACK 是否允许重发、设备是否返回额外确认 |
| ACK 后行为 | 设备停止重复握手 | ACK 后等待 `0xE1` 的超时和恢复规则 |
| 开启脑电 | `0xE1` | 是单字节指令还是需要外层帧；成功/失败响应和幂等规则 |
| 关闭脑电 | `0xE0` | 是单字节指令还是需要外层帧；成功/失败响应和幂等规则 |

收到完整的 7 字节握手帧后，网关必须立即向发送该握手的候选串口回复同值 ACK；ACK 不等待算法初始化。完整探测候选集合后，只有恰好一个有效目标可以继续初始化算法并发送 `0xE1`，其他候选端口不得发送 `0xE1`、`0xE0` 或订阅指令。若多个候选均返回握手，ACK 可能已分别发送，需记录目标不唯一并按设备方确认的复位/重新上电规则恢复，不能随机选择目标。

#### 6.4.3 已确认的数据帧结构

协议给出的数据帧总长为 28 字节（`0x1C`）：

| 偏移 | 长度 | 字段 | 已确认值/含义 | 仍需确认 |
|---:|---:|---|---|---|
| 0 | 3 | 包头 | `AA AA AA` | 无 |
| 3 | 1 | 包长字段 | `0x1C`，等于 28 | 原文名称为“校验位(包长)”，是否还有校验语义 |
| 4 | 2 | 序列号 | 示例 `00 01` | 大小端、起始值、回绕和丢包判断规则 |
| 6 | 3 | 脑电左 1 | 第 1 个左通道样本 | 大小端、有符号性、单位、量程和缩放 |
| 9 | 3 | 脑电右 1 | 第 1 个右通道样本 | 同上 |
| 12 | 3 | 脑电左 2 | 第 2 个左通道样本 | 同上 |
| 15 | 3 | 脑电右 2 | 第 2 个右通道样本 | 同上 |
| 18 | 3 | 脑电左 3 | 第 3 个左通道样本 | 同上 |
| 21 | 3 | 脑电右 3 | 第 3 个右通道样本 | 同上 |
| 24 | 1 | 心率 | 示例 `0x5A` | 单位、范围、无效值和刷新语义 |
| 25 | 3 | 包尾 | `BB BB BB` | 无 |

该协议当前没有定义独立 CRC 或 checksum。实现可以校验固定包头、`0x1C` 包长和固定包尾，但在设备方明确前不得把某个业务字段当作 CRC，也不得自行增加或改写设备帧。

一次串口 `read()` 返回的数据不等于一个完整协议帧。实现必须维护有界滚动缓冲，按“查找帧头 → 读取长度 → 等待完整帧 → 校验 → 分发”的顺序解析，并能从损坏字节中重新同步。

### 6.6 数据处理、算法与录制

| 编号 | 需求 | 优先级 |
|---|---|---|
| CORE-001 | 网关业务层不得直接依赖 Bleak、串口库或 USB 库的回调细节 | P0 |
| CORE-002 | 三种适配器统一输出设备协议通道、原始字节、接收时间和来源类型 | P0 |
| CORE-003 | 数据解析器按已确认的设备协议工作，不按传输库返回长度猜测帧格式 | P0 |
| CORE-004 | 原始记录和算法结果继续按会话分别持久化并可关联采集窗口 | P0 |
| CORE-005 | 录播直接读取已保存的原始数据和算法结果，不重新计算算法 | P0 |
| CORE-006 | 传输来源可写入内部日志或录制元数据；如需改变已发布采集包格式，必须另行评审和发布文档 | P1 |
| CORE-007 | 新设备连接就绪时必须创建干净的算法会话，未完成初始化的数据不得进入算法 | P0 |
| CORE-008 | 单个非法包或算法异常不得导致设备适配器、北向服务或主进程退出 | P0 |

### 6.7 北向兼容性

本 PRD 不授权修改已发布或预发布的 B 端协议。实现必须满足：

- 根对象继续使用 `{protocolVersion, code, data, message}`；
- 报文 `protocolVersion` 保持版本台账中的当前值；
- `getStatus`、`getLatest`、`subscribe` 和 `unsubscribe` 的行为保持不变；
- 实时与录播继续分别使用 `mode="live"` 和 `mode="replay"`；
- 不向 B 端增加 `transport`、`deviceId` 或 `gatewayId`；
- B 端不需要知道或适配设备侧传输方式；
- 如果后续确需向 B 端暴露传输类型或新增错误字段，必须按北向协议发布门禁另行立项。

## 7. 状态与异常处理

### 7.1 期望状态流

```text
服务启动
  → 校验唯一数据源配置
  → 创建所选适配器
  → connecting
  → 设备连接及协议初始化
  → 算法会话初始化
  → connected / live
  → 断开或错误
  → disconnected
  → 释放资源
  → 等待配置的重试间隔
  → 仅重试当前所选适配器
```

### 7.2 错误分类

| 类别 | 示例 | 期望行为 |
|---|---|---|
| 配置错误 | 未选择传输、未知类型、缺少所选传输必需参数 | 拒绝以错误配置启动，指出具体字段 |
| 设备不存在 | BLE 未发现、串口路径不存在、USB 未枚举 | 北向服务保持可用，记录状态并重试当前传输 |
| 目标不唯一 | 多个候选串口都返回有效目标握手 | 关闭所有候选端口，不发送订阅，记录候选的非敏感标识并等待部署人员限定 |
| 权限错误 | TTY 或 USB 接口无权限 | 记录设备路径/VID/PID 等非敏感定位信息和修复提示，不无限高频重试 |
| 连接中断 | BLE 断连、串口拔出、USB reset/disconnect | 关闭失效资源，状态变为离线，按配置重连 |
| 非法数据 | 包头/包长/包尾错误、帧不完整、未知通道 | 丢弃或隔离当前非法帧，计数并限频记录，不退出主进程 |
| 数据积压 | 串口/USB 接收速度超过处理能力 | 使用有界缓冲和可观察丢弃策略；具体上限待性能 POC 确认 |
| 算法异常 | 初始化或计算失败 | 标记结果无效并记录原因，保留原始数据，主服务继续运行 |

## 8. 非功能需求

### 8.1 可靠性

- 任一设备侧异常不得中断 WebSocket 监听、录播或其他网关管理能力。
- 设备重连、服务重启和系统重启后，只恢复配置指定的传输。
- 适配器必须幂等停止，避免重复关闭导致主进程异常。
- 所有读取缓冲区、待处理队列和重试频率必须有上限并可配置。

### 8.2 性能

- 新增传输抽象不得改变现有每 600 ms 的北向连续数据分组语义。
- 串口和 USB 的接收吞吐必须覆盖设备协议确认的峰值数据率，并保留安全余量。
- 端到端延迟、CPU、内存和丢包率须在目标 N100/N150 + Ubuntu LTS 上实测，不在 PRD 中预设未经验证的数值。

### 8.3 安全与权限

- 服务仅获得所选设备所需的最小访问权限。
- 不允许使用全局可写的 TTY/USB 权限作为交付方案。
- 日志不得记录完整敏感原始数据、受试者隐私数据或凭据。
- USB/串口设备标识不得被误当作北向鉴权凭据。

### 8.4 可观测性

日志和内部指标至少包括：

- 网关应用版本和当前选择的传输类型；
- 连接状态变化及时间；
- 非敏感设备匹配信息；
- 候选串口数量、握手成功数量、选中的稳定设备标识及目标不唯一状态；
- 最近收到有效数据的时间范围；
- 重连次数、非法帧计数、缓冲溢出计数和错误原因；
- 算法会话初始化及异常状态。

## 9. 验收标准

### 9.1 通用验收

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AC-001 | 单选校验 | 三种合法值分别可启动；缺失或未知值被拒绝；进程不会同时创建两个适配器 |
| AC-002 | 资源隔离 | 选择一种传输时，其他两种传输没有扫描、打开、声明或权限访问行为 |
| AC-003 | 实时链路 | 所选设备数据可经解析、算法、录制和北向订阅完整流转 |
| AC-004 | 原始数据一致性 | 保存的原始字节与设备侧抓取数据逐字节一致 |
| AC-005 | 设备断线 | 断线后北向服务继续运行，状态可观察，录播回退符合现有规则 |
| AC-006 | 设备恢复 | 仅重连所选传输；算法建立新会话；实时恢复后停止录播 |
| AC-007 | 服务端不可达与恢复 | B 端断开不影响设备采集主循环；重连后先 `getStatus` 并重新订阅 |
| AC-008 | 录播兼容 | 三种传输采集产生的数据均可从保存结果录播，且录播不重新计算算法 |
| AC-009 | 长时间运行 | 覆盖双方确认的连续运行时长，无句柄泄漏、无界内存增长或主进程退出 |
| AC-010 | 蓝牙回归 | 现有 Flowtime BLE 扫描、连接、FF31/FF32/FF51、FF21 启停和重连测试通过 |

### 9.2 串口专项验收

- 覆盖正常分帧、半包、粘包、损坏帧、读超时和连续高吞吐。
- 覆盖设备启动前不存在、运行中拔出、重新插入后设备路径保持或变化的场景。
- 覆盖权限不足、端口被占用和串口参数错误。
- 构造多个 USB 串口，验证系统只探测候选 USB TTY，不打开控制台或其他非候选串口。
- 验证候选串口中 0、1、多个有效握手三种结果；只有唯一有效目标可以收到订阅指令。
- 验证同一 USB 复合设备包含多个串口时，网关能按父设备与接口号分组并从握手端口识别目标。
- 验证重新插拔导致 `/dev/ttyUSB*` 或 `/dev/ttyACM*` 编号变化后仍可重新发现目标。
- 验证收到完整握手前不发送 `0xE1`、`0xE0` 或订阅指令；收到握手后立即返回同值 ACK，候选探测不会因 DTR/RTS 行为使设备异常复位。
- 按接线图逐项核对 HOST、DEVICE/耳机和 TTL 三组接口，验证电源方向、TTL 电平、RX/TX 方向、D+/D− 连通关系和屏蔽层处理。
- 验证麒麟电脑实际读取路径：USB HOST 侧、TTL 串口侧或转换板的其他 TTY 接口；记录对应稳定设备节点。
- 验证错误接线或反向供电不会损坏耳机、转换板或麒麟电脑，并在文档中保留现场照片和测试结论。
- 验证设备每 200 ms 重复发送 `AA 55 01 01 01 01 6F`；每个收到完整握手的候选串口立即收到同值 ACK，最终只有单一目标继续发送 `0xE1` 并进入采集。
- 验证算法会话就绪后发送 `0xE1`，收到首个完整有效数据帧后进入实时状态；停止时尽力发送 `0xE0`。
- 验证 28 字节数据帧的 `AA AA AA` 包头、`0x1C` 包长、2 字节序列号、6 个 3 字节脑电值、1 字节心率和 `BB BB BB` 包尾。
- 使用真实录制数据核对字节序、帧边界、时间戳和算法输入分组。

### 9.3 原生 USB 专项验收

- 覆盖同 VID/PID 多设备时的唯一匹配策略。
- 覆盖接口声明失败、端点错误、短读、超时、USB reset、拔出和重新枚举。
- 验证 udev 权限仅作用于目标设备。
- 使用 USB 抓取与网关保存数据核对原始字节和包边界。

## 10. 实施阶段与交付门禁

### 阶段 A：协议与硬件确认

- 取得串口和后续原生 USB 候选的正式设备通信规范。
- 确认麒麟系统具体版本与 CPU 架构，以及目标设备使用 CDC ACM 还是内置 USB-Serial 芯片。
- 确认目标硬件、Linux 驱动、VID/PID、USB 序列号、候选串口接口号和串口参数。
- 对照协议修订号 178 确认握手 ACK、`0xE1`/`0xE0` 指令封装、28 字节数据帧、错误恢复和最大数据率。

门禁：协议或硬件资料不完整时，只能搭建模拟适配器，不得声明真实设备 POC 已完成。

### 阶段 B：适配器抽象与蓝牙回归

- 抽离统一设备适配器接口。
- 将现有 BLE 实现接入统一接口。
- 完成配置单选校验和 BLE 全量回归。

门禁：BLE 行为、原始数据和北向结果必须与改造前兼容。

### 阶段 C：串口 POC

- 在目标麒麟系统上使用目标设备完成多串口枚举、握手识别、唯一目标选择、订阅、分帧、停止订阅、断线重连和真实数据比对。
- 验证原始记录、算法输入和录播兼容性。

### 阶段 D：原生 USB POC（后续候选）

- 首期已确认使用 USB 物理连接下的串口通信，本阶段不作为首期交付前提。
- 使用目标设备和目标 Linux 主机验证驱动、权限、接口、端点和热插拔。
- 验证原始记录、算法输入和录播兼容性。

### 阶段 E：部署与现场验收

- 更新示例配置、安装脚本、systemd 权限和运维文档。
- 在目标麒麟系统电脑执行串口验收矩阵，并在 Ubuntu x86_64 兼容基线上执行蓝牙及跨平台回归矩阵。
- 明确记录“源码/文档支持”“POC 已验证”和“现场验收通过”的不同结论。

## 11. 风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 串口/USB 协议与 BLE 数据格式不同 | 复用旧解析器可能产生静默错误 | 以正式设备协议和逐字节真实数据比对为准 |
| USB CDC 被误配置为原生 USB | 重复实现或无法打开设备 | 按 Linux 是否呈现 `/dev/tty*` 明确分类 |
| 多设备具有相同标识 | 网关连接错误头环 | 增加经确认的唯一匹配字段，禁止随机选择 |
| 无差别遍历系统串口 | 干扰控制台、调试设备或其他业务外设 | 只枚举 USB 派生候选 TTY，并允许配置 VID/PID 等候选范围 |
| 多个串口均返回有效握手 | 随机选择导致连接错误设备 | 完整探测候选集合；多于一个有效目标时拒绝订阅并要求进一步限定 |
| 打开候选串口触发 DTR/RTS | 设备复位或进入非预期模式 | 由设备方确认控制线行为，探测阶段禁止发送控制指令 |
| `0xE1`/`0xE0` 指令封装未说明 | 单字节发送与设备实际预期不符 | 在真实设备 POC 前由设备方确认完整下行字节序列和响应语义 |
| 数据帧未定义独立校验 | 传输损坏可能只靠帧头、长度和包尾发现 | 不自行发明 CRC；记录非法帧并推动设备方明确校验能力 |
| 24 位脑电编码未说明 | 大小端或符号解释错误导致算法输入失真 | 用正式字段定义和真实样本逐字节比对后才进入算法 |
| Linux 设备节点重枚举 | 固定路径失效 | 使用稳定 udev 标识或经确认的唯一设备属性 |
| 权限配置过宽 | 增加本机设备访问风险 | 使用最小 udev 规则和专用服务用户 |
| 热插拔导致句柄或任务泄漏 | 长时间运行不稳定 | 统一生命周期、幂等清理和压力测试 |
| 适配器抽象泄漏传输细节 | 业务层出现分支扩散 | 固定统一事件契约并进行模拟适配器测试 |
| 未经确认直接重采样或重编码 | 算法结果不可信 | 原始字节持久化，真实数据回归前禁止转换 |

## 12. 待确认事项

已确认目标耳机使用 USB 物理连接并在电脑侧以串口形式接收数据；同一电脑可能存在多个候选串口，最终通过握手识别目标。以下问题仍须在实现前由设备方、算法方或项目双方确认：

1. 目标麒麟系统的发行版、版本、内核版本和 CPU 架构是什么？
2. 麒麟电脑实际读取的是 USB HOST 侧 TTY、TTL 串口侧 TTY，还是转换板的其他 TTY 接口？
3. 设备枚举为 `/dev/ttyACM*` 还是 `/dev/ttyUSB*`，使用 CDC ACM 还是哪一种 USB-Serial 芯片及驱动？
4. 设备的 VID、PID、USB 序列号、USB 父设备与多串口接口号是什么？
5. 接线图中的 `VDD`、`VIN`、`VBUS` 电压/电流方向和 TTL 电平分别是什么？`RX/TX` 的方向如何连接？
6. HOST/DEVICE 两侧 D+/D− 是否交叉，屏蔽层如何连接，USB 接口型号、线序、插拔和限流要求是什么？
7. 握手帧各字节的含义是什么，`0x6F` 是否为校验值？允许的握手周期误差是多少？
8. 哪些字段可以在多个有效握手设备之间唯一选择目标？当前握手帧固定且不含明显设备序列号，部署是否允许结合 USB 序列号限定？
9. `0xE1` 和 `0xE0` 是直接发送的单字节指令，还是需要包头、长度、序号、包尾或校验？是否存在成功/失败响应？
10. 数据帧第 4 字节原文为“校验位(包长)”且值为 `0x1C`，其语义是否仅为包长？协议是否另有 CRC/checksum？
11. 2 字节序列号的大小端、起始值、回绕、跳号和丢包判断规则是什么？
12. 六个 24 位脑电值、1 字节心率的编码、单位、采样率、超时、重连和算法输入分组是什么？

## 13. 文档影响

本 PRD 是内部产品需求，不修改当前 B 端北向协议、版本台账或已锁定的对外文档。后续实现时：

- 若只替换网关内部设备传输且 B 端可观察行为不变，应更新 README、内部对接方案和版本变更记录中的未发布审计记录；
- 若改变采集包文件或字段，应按采集包文档的独立发布流程处理；
- 若新增 B 端字段、状态、错误或请求行为，必须先完成北向契约评审，并按版本台账发布门禁创建新版本，禁止回写已发布文档。
