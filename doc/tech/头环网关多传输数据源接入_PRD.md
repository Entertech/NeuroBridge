# 头环网关多传输数据源接入 PRD

状态：内部评审草案

日期：2026-08-27

适用范围：NeuroBridge Linux/PC 网关设备接入层

目标平台：Ubuntu LTS on x86_64（N100/N150）

## 1. 背景

当前网关通过 BLE 连接 Flowtime 头环，负责设备扫描、连接、通知订阅、原始数据持久化、算法调用、录播和北向 WebSocket 服务。部分部署现场可能禁用蓝牙，或设备可能提供串口、USB 等有线通信方式，因此网关需要在不改变北向业务契约的前提下支持多种设备侧传输。

本需求将设备接入方式扩展为以下三种互斥策略：

1. 蓝牙（Bluetooth Low Energy，简称 BLE）；
2. 串口（系统表现为串行字符设备，包括板载 UART、USB CDC ACM 和 USB 转串口）；
3. 原生 USB（通过 HID、Bulk 或 Interrupt 等 USB 接口通信，不表现为串口）。

一次网关进程只能选择并运行一种设备数据源。网关不得同时连接多种传输，也不得在运行时自动从一种传输切换到另一种传输。

## 2. 产品目标

### 2.1 目标

- 允许部署人员通过本地配置明确选择 `bluetooth`、`serial` 或 `usb`。
- 保证三种传输在业务层呈现一致的设备连接、数据接收、错误和停止语义。
- 保留设备原始字节、接收时间戳和采集会话关联，不因传输适配而改写原始数据。
- 保持现有算法、录制、录播和北向 WebSocket 行为稳定。
- 设备或所选传输不可用时，网关主服务继续运行；B 端请求数据时按现有规则使用录播。
- 为后续设备协议 POC、驱动验证、现场部署和故障定位提供清晰的验收边界。

### 2.2 非目标

- 本期不支持同时连接多个头环。
- 本期不支持蓝牙、串口、USB 并行采集、合流或去重。
- 本期不允许 B 端通过 WebSocket 选择或切换设备传输。
- 本期不做传输间自动故障转移，例如蓝牙失败后自动切到 USB。
- 本期不改变 B 端北向报文版本、请求动作、数据字段或录播规则。
- 本期不假定串口或原生 USB 的帧格式、采样率、校验算法、启停命令或算法输入分组。
- 本期不把 USB 蓝牙适配器视为“USB 数据源”；它仍属于蓝牙传输的硬件实现。

## 3. 名词与边界

| 名词 | 定义 | 判定示例 |
|---|---|---|
| 蓝牙数据源 | 网关经 BLE GATT 与头环通信 | 板载蓝牙或 USB 蓝牙适配器 + BlueZ/Bleak |
| 串口数据源 | 操作系统将设备暴露为串行字符设备 | `/dev/ttyS*`、`/dev/ttyUSB*`、`/dev/ttyACM*` |
| 原生 USB 数据源 | 网关直接访问 USB 接口或端点，不经 TTY | HID、Bulk、Interrupt；具体类型待设备协议确认 |
| 传输适配器 | 封装一种设备连接方式，并向网关核心提供统一生命周期和原始包回调 | BLE、Serial、USB Adapter |
| 设备协议 | 规定原始字节的分帧、字段、字节序、校验和启停命令 | BLE 已确认部分以 Flowtime 协议为准；串口和 USB 待确认 |
| 录播 | 从已保存的原始数据和算法结果回放 | 不属于第四种物理数据源，也不参与互斥配置 |

串口与原生 USB 的分类以操作系统接口为准。即使物理线缆使用 USB，只要设备在 Linux 上呈现为 `/dev/tty*`，产品配置仍选择 `serial`。

## 4. 用户与使用场景

### 4.1 部署人员

部署人员根据现场设备和驱动条件选择唯一传输方式，填写该传输所需参数，安装服务并完成设备读写权限配置。

### 4.2 运维人员

运维人员通过服务状态和日志确认当前选择的传输、连接状态、最近数据时间范围以及错误原因，不需要读取敏感原始数据。

### 4.3 B 端客户端

B 端仍只连接网关的 WebSocket 服务，不感知设备使用蓝牙、串口还是 USB。B 端继续使用 `getStatus`、`getLatest`、`subscribe` 和 `unsubscribe`。

### 4.4 开发与测试人员

开发和测试人员可以为不同传输注入模拟设备数据，验证相同原始包经算法、录制和北向链路产生兼容结果。

## 5. 核心产品规则

### 5.1 单选规则

- 部署配置必须使用一个枚举字段选择传输类型，不使用三个可独立开启的布尔开关。
- 合法值只有 `bluetooth`、`serial`、`usb`。
- 一次进程只创建所选传输的适配器，不初始化、探测或占用其他传输资源。
- 未选择、选择未知值或所选传输缺少必需参数时，配置校验必须明确失败并给出可操作的错误原因。
- 传输切换属于部署配置变更，需由运维人员修改本地配置并重启服务后生效。
- B 端请求、网页操作或设备异常都不得触发传输切换。

### 5.2 不自动跨传输降级

所选传输连接失败、设备拔出或数据非法时，网关只重试当前传输。不得扫描或连接其他传输上的设备，也不得把另一个已接入设备当作替代数据源。

当所选设备不在线时：

- 网关北向服务继续监听；
- `getStatus` 返回现有设备离线/异常状态语义；
- B 端发起 `getLatest` 或 `subscribe` 时，网关按现有规则自动使用录播；
- 设备恢复并完成初始化后，网关停止录播并恢复实时模式；
- 旧的 B 端订阅与重连规则保持现有协议定义。

### 5.3 原始数据原则

- 适配器必须保存设备协议定义的全部原始字节，不得只保存解析后的数值。
- 网关接收时间戳由数据进入适配器后的统一边界产生，使用毫秒时间戳。
- 分帧、校验和控制字节属于设备协议层；适配器不得为迁就旧 SDK 示例而自行重编码。
- 算法输入必须保留已确认的字节序和完整分组。
- 串口和 USB 数据在真实录制数据完成比对前，不得假定与 BLE 通知具有相同分帧边界。

## 6. 功能需求

### 6.1 配置与启动

| 编号 | 需求 | 优先级 |
|---|---|---|
| DS-001 | 配置提供唯一的设备传输选择项，取值为 `bluetooth`、`serial` 或 `usb` | P0 |
| DS-002 | 启动时只校验所选传输的必需参数；未选择传输和参数冲突须输出明确错误 | P0 |
| DS-003 | 未选择的传输不得初始化驱动、扫描设备、打开端口或声明设备接口 | P0 |
| DS-004 | 修改传输类型必须重启服务后生效，不支持热切换 | P0 |
| DS-005 | 示例配置须解释 USB 串口与原生 USB 的分类差异 | P1 |
| DS-006 | 日志须记录当前传输类型，但不得记录设备敏感数据或完整原始包 | P0 |

建议的配置形态如下，仅用于表达产品语义；字段名和具体参数在实现设计评审中确定：

```toml
[data_source]
type = "bluetooth" # bluetooth | serial | usb，三选一

[bluetooth]
# BLE 设备匹配、扫描和重连参数

[serial]
# device、baud_rate、data_bits、parity、stop_bits、flow_control
# 实际值必须来自已确认的串口协议

[usb]
# vendor_id、product_id、interface、endpoint 等
# 实际字段必须来自已确认的原生 USB 协议和 Linux 驱动验证
```

### 6.2 统一适配器生命周期

三种适配器必须向网关核心提供等价的生命周期语义：

| 能力 | 产品要求 |
|---|---|
| 启动 | 打开所选传输，寻找或等待目标设备 |
| 连接中 | 报告 `connecting`，但不提前声明实时数据可用 |
| 初始化 | 完成必要订阅、端点声明、参数设置和采集启动命令 |
| 就绪 | 算法会话初始化成功后才能报告 `connected` |
| 数据 | 输出设备协议通道、未改写的原始字节和接收时间 |
| 异常 | 报告可观察错误，释放不完整连接，再按配置重试当前传输 |
| 停止 | 尽力发送设备停止采集命令，并关闭连接、端口或 USB 句柄 |

### 6.3 蓝牙传输

| 编号 | 需求 | 优先级 |
|---|---|---|
| BLE-001 | 保持已确认的 Flowtime BLE profile：`FF31`、`FF32`、`FF51` 通知及 `FF21` 启停 | P0 |
| BLE-002 | 保留现有扫描、设备匹配、连接、订阅和断线重连行为 | P0 |
| BLE-003 | 本次抽象改造不得新增 `FF52` 或改变已定义包长和字节序 | P0 |
| BLE-004 | 蓝牙回归测试须覆盖真实模式、录播回退、断连与恢复 | P0 |

### 6.4 串口传输

| 编号 | 需求 | 优先级 |
|---|---|---|
| SER-001 | 支持配置明确的 Linux 串口设备路径，不通过不受控通配符随机选择设备 | P0 |
| SER-002 | 支持配置协议确认后的波特率、数据位、校验位、停止位和流控 | P0 |
| SER-003 | 串口打开失败、权限不足、设备消失、读超时和帧校验失败须转换为可观察状态 | P0 |
| SER-004 | 设备拔出后关闭失效句柄，并按配置间隔仅重试同一已配置设备 | P0 |
| SER-005 | 连续字节流必须使用已确认的分帧和校验规则处理半包、粘包和损坏帧 | P0 |
| SER-006 | 必须限制接收缓冲区和最大帧长，非法流量不得导致内存无限增长或主进程退出 | P0 |
| SER-007 | 如设备协议定义启停或握手命令，必须在算法会话就绪后启动采集，并在停止时尽力关闭采集 | P1 |

### 6.5 原生 USB 传输

| 编号 | 需求 | 优先级 |
|---|---|---|
| USB-001 | 仅在确认设备使用原生 USB 接口而非 TTY 后启用本策略 | P0 |
| USB-002 | 支持用已确认的 VID、PID、序列号或接口特征唯一匹配目标设备 | P0 |
| USB-003 | 支持设备协议要求的接口声明、端点选择、读写方式和超时 | P0 |
| USB-004 | 设备拔出、重新枚举、权限不足、接口占用、短读和传输错误须转换为可观察状态 | P0 |
| USB-005 | 重连时必须重新发现并声明设备接口，不复用失效句柄 | P0 |
| USB-006 | 仅释放本进程声明的接口；不得影响其他 USB 设备或未选择的接口 | P0 |
| USB-007 | Linux udev 规则或服务权限必须最小化到目标设备，不允许为方便而开放所有 USB 设备 | P0 |

### 6.6 数据处理、算法与录制

| 编号 | 需求 | 优先级 |
|---|---|---|
| CORE-001 | 网关业务层不得直接依赖 Bleak、串口库或 USB 库的回调细节 | P0 |
| CORE-002 | 三种适配器统一输出设备协议通道、原始字节、接收时间和来源类型 | P0 |
| CORE-003 | 数据解析器按已确认的设备协议工作，不按传输库返回长度猜测帧格式 | P0 |
| CORE-004 | 原始记录和算法结果继续按会话分别持久化并可关联采集窗口 | P0 |
| CORE-005 | 录播直接读取已保存的原始数据和算法结果，不重新计算算法 | P0 |
| CORE-006 | 传输来源可写入内部日志或录制元数据；如需改变已发布采集包格式，必须另行评审和发布文档 | P1 |
| CORE-007 | 新设备连接就绪时必须创建干净的算法会话，未完成初始化的数据不得进入算法 | P0 |
| CORE-008 | 单个非法包或算法异常不得导致设备适配器、北向服务或主进程退出 | P0 |

### 6.7 北向兼容性

本 PRD 不授权修改已发布或预发布的 B 端协议。实现必须满足：

- 根对象继续使用 `{protocolVersion, code, data, message}`；
- 报文 `protocolVersion` 保持版本台账中的当前值；
- `getStatus`、`getLatest`、`subscribe` 和 `unsubscribe` 的行为保持不变；
- 实时与录播继续分别使用 `mode="live"` 和 `mode="replay"`；
- 不向 B 端增加 `transport`、`deviceId` 或 `gatewayId`；
- B 端不需要知道或适配设备侧传输方式；
- 如果后续确需向 B 端暴露传输类型或新增错误字段，必须按北向协议发布门禁另行立项。

## 7. 状态与异常处理

### 7.1 期望状态流

```text
服务启动
  → 校验唯一数据源配置
  → 创建所选适配器
  → connecting
  → 设备连接及协议初始化
  → 算法会话初始化
  → connected / live
  → 断开或错误
  → disconnected
  → 释放资源
  → 等待配置的重试间隔
  → 仅重试当前所选适配器
```

### 7.2 错误分类

| 类别 | 示例 | 期望行为 |
|---|---|---|
| 配置错误 | 未选择传输、未知类型、缺少所选传输必需参数 | 拒绝以错误配置启动，指出具体字段 |
| 设备不存在 | BLE 未发现、串口路径不存在、USB 未枚举 | 北向服务保持可用，记录状态并重试当前传输 |
| 权限错误 | TTY 或 USB 接口无权限 | 记录设备路径/VID/PID 等非敏感定位信息和修复提示，不无限高频重试 |
| 连接中断 | BLE 断连、串口拔出、USB reset/disconnect | 关闭失效资源，状态变为离线，按配置重连 |
| 非法数据 | 帧长错误、校验失败、未知通道 | 丢弃或隔离当前非法帧，计数并限频记录，不退出主进程 |
| 数据积压 | 串口/USB 接收速度超过处理能力 | 使用有界缓冲和可观察丢弃策略；具体上限待性能 POC 确认 |
| 算法异常 | 初始化或计算失败 | 标记结果无效并记录原因，保留原始数据，主服务继续运行 |

## 8. 非功能需求

### 8.1 可靠性

- 任一设备侧异常不得中断 WebSocket 监听、录播或其他网关管理能力。
- 设备重连、服务重启和系统重启后，只恢复配置指定的传输。
- 适配器必须幂等停止，避免重复关闭导致主进程异常。
- 所有读取缓冲区、待处理队列和重试频率必须有上限并可配置。

### 8.2 性能

- 新增传输抽象不得改变现有每 600 ms 的北向连续数据分组语义。
- 串口和 USB 的接收吞吐必须覆盖设备协议确认的峰值数据率，并保留安全余量。
- 端到端延迟、CPU、内存和丢包率须在目标 N100/N150 + Ubuntu LTS 上实测，不在 PRD 中预设未经验证的数值。

### 8.3 安全与权限

- 服务仅获得所选设备所需的最小访问权限。
- 不允许使用全局可写的 TTY/USB 权限作为交付方案。
- 日志不得记录完整敏感原始数据、受试者隐私数据或凭据。
- USB/串口设备标识不得被误当作北向鉴权凭据。

### 8.4 可观测性

日志和内部指标至少包括：

- 网关应用版本和当前选择的传输类型；
- 连接状态变化及时间；
- 非敏感设备匹配信息；
- 最近收到有效数据的时间范围；
- 重连次数、非法帧计数、缓冲溢出计数和错误原因；
- 算法会话初始化及异常状态。

## 9. 验收标准

### 9.1 通用验收

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AC-001 | 单选校验 | 三种合法值分别可启动；缺失或未知值被拒绝；进程不会同时创建两个适配器 |
| AC-002 | 资源隔离 | 选择一种传输时，其他两种传输没有扫描、打开、声明或权限访问行为 |
| AC-003 | 实时链路 | 所选设备数据可经解析、算法、录制和北向订阅完整流转 |
| AC-004 | 原始数据一致性 | 保存的原始字节与设备侧抓取数据逐字节一致 |
| AC-005 | 设备断线 | 断线后北向服务继续运行，状态可观察，录播回退符合现有规则 |
| AC-006 | 设备恢复 | 仅重连所选传输；算法建立新会话；实时恢复后停止录播 |
| AC-007 | 服务端不可达与恢复 | B 端断开不影响设备采集主循环；重连后先 `getStatus` 并重新订阅 |
| AC-008 | 录播兼容 | 三种传输采集产生的数据均可从保存结果录播，且录播不重新计算算法 |
| AC-009 | 长时间运行 | 覆盖双方确认的连续运行时长，无句柄泄漏、无界内存增长或主进程退出 |
| AC-010 | 蓝牙回归 | 现有 Flowtime BLE 扫描、连接、FF31/FF32/FF51、FF21 启停和重连测试通过 |

### 9.2 串口专项验收

- 覆盖正常分帧、半包、粘包、损坏帧、读超时和连续高吞吐。
- 覆盖设备启动前不存在、运行中拔出、重新插入后设备路径保持或变化的场景。
- 覆盖权限不足、端口被占用和串口参数错误。
- 使用真实录制数据核对字节序、帧边界、时间戳和算法输入分组。

### 9.3 原生 USB 专项验收

- 覆盖同 VID/PID 多设备时的唯一匹配策略。
- 覆盖接口声明失败、端点错误、短读、超时、USB reset、拔出和重新枚举。
- 验证 udev 权限仅作用于目标设备。
- 使用 USB 抓取与网关保存数据核对原始字节和包边界。

## 10. 实施阶段与交付门禁

### 阶段 A：协议与硬件确认

- 取得串口和原生 USB 的正式设备通信规范。
- 确认目标硬件、Linux 驱动、VID/PID、串口参数、接口和端点。
- 确认设备启停命令、分帧、校验、错误恢复和最大数据率。

门禁：协议或硬件资料不完整时，只能搭建模拟适配器，不得声明真实设备 POC 已完成。

### 阶段 B：适配器抽象与蓝牙回归

- 抽离统一设备适配器接口。
- 将现有 BLE 实现接入统一接口。
- 完成配置单选校验和 BLE 全量回归。

门禁：BLE 行为、原始数据和北向结果必须与改造前兼容。

### 阶段 C：串口 POC

- 使用目标设备完成连接、分帧、启停、断线重连和真实数据比对。
- 验证原始记录、算法输入和录播兼容性。

### 阶段 D：原生 USB POC

- 使用目标设备和目标 Linux 主机验证驱动、权限、接口、端点和热插拔。
- 验证原始记录、算法输入和录播兼容性。

### 阶段 E：部署与现场验收

- 更新示例配置、安装脚本、systemd 权限和运维文档。
- 在目标 Ubuntu x86_64 主机分别执行蓝牙、串口和 USB 验收矩阵。
- 明确记录“源码/文档支持”“POC 已验证”和“现场验收通过”的不同结论。

## 11. 风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 串口/USB 协议与 BLE 数据格式不同 | 复用旧解析器可能产生静默错误 | 以正式设备协议和逐字节真实数据比对为准 |
| USB CDC 被误配置为原生 USB | 重复实现或无法打开设备 | 按 Linux 是否呈现 `/dev/tty*` 明确分类 |
| 多设备具有相同标识 | 网关连接错误头环 | 增加经确认的唯一匹配字段，禁止随机选择 |
| Linux 设备节点重枚举 | 固定路径失效 | 使用稳定 udev 标识或经确认的唯一设备属性 |
| 权限配置过宽 | 增加本机设备访问风险 | 使用最小 udev 规则和专用服务用户 |
| 热插拔导致句柄或任务泄漏 | 长时间运行不稳定 | 统一生命周期、幂等清理和压力测试 |
| 适配器抽象泄漏传输细节 | 业务层出现分支扩散 | 固定统一事件契约并进行模拟适配器测试 |
| 未经确认直接重采样或重编码 | 算法结果不可信 | 原始字节持久化，真实数据回归前禁止转换 |

## 12. 待确认事项

以下问题必须在串口或 USB 实现前由设备方、算法方或项目双方确认：

1. 设备是否同时提供 BLE、串口和原生 USB，还是不同硬件型号分别提供？
2. 串口设备在目标 Ubuntu 上的稳定识别方式是什么？
3. 串口的波特率、数据位、校验位、停止位和流控参数是什么？
4. 串口字节流的帧头、长度、转义、校验、超时和最大帧长是什么？
5. 原生 USB 的 VID、PID、设备版本、序列号、配置、接口和端点是什么？
6. 原生 USB 使用 HID、Bulk、Interrupt 还是厂商驱动？是否需要内核模块或用户态库？
7. 串口和 USB 的开始采集、停止采集、状态查询和确认响应是什么？
8. 串口和 USB 是否承载与 BLE `FF31`、`FF32`、`FF51` 等价的数据？若不等价，逻辑通道如何映射？
9. 三种传输的采样率、包节奏、序号、丢包检测和算法输入分组是否一致？
10. 目标设备在断线重连后是否需要重新握手、清空缓冲或重置序号？
11. 同一主机连接多个候选设备时，如何唯一选择目标设备？
12. 交付现场是否允许安装 udev 规则、专用驱动或额外用户态依赖？
