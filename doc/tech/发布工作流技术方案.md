# NeuroBridge 发布工作流技术方案

- **依据**：[发布工作流 PRD](../product/发布工作流%20PRD.md)、`release/release_matrix.toml`
- **状态**：实施方案；本地构建与 CI 证据、真机验收分别记录

## 1. 版本与触发

`neurobridge/version_registry.toml` 是版本唯一来源：`[application].version` 表示总交付批次，`[application.platform_versions]` 分别决定 Windows、麒麟的安装器、运行时和诊断版本；缺少平台字段的旧台账回退到总版本。仅某个平台变化时只提升该平台版本，总批次仍按门禁提升，其他平台保持原版本。PR 对 `master` 的业务、部署、依赖、打包或**随包交付的对外文档**（`doc/tech/对外/`）变更必须按影响级别提升版本，并在台账 `application_release_changes` 写明旧版、新版、级别、兼容性边界和依据。只有交付范围之外的文档/测试变更可不升版。合入后的 `push master` 运行同一门禁；版本未递增则记录跳过，不占用已有 tag。报文版本和对外协议发布独立。

**出包判定只看版本号**：是否产出发布包由 `[application].version` 相对基线是否递增决定（`tools/release_pipeline.py` 的 `gate`），与改了哪些文件无关；变更文件列表只用于判定「必须升版本」。改了交付范围（`PRODUCT_PATHS`）内的文件却没升版本时门禁**失败**，而不是安静跳过——所以「改了某个目录就等效于该变化」不成立。基线：PR 门禁用 PR 目标分支的提交；打包运行通过 GitHub API 查找带已上传总 ZIP、已公开且非预发布的应用 Release，选择版本最高者，再由关联 tag 解引用到源码并核对台账版本。孤立 tag、draft、无资产记录都不代表成功发布。首次尚无正式应用 Release 时，沿当前分支第一父链的台账历史寻找低于当前版本的最近记录；不退回单个 `HEAD^`，避免版本提升后追加提交导致误判。API 或基线解析失败直接报错，不伪装成无需发布。

打包与 PR 解耦：PR 只运行门禁与测试，不产出任何包；打包由独立的 `Release` workflow 承担，入口只有两个——`Test` workflow 在 `master` 上成功完成后自动触发，或手动对所选分支的最新提交触发。只有 `release-plan` 判定 `should_release` 为真时各打包作业才运行，否则运行页写明本次无需发布。

## 2. 构建输入与矩阵

矩阵来自 `release/release_matrix.toml`：Windows 10/11 × x86_64 × EXE/MSI 共 4 个目标；麒麟只有一个目标 `kylin-v10-all-deb`，`package_kind = "bootstrap"`。合计 5 个目标。麒麟不再按服务器版/桌面版、五种架构和 DEB/RPM 预先构建。每个目标有稳定 ID、独立构建目录和日志。Windows 7 与 x86 32 位不在发布矩阵内，不构建，不产生空归档。

产物构建不得从现有 `build-product-candidate.py` 的源码 ZIP/TAR 伪装安装包。Windows 的 MSI/EXE 由 WiX MSI/Burn 分别生成，输入来自批准的 `native_input_run_id`。麒麟引导包由 Release 自己在 ubuntu runner 上调用 `tools/build-kylin-bootstrap-package.py` 生成，不下载 `neurobridge-input-<targetId>`，也不需要麒麟 runner 上预先编好的运行时。包内携带 Python 3.11、wheel、CMake 和 Eigen 3.3.7；运行时在安装该包的银河麒麟 V10 实际目标架构机器上构建。`tools/write-kylin-bootstrap-verification.py` 写出符合 [`release-target-verification.schema.json`](../../schemas/release-target-verification.schema.json) 的 `verification.json`，其中 `runtimeSha256` 与 `inputSha256` 都来自实际 DEB 载荷中的资源选择、锁定清单及实际所选文件摘要；无资源时仍摘要锁定清单和选择，不伪装成预编译运行时。打包按分支最新提交执行：手动触发时使用所选分支的 head SHA，`master` 自动触发时使用该 `master` commit 的 SHA；Windows 输入运行的分支、SHA 和成功状态必须对应。Windows 未提供经校验的输入、缺少打包器或目标机验证时，逐目标记录 `blocked`/`failed`，不纳入平台 ZIP。

### 麒麟离线资源打包参数

三个准备/打包 Workflow 的 `offline_resources` 支持 `all`（默认）、`none` 或逗号分隔的 `python,cmake,eigen,pyserial,websockets`。命令行准备和打包工具使用 `--offline-resources` 同步选择，Python/CMake 选择同时包含各自二进制与源码，未选资源不会进入载荷。缓存键由锁定文件摘要和规范化资源清单组成；`none` 不要求缓存。实际 DEB 必须通过 `tools/check-kylin-bootstrap-payload.py --package <DEB> --offline-resources <选择>`，校验必需源码、`offline-resources.json`、锁定清单及所选文件 SHA-256，并拒绝漏项和混入未选输入。Release 只恢复所选受控缓存，独立引导 Workflow 可以显式准备缺失项。

### 麒麟引导包安装生命周期

资源选择入口为 `install-bootstrap.sh --package <DEB> [资源名 [HTTPS URL或文件] ...]`，随独立引导 Artifact 和总包的麒麟版本 ZIP 交付，亦保存于引导载荷。该入口先在私有临时目录解包、选择目标 CPU、校验本次五个资源，再通过 `NEUROBRIDGE_RESOURCE_DIR` 将已准备文件传入同步 `dpkg --install` 的首次 postinst。`bootstrap-build.sh` 按新包锁定清单再次校验并复制到一次性源码树，成功或失败后均清理临时资源，普通后续配置仍使用包内默认值。直接重建支持同样资源参数，资源清单查询不构建。URL 或本机文件选择失败不回退；包内缺项且未提供来源时，在下载/安装前列出全部必需缺项、补充参数格式并记录 `resource_missing`，非零退出；整个过程不改包内文件，系统依赖仍须独立准备。详细语法与资源表见[内部手册](麒麟V10网关运行与串口联调内部文档.md#引导安装资源来源选择)。

以下行为属于 PR #15 的源码修复与模拟回归范围，尚未在银河麒麟 V10 x86_64 上完成安装包验收。

- **首次安装与串口权限：**允许未接耳机时运行 `dpkg -i`，日志明确标记 `waiting_for_device`，服务等待接入。安装器检查实际 `/dev/ttyACM*`、`/dev/ttyUSB*` 字符设备，为服务账户追加节点的非 root 所属组；不授权 root 组。另安装 `70-neurobridge-usb-serial.rules`，只匹配 USB 祖先下的 ttyUSB/ttyACM 节点，为其设置 `neurobridge` 组和 `0660`，后续插入无需重装。服务账户加入该组；规则重新加载后只触发这两类串口的 change 事件，不触发其他设备。现有同名非本包规则或软链接拒绝替换，权限设置失败仍中止。该规则涵盖这两类 USB 串口，不推测耳机 VID/PID；现场须确认与其他串口工具的权限策略相容。安装成功仍不代表合法帧采集通过。
- **升级与同版本重装：**每次 `configure` 都构建并部署当前包内源码，不再用已有 Python 文件判断是否跳过更新。构建与暂存期间原服务继续运行；替换程序前先正常停止并确认退出，使原录制及 E0 收尾使用旧代码。已有服务保留原来的运行、自启状态；首次安装启用并启动服务。配置、日志和录制数据保留。
- **安装成功与服务状态：**`INSTALL_END exit_code=0` 仅表示安装事务完成。旧服务为 stopped 时，升级会保留停止状态，包括已 enabled 但未运行的服务；安装阶段名 `activate-service` 不能作为服务启动证据。日志明确记录 enable/keep_disabled、start/skip_start 及原因；跳过启动时输出 `installed_not_started`、`startup_verified=false` 和手动启动、状态、journal 命令。只有实际执行 start 且 is-active 成功时才输出 started；该即时检查仍不能替代持续运行、真实串口与重启验收。
- **回滚：**分别保存原服务单元、运行状态、自启状态、程序目录与本包旧权限规则。安装失败恢复原文件及状态，重新加载恢复的规则；首次失败移除本次新增程序、配置、服务单元与权限规则。回滚自身失败时输出错误与备份目录并保留备份，不能表述为已恢复。
- **Python 选择：**运行时归档调用 Python 准备脚本时指定 `NEUROBRIDGE_PORTABLE_PYTHON=1`，即使系统已有 Python 3.11 或更新版本，也使用随包校验的解释器和 cp311 wheel。普通源码部署仍可以选择符合要求的系统解释器。
- **卸载：**DEB 的 `prerm remove` 停止并确认服务退出，再取消自启；`postrm remove/purge` 只删除匹配本安装路径的服务单元并执行 `daemon-reload`，另清理含本包标记的串口规则并重新加载。停止失败时拒绝卸载；升级维护钩子和其他源码部署的同名服务保持不变。`/opt/neurobridge`、现场配置、日志与录制数据保留。构建器兼容 RPM 的卸载钩子采用同样规则，RPM 不属于当前正式发布矩阵。

目标机验收必须覆盖：无耳机首次安装及后续接入、已接耳机的首次安装、实际服务组/节点权限及合法帧；授权失败后的重试与旧规则恢复；已有 Python 3.11 时的离线构建；运行中与已停止服务升级；启动失败回滚；卸载后整机重启不再启动网关；以及串口离线且存在历史录制时不启动录播、拔插重连、服务重启与浏览器断开恢复。模拟工具不能代替这些结果。

历史部署指南 v1.0 与 v1.1 已锁定，不回写。v1.1 要求安装前连接耳机；本次修复允许无设备安装并通过热插入规则授权，只更新实现、内部说明及未发布变更记录，后续获文档发布授权再新增下一版本。

总包根目录由 `build-release-bundle.py` 根据实际交付清单生成 `bundle-directory-guide.pdf`，中文标题为“NeuroBridge 交付包目录说明”，面向部署人员列出各层 ZIP、解压顺序、安装包、指南、日志工具和核验资料位置；不再交付根目录 `PRD.md`。复用 `render-protocol-pdf.sh` 的 Pandoc/Chrome 与中文字体工具链，PDF 纳入 `bundle-manifest.json.documents`，缺失、渲染失败或不是 PDF 时阻止交付；汇总 CI 验证中文字体并渲染全部页面作为独立预览 Artifact，PDF 与预览均不提交 Git。Windows 保持 10/11 x64；麒麟引导按 PRD 七个架构 Profile 选依赖，新架构仍待真机验收。麒麟运行时模板版本及文件名由版本台账同步，版本门禁检查这两个字段，防止引导包与本地运行时归档版本不一致。

## 3. 发布状态机

打包与 PR 解耦：PR 只跑门禁与测试，不产出任何包。打包入口只有两个——`Test` workflow 在 `master` 上成功完成后自动触发，或手动对所选分支的最新提交触发；手动触发只到候选包为止，不进入 tag 与 Release 阶段。

```mermaid
flowchart LR
  A["PR 版本门禁与测试（不打包）"] --> B[master 版本递增]
  B --> C[Test workflow 通过后触发打包]
  M["手动触发：任意分支最新提交"] --> C
  C --> D[尝试 5 个目标并记录日志]
  D --> E{两平台各至少一个合格包?}
  E -->|否| F[失败并保留目标日志]
  E -->|是| G[两个平台 ZIP 与唯一总 ZIP]
  G --> H[包外 manifest 与 SHA-256 复验]
  H --> U[上传 Actions Artifact]
  U --> V[按 Artifact ID 回下载并核对上传前 ZIP SHA-256 与内容]
  V --> I[创建或核对同 commit 注释 tag]
  I --> J[创建或续用 draft Release]
  J --> K[上传并下载复验资产]
  K --> L[公开 Release 并写回执]
```

`release-manifest.json` 是发布前不可变候选清单；它记录全部目标的结果，只为合格包填写文件名和哈希。两个平台 ZIP 仅含合格包与验证日志；麒麟平台 ZIP 只含一个引导包。总 ZIP 含两个平台 ZIP、内部构建清单和 5 个目标的 `release-logs.jsonl`。原生包汇总 ZIP 的时间戳与文件名日期取经验证输入的构建时间；每次运行的实际检查时间留在 Actions 目标结果中。总 ZIP 还包含重新生成的文档 PDF，PDF 的生成时间元数据可能使同提交重跑产生不同字节，因此发布续跑复用此前已上传并校验的原总 ZIP。总 ZIP 自身的哈希在包外清单；公开状态由独立 `release-receipt.json` 记录。后续真机日志作为带版本、目标、时间的新增附件，不覆盖既有资产。所有缺口写入 Release 说明，不将源码构建、结构检查或模拟测试表述为真机通过。

## 4. 幂等与权限

PR 只用 `contents: read`；发布 job 才用 `contents: write`，同一版本串行。聚合作业计算上传前总 ZIP 的 SHA-256，通过 job output 传给发布作业，并上传 Artifact；上传成功后发布作业按返回的 Artifact ID 回下载，必须与上传前摘要相同且包、清单、日志验证通过才允许创建 tag。摘要缺失、格式错误或下载字节不符均在 tag 写入前失败。已有 tag 必须解引用至同一 commit，否则失败，永不移动或删除。已存在 draft 时只补缺失资产，同名资产需下载比对 SHA-256；已公开且完全相同则视为重跑成功，不同则要求新版本。网络或上传错误保留 draft，禁止将仅有 tag/draft 记为 `published`；后续门禁仍使用上一成功公开的 Release，因此允许同提交重试完成发布。打包和 Artifact 上传本身不需要 tag；GitHub Release 需要关联 tag，它用于绑定版本与源码，不单独承担成功状态。

同一源码提交的整个 Release 工作流串行执行，避免两次运行在资产上传前各自生成不同的总 ZIP。首次创建 draft 时，Release 说明同时保存总 ZIP 的源码提交、版本、文件名和 SHA-256。自动发布续跑在聚合后、Actions Artifact 上传前，以只读方式下载已存在的唯一总 ZIP，校验保存的摘要、内层内容、源码/版本、安装包摘要及全部目标结果一致后复用原字节。该原包重新上传 Actions Artifact 并回下载校验后，才继续既有 tag/draft 公开流程。尚无资产的 draft 可以登记本轮已验证摘要后重试首次上传；已有资产但缺少摘要记录、资产损坏、安装包或目标结果变化时拒绝复用，不覆盖、不删除原资产。手动打包仍只产出 Artifact，当前复审 #1 的正式发布入口问题另行处理。

## 5. 日志与验收

每个目标写 UTF-8 结构化结果，至少包含 `targetId`、状态、阶段、时间、runner、工具链、输入摘要、包文件/摘要、自动验证与未验证原因；文本日志保留命令的退出码和错误摘要。不得输出令牌、密码、私钥、完整人体原始数据。发布前验证 5 个目标各有结果、包字节与清单一致、两个平台各至少一个合格包、ZIP 可解压且内层摘要一致。Windows 10/11 与麒麟引导包的真机安装、回滚、串口及离线无 replay 证据仍分别验收。

## 6. 当前仓库可执行边界

仓库已有 x64 Windows 算法构建、源码候选包脚本和麒麟引导包构建脚本，但没有 Windows x86/7 兼容运行时和 WiX 离线工具链。麒麟不再要求五架构 sysroot 或预先编好的运行时：引导包在 ubuntu runner 上打包，运行时留到安装它的银河麒麟 V10 实际目标架构机器上构建。本次交付范围是版本门禁、5 个目标的规划、目标证据检查、归档与发布状态机。Windows 正式安装包仍依赖经批准的目标构建输入运行；麒麟引导包不依赖该输入。打包运行在 Windows 输入缺失时仍汇总该平台的 `blocked`/`failed` 结果并上传诊断总 ZIP，不把它当作合格安装包。`master` 自动触发时，两平台各至少一个合格包才允许创建 tag 或 GitHub Release；未达门槛时发布失败并保留诊断日志。手动触发的非正式构建不创建 tag 或 Release。补齐 Windows 输入与目标机验证前，不能宣称 5 个安装包已交付或让 `master` 自动发布源码候选包。

### 安装失败取证与交付文件名

麒麟引导包每次配置均执行构建，记录 `/var/log/neurobridge-bootstrap/install-*.log` 中的版本、源码提交、阶段和退出码，清理临时构建目录前保留其子日志；日志导出脚本不依赖网关运行时或网页。DEB 增加 `make` 系统依赖，离线部署须预先准备全部系统依赖。Windows 每个可用系统 ZIP 随附 `install-with-logs.ps1`，支持 MSI/Burn 日志和离线失败日志导出。原生包收集拒绝矩阵外输入，家族和架构没有安装包时不创建空 ZIP。

## 诊断身份、环境与架构边界

支持表及扩展准入见[PRD §2.7–2.9](../product/发布工作流%20PRD.md#27-系统与-cpu-架构支持表)。引导 DEB 标识为 all，按系统/CPU/ABI 选择锁定输入；x86_64 用既有预编译依赖，其余六个 Profile 用本机源码构建。详细条件与状态见 PRD §2.7–2.8，all 不代表跨架构运行时通用。

`windows/diagnostic-context.ps1` 与 `packaging/kylin/diagnostic-context.sh` 供安装/运行导出共用。原生载荷与麒麟安装生成的运行时保留 `build-info.txt`（应用版本、源码提交）；Windows 版本 ZIP 另附同源 `build-info.txt` 与上下文模块。导出从部署目录读软件身份，从包目录读本次安装包身份，不混用；无台账/构建信息或 Python 不可用时为 `unknown`。版本字段为磁盘文件身份，配合独立服务状态使用。

上下文包含诊断类型/UTC 时间、版本与提交、OS 名称/版本/构建、CPU 架构/系统位数、Python 版本/位数；Windows 另记 PowerShell 和导出进程位数，麒麟另记内核/glibc/Bash。麒麟运行时载荷包含 `/opt/neurobridge/kylin/export-logs.sh` 及模块；安装诊断在尚未部署运行时时也可生成。网页日志下载与 Windows 摘要使用 Python 共用上下文，明确为已加载模块及导出进程环境。麒麟综合采集器分别标识采集器源码和已部署目录，不将采集器版本当作服务版本。全部上下文只读取必要字段，不导出配置正文或全量环境变量。

用户提供的旧总包 PDF 文件名已有 UTF-8 ZIP 标记，旧解压器仍可能误解码。用户交付 ZIP 使用 ASCII 文档副本名，元数据保留其与台账原名的映射；PDF 字节不因此改写。旧已发布 PDF 与 Markdown 不回写，Windows/麒麟指南各新增独立 v1.1 并保存历史版本元数据。


## 多架构依赖供应与日志

`config/kylin-bootstrap-inputs.toml` 是架构映射和输入摘要的唯一清单；`tools/prepare-kylin-bootstrap-inputs.py` 默认仅验证，可由开发人员显式 `--download` 准备 `.runtime/kylin-bootstrap-inputs`。Actions 的 `Prepare Kylin dependencies` 仅由人工触发，下载锁定 URL 并按 SHA-256 验证后保存依赖缓存，不构建安装包。Release 只恢复相同清单摘要的缓存并复验，缺失或污染立即失败。本轮不触发这些任务。

打包器验证全部 Profile 输入后复制到引导载荷；仅保留串口所需的通用 wheel，生成匹配的校验清单。维护脚本不联网获取依赖。系统开发库须在 dpkg 配置包前由管理员/软件中心准备，避免维护脚本持有包锁时再调用 apt。Python 源码构建在模块检查通过后才继续，CMake 与算法输出、config.log/CMake日志在临时树删除前转存。运行时归档 manifest 写入真实架构，安装器先校验 OS/CPU，再验证摘要和解释器 ABI/模块，随后才修改账号或服务。

日志新增 UTC phase 事件：detect_host、selected_profile、verify_input、toolchain、build_python/complete、build_cmake/complete、algorithm_build、verify_runtime_identity 和各 setup_end 的耗时/退出码；失败带稳定原因（unsupported_os/cpu/abi、abi_bitness_mismatch、compiler_target_mismatch、missing_or_unsafe_input、input_hash_mismatch）。安装与运行导出继续包含包/部署版本、源码提交和 OS/CPU/Python 环境，不包含配置正文或人体数据。
