# NeuroBridge 发布工作流技术方案

- **依据**：[发布工作流 PRD](../product/发布工作流%20PRD.md)、`release/release_matrix.toml`
- **状态**：源码实现与自动化验证；正式运行和现场验收分别记录

## 1. 三套独立版本与迁移

版本台账是唯一来源。`platform_releases.windows.version` 控制 Windows MSI、EXE、候选包及部署诊断身份；`platform_releases.kylin.version` 控制麒麟引导包、运行时归档与部署诊断身份。`application.version` 仅控制源码分发元数据和总交付包，不作为两个平台的安装包版本；协议与文档版本继续独立。

迁移前平台字段被忽略，实际安装包使用统一应用版本。因此首次独立版本必须从实际安装包版本迁移，不从旧平台字段退回。台账 `release_version_policy.independent_platforms=true` 声明新策略；旧台账没有该标志时，历史基线与诊断读取 `application.version`。本次迁移依据和版本增量写入 `platform_release_changes`，总包变更写入 `application_release_changes`。

版本采用三段数字；修复递增 patch，兼容功能递增 minor 并清零 patch，不兼容变更递增 major 并清零后两位。PR 门禁相对目标分支确认各平台变化及一条对应的升级依据。`linux/`、麒麟打包与锁定输入只要求麒麟升版；`windows/` 与 Windows 适配只要求 Windows 升版；共用业务、依赖、网页和发布工具要求两个受影响平台升版。纯内部文档、测试和生成的变更记录不强制升版。单个平台升版不要求提升总包版本；同一总包版本可通过不同 commit 标识新的组合交付。

PR 仅验证，不构建或发布。自动发布在默认分支 `master` 的 Test 成功后运行；手动分支构建只生成候选 Artifact，不写标签或 Release。

## 2. 构建矩阵与发布输入

构建矩阵为 `windows-10-11-x86_64-msi`、`windows-10-11-x86_64-exe` 和 `kylin-v10-all-deb`，共三个包目标。Windows 的操作系统支持列表仍为 10/11；这是一个共享安装包目标，不是两套重复包。WiX MSI 与 Burn EXE 保留既有固定 UpgradeCode，使用 Windows 独立版本，升级识别不会因合并系统目标而变成另一个产品。

Windows 原生输入由 `native-inputs.yml` 在指定源码提交上构建。Release 可显式指定 `native_input_run_id`；未指定时查找该提交、分支上成功的原生输入运行，再复核提交、分支、格式、平台版本、SHA-256、工具链和输入来源。不存在合格输入时 Windows 阻断；不能从其他提交找替代包。麒麟由 Release 在 Ubuntu 协调机构建引导 DEB，读取已校验的离线缓存；运行时在实际麒麟安装机器上构建。协调机生成包不代表目标机通过。

各平台只在自身版本递增时构建。`tools/platform_release.py` 从候选结果生成 `<platform>-v<platformVersion>.zip`，包含该平台全部结果、安装包、验证日志和 `platform-release-manifest.json`；Windows 两种格式和麒麟一个 DEB 必须完整。该 ZIP 是独立发布及后续复用的不可变输入，不是最终用户交付总包。

### 麒麟引导包安装生命周期

以下行为属于 PR #15 的源码修复与模拟回归范围，尚未在银河麒麟 V10 x86_64 上完成安装包验收。

- **首次安装与串口权限：**允许未接耳机时运行 `dpkg -i`，日志明确标记 `waiting_for_device`，服务等待接入。安装器检查实际 `/dev/ttyACM*`、`/dev/ttyUSB*` 字符设备，为服务账户追加节点的非 root 所属组；不授权 root 组。另安装 `70-neurobridge-usb-serial.rules`，只匹配 USB 祖先下的 ttyUSB/ttyACM 节点，为其设置 `neurobridge` 组和 `0660`，后续插入无需重装。服务账户加入该组；规则重新加载后只触发这两类串口的 change 事件，不触发其他设备。现有同名非本包规则或软链接拒绝替换，权限设置失败仍中止。该规则涵盖这两类 USB 串口，不推测耳机 VID/PID；现场须确认与其他串口工具的权限策略相容。安装成功仍不代表合法帧采集通过。
- **升级与同版本重装：**每次 `configure` 都构建并部署当前包内源码，不再用已有 Python 文件判断是否跳过更新。构建与暂存期间原服务继续运行；替换程序前先正常停止并确认退出，使原录制及 E0 收尾使用旧代码。已有服务保留原来的运行、自启状态；首次安装启用并启动服务。配置、日志和录制数据保留。
- **安装成功与服务状态：**`INSTALL_END exit_code=0` 仅表示安装事务完成。旧服务为 stopped 时，升级会保留停止状态，包括已 enabled 但未运行的服务；安装阶段名 `activate-service` 不能作为服务启动证据。日志明确记录 enable/keep_disabled、start/skip_start 及原因；跳过启动时输出 `installed_not_started`、`startup_verified=false` 和手动启动、状态、journal 命令。只有实际执行 start 且 is-active 成功时才输出 started；该即时检查仍不能替代持续运行、真实串口与重启验收。
- **回滚：**分别保存原服务单元、运行状态、自启状态、程序目录与本包旧权限规则。安装失败恢复原文件及状态，重新加载恢复的规则；首次失败移除本次新增程序、配置、服务单元与权限规则。回滚自身失败时输出错误与备份目录并保留备份，不能表述为已恢复。
- **Python 选择：**运行时归档调用 Python 准备脚本时指定 `NEUROBRIDGE_PORTABLE_PYTHON=1`，即使系统已有 Python 3.11 或更新版本，也使用随包校验的解释器和 cp311 wheel。普通源码部署仍可以选择符合要求的系统解释器。
- **卸载：**DEB 的 `prerm remove` 停止并确认服务退出，再取消自启；`postrm remove/purge` 只删除匹配本安装路径的服务单元并执行 `daemon-reload`，另清理含本包标记的串口规则并重新加载。停止失败时拒绝卸载；升级维护钩子和其他源码部署的同名服务保持不变。`/opt/neurobridge`、现场配置、日志与录制数据保留。构建器兼容 RPM 的卸载钩子采用同样规则，RPM 不属于当前正式发布矩阵。

目标机验收必须覆盖：无耳机首次安装及后续接入、已接耳机的首次安装、实际服务组/节点权限及合法帧；授权失败后的重试与旧规则恢复；已有 Python 3.11 时的离线构建；运行中与已停止服务升级；启动失败回滚；卸载后整机重启不再启动网关；以及串口离线且存在历史录制时不启动录播、拔插重连、服务重启与浏览器断开恢复。模拟工具不能代替这些结果。

历史部署指南 v1.0 与 v1.1 已锁定，不回写。v1.1 要求安装前连接耳机；本次修复允许无设备安装并通过热插入规则授权，只更新实现、内部说明及未发布变更记录，后续获文档发布授权再新增下一版本。

## 3. 独立发布与完整交付

发布基线分别取带对应平台 ZIP、已公开且非预发布的 `windows-v<version>`、`kylin-v<version>` Release；孤立标签、draft 或无资产记录不算成功。首次迁移回查旧统一正式 Release 或版本历史。查找失败必须报错，不能伪装成无需发布。

每个平台单独生成 ZIP、记录上传前摘要、上传 Actions Artifact，再按 Artifact ID 回下载并完整校验。只有上传前后摘要与内容一致才创建指向该平台源码提交的注释标签，创建/续用 draft，上传并复验唯一平台 ZIP 后公开。两个平台的发布结果相互独立；Windows 阻断不撤销麒麟成功发布，最终总包此时阻断。

未更新的平台下载台账指定版本的公开 Release。下载须核对 Release 检查点、完整 ZIP SHA-256、所有成员路径与包格式、包摘要、结果与清单一致性、平台版本以及标签原始提交。恢复的结果保留原始 `sourceCommit`，增加 `reusedRelease` 的 tag、archiveSha256 和 sourceCommit；不能改写为本次总包的提交。找不到旧版、出现 draft、版本/摘要/标签不符或缺少任一格式时拒绝交付。

总包版本不变、平台版本组合也未改变且已有完整总包时跳过发布；平台已成功发布但总包失败的重试只复用平台资产，不重新构建。尚未完成公开的同提交平台 draft 重试恢复其经过检查点校验的原始 ZIP 和结果；不同提交占用同平台版本时要求升版，不移动标签或覆盖资产。

## 4. 总包结构与清单

总包文件名为 `neurobridge-v<application.version>-<commit前12位>.zip`，标签为 `delivery-v<application.version>-<commit前12位>`。完整 commit 写入清单，不使用日期或运行次数代替 commit。平台标签不绑定交付版本。

```text
neurobridge-v<deliveryVersion>-<commit12>.zip
  bundle-directory-guide.pdf
  windows/windows.zip
    windows-v<windowsVersion>.zip
      windows-v<windowsVersion>-x86_64.zip  # 一份 MSI、一份 EXE、校验清单
      docs/、安装日志工具、平台 build-info.txt
  kylin/kylin.zip
    kylin-v<kylinVersion>.zip
      kylin-v<kylinVersion>-all.zip         # 一个引导 DEB、校验清单
      docs/
  docs/external/
  metadata/
```

正式及手动交付总包都必须有两个平台，并包含完整安装包格式；不会生成单平台交付总包或空目录。独立平台 Artifact 可以先成功保存。总包 `bundle-manifest.json` 的 schemaVersion 为 3，记录 `applicationVersion`、`sourceCommit`、`platformVersions` 和带独立 version/sourceCommit 的 systemArchives。构建清单、包条目与发布回执同步记录平台版本与原始源码提交；日志记录复用依据。Windows 随包 build-info 使用其原始版本与提交，避免将本次麒麟修复的提交误标成 Windows 的来源。

根目录 PDF 根据实际清单生成，注明交付版本、两平台版本、提交与解压顺序；Windows 10/11 x64 共用同一分组。共用及平台文档仍按台账 delivery 策略路由；已发布文档标题、日期、摘要和正文不回写。CI 渲染目录 PDF 的全部页面供检查，PDF 与临时预览不提交 Git。

总包先上传 Actions Artifact、回下载验证摘要与各层内容后，再创建交付标签和 Release；PDF 重试恢复原始已校验总 ZIP，不覆盖同名资产。构建清单不自包含总 ZIP 摘要；摘要写在包外与独立回执。

## 5. 验证边界

回归覆盖：旧统一版本迁移；单平台递增与另一平台保持不变；共用代码双平台门禁；三目标矩阵；共享 Windows 安装包升级身份；独立发布；旧包复用的版本/提交/摘要/路径校验；缺平台和缺格式阻断；上传前后摘要门禁及同提交发布重试。正式平台发布与总交付分开记录，平台发布成功不等于完整交付或现场验收通过。

Windows 10 与 11 仍分别验收安装、升级、卸载、自启、USB 实时采集、串口拔插、服务/整机重启、浏览器恢复与离线禁止录播。麒麟各 CPU Profile 分别完成目标机编译、算法比对和同等场景验收；不同系统/架构结果不可替代。当前本地检查只提供源码与自动化证据，不触发远程发布或声明现场通过。
