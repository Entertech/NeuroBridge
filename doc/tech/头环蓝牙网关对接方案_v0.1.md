# 头环蓝牙网关对接方案

版本：v0.1

日期：2026-08-04
用途：头环数据接入第三方服务端的方案确认、开发与联调

## 1. 结论

第一期（演示与首次对接）建议采用 **N100/N150 x86 小主机 + Ubuntu LTS/Linux**，作为头环的蓝牙网关和协议转换盒。

推荐基础配置：8 GB 内存、256 GB SSD、千兆网口（双网口优先）、板载蓝牙 5.x；采购前需实测该蓝牙芯片能稳定支持目标头环的 BLE 连接。盒子不需要运行 Android；Android 或浏览器仅可作为对方的展示端，盒子只负责可靠地把数据送至对方服务端。

NanoPi R3S-LTS 可作为后续低成本、批量部署的候选，但需外接并验证 USB 蓝牙模块，且算法和依赖需适配 ARM Linux，因此不建议作为第一次联调的首选。

## 2. 总体架构

```text
头环
  │ BLE：连接、订阅数据通知
  ▼
网关小盒子（N100/N150 + Linux）
  ├─ 蓝牙连接管理：配对、重连、信号与电量状态
  ├─ 数据解析：校验、时间戳、缓存
  ├─ 算法：按实际部署位置运行算法 / 转发算法输出
  ├─ 协议适配：转换为双方约定的数据格式
  ├─ 可靠传输：断网缓存、恢复后的补传（如需要）
  └─ 运维：开机自启、日志、远程诊断
  │ Ethernet：TCP / WebSocket / HTTP(S) 等约定协议
  ▼
第三方 B 端主机（展示与数据保存；是否再上传服务端由对方处理）
```

### 两种运行模式

1. **实时模式**：头环持续通过 BLE 上报；第三方 B 端主机通过协议主动请求数据，盒子按约定返回当前值或在订阅期内返回连续数据。
2. **录播模式**：头环未连接时，盒子在 B 端首次 `getLatest` 或订阅后自动启动网关级录播流程，从部署配置的本地录播文件读取历史数据，并按与实时相同的北向协议发送；消息以 `mode="replay"` 标识数据来源。后续订阅加入当前回放进度；最后一个 B 端 WebSocket 连接断开时，网关立即停止回放并重置进度；只要仍有 B 端连接，文件读到末尾即从首条继续循环。头环重连时立即停止回放。录播回放节奏由网关部署配置确定。

实时采集时，盒子按会话分别保存原始脑波、原始心率和独立算法指标事件，并为每条记录保留接收/计算时间戳。算法指标不要求使用同一时间线；录播读取已保存的原始数据和算法事件，不重新运行算法。网页可将同一会话导出为 ZIP，文件与字段见《头环数据采集包格式说明》。

实现仓库按跨平台边界划分：`neurobridge/` 是平台无关的网关核心，`web/` 存放可由 macOS、Windows 或 Linux 托管的静态采集与 B 端联调页面；`mac/`、`linux/`、`windows/` 只存放各平台启动、部署或说明文件。首期 Ubuntu 部署入口为 `linux/install-ubuntu.sh`，macOS POC 入口为 `mac/start-poc.command`。

## 3. 关键前提与边界

- 如果场地的要求是“不得启用任何蓝牙”，则本方案的实时链路无法工作，因为头环到盒子的第一跳仍是 BLE。此时只能改为有线头环、在允许蓝牙的区域采集后录播，或由场地方书面确认仅限制其电脑/展示设备的蓝牙。
- 第三方 B 端主机不直接连接或适配头环；BLE 协议、设备重连和数据解析均由我方盒子处理。对方主机是否将数据再上传其服务端，不属于本次盒子对接边界。
- 需要确认算法实际运行位置。若算法运行在盒子内，优先使用 x86 Linux；若仅转发轻量数据，NanoPi 也足够。
- 盒子与第三方服务端之间建议使用有线以太网；现场应提供网络地址、端口策略和可达性测试条件。

## 4. 建议的硬件选择

| 维度 | N100/N150 小主机（推荐第一期） | NanoPi R3S-LTS |
|---|---|---|
| 架构 | x86-64 | ARM RK3566 |
| 蓝牙 | 通常可使用板载蓝牙；仍需以实机测试为准 | 官方板卡规格未列出板载蓝牙，需 USB 蓝牙适配器 |
| 算法部署 | x86 SDK、Python、Docker 等通常更容易直接使用 | 需要 ARM64 构建或厂商提供 ARM 版依赖 |
| 网络 | 千兆网口，选双网口型号 | 双千兆网口 |
| 存储与日志 | SSD，录播缓存和问题定位更从容 | eMMC/microSD，容量和寿命需规划 |
| 现场联调 | 驱动、抓包、远程排障工具完整 | 可实现，但需更多嵌入式 Linux 经验 |
| 功耗/体积/成本 | 较高 | 更低、更小 |
| 适合阶段 | 首次交付、算法部署、快速排障 | 量产、轻量协议网关 |

NanoPi R3S-LTS 的官方资料显示其使用 RK3566、提供双千兆网口、USB 3.0 与 Linux 系统支持；规格表没有列出板载 Wi-Fi 或蓝牙。因此若选择该板卡，USB 蓝牙适配器及其 Linux 驱动稳定性是必验项。[官方规格](https://www.friendlyelec.com/index.php?category_id=0&description=true&limit=25&order=ASC&page=2&product_id=311&route=product%2Fproduct&search=NanoPi&sort=p.price&sub_category=true)

## 5. Linux 与 Windows 对比

| 维度 | Linux（建议 Ubuntu LTS） | Windows |
|---|---|---|
| 适合本项目程度 | **推荐作为交付网关系统** | 适合原型验证或依赖 Windows 专有 SDK 时使用 |
| 蓝牙开发 | BlueZ、命令行诊断和服务化运行成熟；需确认目标蓝牙芯片驱动 | 厂商驱动与图形化操作较直观；部分 BLE 调试工具更易上手 |
| 算法与依赖 | Python/C++/Docker/网络服务部署灵活；可固定版本 | 若算法 DLL、驱动或授权仅支持 Windows，则优势明显 |
| 稳定运行 | 可裁剪为无界面系统，资源占用低，适合 7×24 开机自启 | 系统更新、弹窗或重启策略须额外管控 |
| 网络与协议服务 | 原生适合 TCP、WebSocket、HTTP(S)、MQTT、Docker 等服务 | 也完全支持，但部署为后台服务与防火墙规则需额外管理 |
| 远程排障 | SSH、日志、抓包、脚本自动化方便 | 远程桌面便于非技术人员操作，但常需要图形界面维护 |
| 授权与成本 | 系统通常无额外授权成本 | 可能有 Windows 授权成本与镜像维护成本 |
| 录播与日志 | SSD + systemd + 日志轮转，便于长期留存 | 也可实现，但磁盘、更新和权限策略要专门配置 |
| 主要风险 | 团队若不熟悉 Linux，初期配置与驱动调试有学习成本 | 长期无人值守时，更新/重启/安全软件可能影响演示或数据传输 |

### 系统选型规则

- **算法可运行于 Linux 或尚未限定平台：选 Linux。** 推荐 Ubuntu LTS，程序以 systemd 服务开机自启。
- **算法 SDK 或加密狗/驱动明确只支持 Windows：选 Windows。** 应关闭非必要自动更新并设置开机自启、固定防火墙规则和日志目录。
- **不要因为展示端是 Android 或 B/S 而选择 Android 系统的盒子。** 展示端和网关系统可独立：网关运行 Linux，数据送入第三方服务端即可。

## 6. 联调前须由双方确认的信息

### 我方提供

- 头环 BLE 接入说明：以《Flowtime headband 蓝牙通信协议》（2023-06-19）为准，使用 `FF31`/`FF32`/`FF51` 特征和 `FF21` 采集控制；该文档未定义 `FF52`，不得订阅它。仍须确认配对方式、加密方式与最大并发头环数。
- 头环数据协议：多字节数据为大端序；EEG `FF31` 为 20 字节（2 字节序号与 6 个 24 位采样）、心率 `FF51` 为 1 字节、佩戴/接触状态 `FF32` 为 2 字节；仍须实测采样率、每 600 ms 包数、校验方式与算法输入分组。
- 算法输出说明：字段、单位、取值范围、刷新频率、处理延迟、有效性或置信度标识。
- 北向协议示例：实时数据样例、异常状态样例、录播样例文件和解析/发送示例。

### 第三方 B 端主机提供/确认

- B 端主机的地址分配方式：默认是两端静态 IP、子网掩码、WS 端口及连接方向（B 端主机连接盒子）；若启用 DHCP，则盒子接入网卡仍使用固定 IP，B 端由 DHCP 获得地址并从默认网关选项取得盒子 IP，WS 端口仍固定。DHCP 与静态方案必须由部署配置二选一，且 DHCP 单元可独立禁用或卸载，不影响采集/录播业务。B 端应用须能读取操作系统默认网关；纯浏览器 JavaScript 不能直接读取 DHCP 租约。
- 专用有线直连网络的隔离方式；本期不使用 TLS、证书、Token、签名或账号密码，WS 数据为明文。
- 期望的数据字段、消息格式（JSON 或二进制）、频率/最大包大小和 ACK 要求。
- 时间戳格式、时区、是否需 B 端主机统一授时，以及允许的端到端延迟。
- 断线后的规则：重连间隔、是否允许缓存、缓存时长、是否需要补传、重复数据如何幂等处理。
- 连接保活：不使用应用层保活，不发送 WebSocket Ping/Pong 或 JSON 心跳；实际断线后 B 端重新建立连接并重新订阅。
- 现场有线直连网络条件：静态或 DHCP 二选一的地址分配方式、子网掩码、网口数量、USB 转网口适配器需求与防火墙放行；DHCP 模式不提供 DNS，均不需要 VLAN。
- 自动录播回退的文件来源、回放节奏与结束标识。

## 7. 会议确认的协议与演示要求

以下内容来自 2026-08-04 的项目沟通录音，已按逐字稿核对后整理：

1. **协议覆盖面要完整，但数据按需供给。** 协议中保留面板可展示的全部数据：原始数据、脑波节律（如 Alpha/Beta）和算法结果（如注意力、放松度）。对方发起某字段或某类数据的请求后，我方才返回对应数据；未请求的数据不发送。
2. **推送节奏由对方发起并控制。** 不应默认无条件向对方推送。建议定义“读取当前值”和“启动/停止订阅”两类请求：
   - 对注意力、放松度等小数据：`getLatest`，一请求一返回当前最新值；
   - 对原始波形、脑波节律等连续数据：`subscribe` 后，每 600 ms 返回一组或一批数据，直至对方 `unsubscribe`。这样既满足“对方决定要不要数据”，也能保证波形连续展示。
3. **目前采集节奏：600 ms 一组数据。** 此值应写入协议的字段说明、时序示例和验收项；原始数据的实际采样点数、每组点数、编码格式仍需补充。
4. **演示链路：头环 → BLE → 我方迷你主机 → 有线网络 → 对方 B 端主机。** 对方 B 端主机负责显示和保存，迷你主机只承担蓝牙数据到网络可访问数据的转换。
5. **录播模式是必需项。** 没有头环时，对方仍可访问盒子；B 端请求数据或订阅后，由盒子自动读取一段已配置录制数据并按与实时模式一致的协议回放。协议以 `mode`（`live`/`replay`）、`subjectId` 和回放状态字段标识来源。
6. **现场不预期操作盒子。** 盒子可在演示前接显示器完成配置；现场应开机自动运行。因此目标录播文件与回放参数须提前在网关配置，B 端不通过协议指令切换。
7. **本次演示为单人。** 协议保留 `subjectId`，用于录播文件的受试者区分；v0.1 不传 `deviceId` 或 `gatewayId`。
8. **物理连接预案：以网线为主。** 若对方 B 端主机没有网口，随盒子提供 USB 转千兆网口适配器和网线；有网口时直接连接。

## 8. 建议的北向消息最小字段

实时消息应至少能标识“谁、何时、什么数据、是否有效”。示例：

```json
{
  "messageType": "data",
  "mode": "live",
  "subjectId": "SUBJECT-001",
  "timestampMs": 1785800000123,
  "data": {
    "attention": 72,
    "relaxation": 48,
    "signalQuality": 96
  },
  "valid": true
}
```

原始波形和脑波节律建议使用批量 JSON 或二进制帧，避免每个采样点单独发一条 JSON 导致带宽与服务端压力增大。连续数据应由对方的 `subscribe` 请求开启，并按照当前暂定的 600 ms 分组返回。

### 建议的最小请求语义

| 请求 | 用途 | 返回 |
|---|---|---|
| `getLatest` | 获取指定算法字段的当前值 | 一次数据响应 |
| `subscribe` | 请求连续展示原始波形或节律数据 | 确认响应 + 每 600 ms 一组/批数据 |
| `unsubscribe` | 结束连续数据传送 | 确认响应 |
| `getStatus` | 查询头环连接、信号质量、电量、当前模式 | 状态响应 |

请求名和 JSON 字段仅为建议，最终以双方确认的协议文档为准。

## 9. 实施与验收

1. 用目标头环在拟定盒子上连续连接测试，覆盖配对、断连、重连、重启恢复和多设备干扰。
2. 完成 BLE 解析与算法调用，落地本地日志和短期缓存。
3. 与第三方确认并实现北向协议；使用模拟服务端和真实服务端分别联调。
4. 验证实时、录播、断网、恢复、服务端不可达、头环离线、异常数据等场景；一名 B 端订阅者断连、发送失败或消费过慢时，其他订阅者的录播不得停止。
5. 在实际展演网络环境进行至少一次全链路演练，输出版本号、配置备份、操作手册和问题日志。

### 建议验收指标（待双方填写）

| 项目 | 建议目标 |
|---|---|
| 头环 BLE 自动重连 | 断开后可自动恢复，具体时限双方确认 |
| 实时端到端延迟 | 以算法与服务端要求为准，联调时实测记录 |
| 断网数据 | 缓存时长、补传策略双方确认 |
| 连续运行 | 至少覆盖完整演示时长，并进行更长时间稳定性测试 |
| 数据完整性 | 按时间戳和服务端确认回执核对 |

## 10. 当前待决项

1. 是否允许多头环同时连接，以及算法 SDK 的输入究竟是原始 BLE 字节、哪些特征包或已解析数据；以真实录制数据完成 POC 验证。
2. 算法是否已有 Linux x86、Linux ARM64 或 Windows 版本；是否存在 USB 加密狗、GPU、运行库等依赖。
3. 第三方 B 端主机的协议与网络条件；是否需要由其主机进一步上传服务端。
4. 场地方对蓝牙禁用范围的准确解释。
5. 录播文件格式与业务展示规则。
6. 原始数据的实际采样率、每 600 ms 对应的样本数，以及“读取当前值”与“连续订阅”的最终指令格式。
