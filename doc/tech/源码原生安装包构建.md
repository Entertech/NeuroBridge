# 源码原生安装包构建

## 用途

`.github/workflows/native-inputs.yml` 从指定源码提交构建无签名的原生安装包，并为 32 个发布目标上传同名 Artifact：

```text
neurobridge-input-<targetId>
```

每个成功目标包含一个真实的 MSI、EXE、DEB 或 RPM、`verification.json` 和 `validation.log`。源码 ZIP/TAR 候选不会被改名为安装包。

## 运行方式

在 GitHub Actions 中手动运行 **Build native release inputs**。`source_ref` 填写准备发布的分支或提交。`platforms=available` 构建 GitHub 托管的 Windows 安装包，以及当前已注册的银河麒麟 V10 x86_64 Runner 上的 deb/rpm。`platforms=windows` 不等待麒麟 Runner。`platforms=all` 才会排队全部麒麟架构。

输入运行完成后会自动把本次 Run ID 写入仓库变量 `NEUROBRIDGE_RELEASE_INPUT_RUN_ID`，无需手动同步。写入由 Workflow 末尾的 `publish-input-run` 作业完成，它只在 Windows 与麒麟两组作业都成功时执行：`platforms=windows` 这类部分构建不会更新该变量，否则下一次发布聚合会静默丢掉麒麟安装包。若两个平台都失败或整个运行被取消，变量保持原值，发布侧继续消费上一次可用的输入运行。

输入运行必须与发布提交使用相同的源码 SHA。发布 Workflow 会再次校验分支、提交、文件格式、SHA-256 和验证清单。

Windows 目标是否可构建由 Workflow 矩阵中的 `blocked_reason` 字段显式声明：为空则构建，非空则跳过构建并把它写进 `blocked.log`。`tests/package/test_native_inputs_workflow.py` 会校验该矩阵与 `release/release_matrix.toml` 声明的 12 个 Windows 目标一致，并校验每个阻断目标的 `blocked_reason` 与它真正的阻断点相符。

## 目标环境

- Windows 10/11 x86_64：GitHub-hosted `windows-2022` Runner，源码运行时由锁定脚本准备，WiX CLI 生成 MSI/Burn EXE；不签名。
- Windows 7 和 Windows x86：当前保持 `blocked`。每个目标仍会运行并写出自己的阻断原因，不生成假包；原因按目标记录，不再是所有目标共用一句。
  - Windows 7：源码要求 Python 3.11，而 Python 3.9 起不再支持 Windows 7，需要单独的 Python 3.8 兼容移植（见 `release/release_matrix.toml` 的 `windows_7_python` 与 `windows_7_requires_compatibility_port`）。
  - Windows x86：阻断点在算法构建链，不在 Python 运行时。`sdk.lock` 只为 `windows_x86_64` 锁定 Eigen 版本、`llvm-mingw-20250114-ucrt-x86_64` 是 x86_64 目标工具链，且 `windows/algorithm_build.py` 会拒绝任何非 AMD64 的 PE 输出，因此产不出 32 位 `neurobridge_affective_bridge.exe`。Python 官方虽提供 `python-3.11.9-embed-win32.zip`，仅补齐运行时不足以解锁该目标。
- 麒麟：使用标签为 `self-hosted,kylin-v10,<architecture>` 的 Runner。仓库变量 `NEUROBRIDGE_KYLIN_RUNTIME_ROOT` 指向 Runner 上的运行时根目录，每个目标需要：

  ```text
  <root>/<targetId>/runtime/bin/python
  <root>/<targetId>/runtime/bin/neurobridge_affective_bridge
  ```

  目标 Runner 必须预装对应的 `dpkg-deb` 或 `rpmbuild`、目标架构 Sysroot/工具链和已验证的算法桥接程序。缺少输入时该目标上传 `blocked.log`，不会生成假包。

## 验证与发布

构建脚本会从当前源码复制产品 payload，调用原生打包器，检查包格式，并写入源码提交、运行时摘要、输入摘要、工具链和来源引用。最终发布仍由现有 CI 组装为唯一外层 ZIP；未通过原生格式校验的文件不会进入 ZIP。

## 安装与卸载

安装包形态与源码形态是两套独立部署，卸载方式不能混用。源码形态见 [`linux/README.md`](../../linux/README.md) 第 10 节与 [`windows/README.md`](../../windows/README.md) 的一键退出章节。

### Windows：MSI / EXE

- 安装：双击 MSI 或 Burn EXE，或在「应用和功能」中按包名安装。服务名固定为 `NeuroBridge`，由 WiX `ServiceInstall` 注册，账户为 `LocalSystem`，启动方式为自动。
- 卸载：在「应用和功能」中卸载，或执行 `msiexec /x`。MSI 的 `ProductCode` 由构建生成、未固定，因此按 `ProductCode` 卸载前需要先从已安装列表查询；按包名从「应用和功能」卸载不需要。
- 运行中的服务不会造成冲突：`ServiceControl Stop="both" Wait="yes" Remove="uninstall"` 保证卸载时先停止服务、等待其进入 Stopped，再删除文件，最后删除服务注册。服务进程持有 `C:\Program Files\NeuroBridge` 下的文件时也不会阻断删除。
- 服务首次启动时会自建数据目录：创建 `C:\ProgramData\NeuroBridge` 下的 `logs`、`recordings`，并在 `gateway.toml` 不存在时从随包模板复制一份。已存在的配置不会被覆盖，因此重装和卸载都不会丢现场数据。
- `C:\ProgramData\NeuroBridge`（配置、日志、录制）不归 MSI 所有，卸载后保留。需要彻底清除时手动删除该目录。
- 注意：MSI 的载荷根目录只有 `windows/`，`packaging/windows/` 下的 `install.ps1` / `uninstall.ps1` 是候选包（`tools/build-product-candidate.py`）用的，不随 MSI 分发。

### 麒麟：DEB / RPM

- 安装：`sudo dpkg -i <包>` 或 `sudo apt install ./<包>`；RPM 用 `sudo rpm -ivh <包>` 或 `sudo dnf install ./<包>`。`postinst` / `%post` 负责创建 `neurobridge` 系统账户与数据目录、安装并启用 `neurobridge.service`。
- 卸载：`sudo apt remove neurobridge-<edition>`（或 `dpkg -r`）、`sudo dnf remove neurobridge-<edition>`（或 `rpm -e`）。
- 运行中的服务不会造成冲突，且**只会动本包自己的单元**：`prerm` / `%preun` 先确认 `/etc/systemd/system/neurobridge.service` 的 `ExecStart` 指向 `/opt/neurobridge/...`，再 `systemctl disable --now`，然后轮询 `systemctl is-active` 确认真的停了（单元是 `Restart=always` + `RestartSec=3`，停止未完成时会被拉起）。若 10 秒后仍在运行则尝试 `systemctl kill`，仍不停就以非零退出，避免把正在运行的网关从脚下删掉。
- 源码形态的单元写在**同一个路径**上，所以单元归属判断是必需的：`ExecStart` 指向源码目录时，本包既不停止也不删除该单元，源码部署不会被安装包的卸载破坏。
- 卸载后保留：`/etc/neurobridge`（配置）、`/var/lib/neurobridge`（录制）、`/var/log/neurobridge`（日志）和 `neurobridge` 系统账户。这些都不归包所有，`purge` 也不会删除；需要彻底清除时手动删除，并 `userdel neurobridge`。

### 覆盖安装已发出的包

[Actions run 37751485418](https://github.com/Entertech/NeuroBridge/actions/runs/37751485418)（源码 `c305511`，应用版本 `0.2.0`）的安装包已经交到现场。后续构建必须替换这些包，而不是并列再装一个：

- Windows 的 `UpgradeCode` 由固定 URL 派生，MSI 与 Burn EXE 各自一个，不随版本变化。MSI 开启 `AllowSameVersionUpgrades`，所以版本号没有升高时也会替换已安装的 `0.2.0`，而不是被 Windows Installer 当成另一个产品。EXE 用 `RelatedBundle Action="Upgrade"` 检测同一个 `UpgradeCode` 的旧引导程序。`ProductCode` 每次构建都变，这是 major upgrade 的前提，不能改成固定值。
- 麒麟的包名是 `neurobridge-<edition>`（`desktop` 或 `server`），版本同为 `0.2.0`。`apt`/`dnf` 按包名匹配，同版本重装即覆盖；配置文件只在不存在时复制，已有的 `gateway.toml` 保留。
- 覆盖安装不停服务。deb 的 `prerm` 在参数为 `upgrade` 时直接返回；rpm 的 `%preun` 只在 `$1 -eq 0`（卸载）时停止服务。新包的安装脚本重写单元并重新启用，由 systemd 完成进程切换。真正卸载时的停止与归属判断不变。

## 导出运行日志

网关自带的 HTTP 导出（`GET <download.path>/logs/neurobridge-logs.zip`）只在网关运行且下载服务已启用时可用，且按设计不含 systemd journal、内核与 USB/TTY 信息。排障时更需要一个**网关没跑起来也能用**的导出命令，两个平台各有一个，会自动识别源码部署与安装包部署：

- 麒麟：`sudo /opt/neurobridge/kylin/export-logs.sh --output-dir /tmp`（安装包部署）；源码部署可用 `sudo ./packaging/kylin/export-logs.sh --output-dir ~`，或菜单项 7 的完整诊断包。
- Windows：`powershell -ExecutionPolicy Bypass -File 'C:\Program Files\NeuroBridge\windows\export-logs.ps1' -OutputDirectory C:\Temp`（MSI 部署）；源码部署用 `<checkout>\windows\export-logs.ps1`，或启动器菜单项 13。

两者都产出单个带时间戳的归档（麒麟 `.tar.gz`、Windows `.zip`）并附 SHA-256，内容包含应用日志、服务状态、journal 或应用事件日志、USB/COM 端口清单和 `manifest.txt`；日志超过上限时只保留尾部（麒麟 `--max-log-bytes`、Windows `-MaxLogBytes`）。命令是只读的：不启停服务、不改配置，且**不包含配置正文、录制数据和凭据**——配置只记录 SHA-256。
