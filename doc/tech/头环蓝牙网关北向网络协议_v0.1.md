# 头环蓝牙网关北向网络协议

版本：v0.1  
日期：2026-08-04  
状态：**实现基线；联调前由双方确认网络地址、令牌、证书与字段选择**

## 1. 目的与结论

本文定义头环蓝牙网关与第三方 B 端主机之间的北向接口。它落实《[头环蓝牙网关对接方案 v0.1](头环蓝牙网关对接方案_v0.1.md)》的“B 端按需请求、连续数据每 600 ms 返回一组”的要求。

首期统一采用 **WebSocket Secure（WSS）+ UTF-8 JSON 文本帧**：

- 网关是 WebSocket 服务端，B 端主机是客户端；B 端主动连接网关并通过请求决定读取或订阅哪些数据。
- 正式环境使用 `wss://`，默认监听 `8443` 端口、路径 `/neurobridge/v1/ws`。证书、端口、网段和令牌均由部署配置提供，不能写死在程序或文档示例中。
- 仅在隔离的本机/验收测试环境，且经双方书面确认后，允许以配置方式启用 `ws://`；不得将明文模式作为现场或生产默认值。
- 所有业务消息使用 JSON，便于 B/S 和桌面端调试；原始字节流以 Base64 承载，避免另行约定 TCP 分帧或二进制解码。以后若原始波形带宽成为瓶颈，再以独立的二进制子协议升级，不能改变本版本 JSON 的语义。

该选择同时支持请求-响应和服务端连续推送，适合 B 端主机控制 `getLatest`、`subscribe`、`unsubscribe` 与录播切换；也使实时与录播复用同一条连接和同一份数据模型。

```text
第三方 B 端主机                         网关
     │  WSS：鉴权、请求、订阅              │
     ├──────────────────────────────────►│
     │◄──── 状态、确认、每 600 ms 数据 ───┤
     │                                     │
     │                             BLE：头环通知
     │                             算法：本地计算
```

## 2. 版本、连接与鉴权

### 2.1 WebSocket 握手

```text
wss://{gateway-host}:8443/neurobridge/v1/ws
```

| 项目 | 规定 |
| --- | --- |
| WebSocket 子协议 | `neurobridge.v1` |
| 编码 | UTF-8 JSON 对象；一个 WebSocket 文本帧对应一个完整业务消息 |
| TLS | WSS 必须校验证书链与主机名；自签名证书仅在双方明确配置可信根时使用 |
| 首个业务请求 | 5 秒内发送 `authenticate`；超时或失败由网关以 `4401` 关闭连接 |
| 连接保活 | 网关每 15 秒发送 WebSocket Ping；B 端必须回复 Pong。连续 3 次未响应，网关关闭连接并释放该连接的订阅 |
| 版本不兼容 | 握手子协议不匹配时拒绝握手；已建立连接收到未知的 `protocolVersion` 时返回 `UNSUPPORTED_VERSION` |

鉴权请求的令牌通过 WSS 业务帧传递，不使用 URL 查询参数，避免令牌出现在代理或访问日志中。令牌的签发、轮换、有效期与权限由部署侧确定；网关日志不得记录令牌明文。

```json
{
  "protocolVersion": "1.0",
  "messageType": "request",
  "requestId": "2c15ddf0-e8e3-46b5-86fb-6dd48b2af1fe",
  "action": "authenticate",
  "params": { "token": "<deployment-issued-token>" }
}
```

成功响应：

```json
{
  "protocolVersion": "1.0",
  "messageType": "response",
  "requestId": "2c15ddf0-e8e3-46b5-86fb-6dd48b2af1fe",
  "ok": true,
  "result": {
    "gatewayId": "GW-001",
    "sessionId": "a8493bc4-86e5-42c2-983a-2521d0d5f75c",
    "serverTimeMs": 1785800000123
  }
}
```

### 2.2 通用字段与约定

| 字段 | 规则 |
| --- | --- |
| `protocolVersion` | 固定为字符串 `1.0` |
| `messageType` | `request`、`response`、`event` 或 `error` |
| `requestId` | 客户端生成的 UUID；所有请求及其响应必须相同。事件没有 `requestId` |
| `sequence` | 网关为每个 `deviceId` 单调递增的无符号整数；重启后可从 0 重新开始，B 端以 `gatewayBootId` 区分序列周期 |
| `timestampMs` | 网关为该组数据赋值的 Unix Epoch 毫秒（UTC）；不使用本地时区字符串 |
| `null` | 表示值暂不可用、该算法尚未产生结果或当前硬件不支持；不得用 `0` 代替未知值 |
| 数值 | JSON number；不得传 `NaN`、`Infinity` 或字符串化数字 |

服务端事件的公共字段如下：

```json
{
  "protocolVersion": "1.0",
  "messageType": "event",
  "event": "data",
  "gatewayId": "GW-001",
  "gatewayBootId": "20260804T100000Z-7bf0",
  "deviceId": "HEADBAND-001",
  "subjectId": "SUBJECT-001",
  "mode": "live",
  "sequence": 1024,
  "timestampMs": 1785800000123,
  "valid": true,
  "data": {}
}
```

`subjectId` 在本次单人演示中仍必须保留；未知时可为 `null`。`valid=false` 时 `data` 可仅含 `status` 与 `invalidReasons`，B 端不得将其作为有效算法值展示或持久化为测量结果。

## 3. 请求与响应

除 `authenticate` 外，所有请求均须在鉴权成功后发送。所有成功响应使用 `messageType: "response"`、原 `requestId`、`ok: true` 与 `result`；失败使用第 7 节的错误格式。

### 3.1 `getStatus`

读取网关、头环连接、佩戴、电量、信号与当前运行模式。B 端连接后应先调用该接口。

```json
{
  "protocolVersion": "1.0",
  "messageType": "request",
  "requestId": "e99942e1-e9ce-4d29-a6f4-8e0bd50a6e42",
  "action": "getStatus",
  "params": { "deviceId": "HEADBAND-001" }
}
```

`result` 至少包括 `gatewayId`、`gatewayBootId`、`deviceId`、`mode`、`connectionState`（`connected`/`connecting`/`disconnected`/`replaying`）、`wearState`（`worn`/`notWorn`/`unknown`）、`batteryPercent`、`signalQuality`、`algorithmState`、`availableStreams` 与 `serverTimeMs`。

### 3.2 `getLatest`

获取指定算法字段的最近一次有效计算结果，不启动持续传送。`streams` 只能包含第 4 节定义的算法流；缺省为 `algorithm.eeg` 和 `algorithm.hr`。

```json
{
  "protocolVersion": "1.0",
  "messageType": "request",
  "requestId": "a671a32d-4ba7-4d18-a6e5-fabc54df3f8e",
  "action": "getLatest",
  "params": {
    "deviceId": "HEADBAND-001",
    "streams": ["algorithm.eeg", "algorithm.hr"]
  }
}
```

响应 `result` 使用与第 5 节 `data` 相同的结构，并包含该结果的 `timestampMs`、`sequence` 与 `valid`。没有可用结果时，响应仍为 `ok: true`，但 `valid=false` 且 `data` 为空对象。

### 3.3 `subscribe` 与 `unsubscribe`

`subscribe` 启动一个独立订阅。成功后网关立即确认，随后以 `event: "data"` 推送。对连续流，网关按 **600 ms 窗口** 至多发送一条事件；窗口内无新数据时不补发空事件，除非订阅了 `status`。

```json
{
  "protocolVersion": "1.0",
  "messageType": "request",
  "requestId": "fa3af4d9-1dc1-436d-af45-5855d3994fe7",
  "action": "subscribe",
  "params": {
    "deviceId": "HEADBAND-001",
    "streams": ["algorithm.eeg", "algorithm.hr", "eeg.raw", "status"],
    "includeInvalid": true
  }
}
```

成功响应的 `result` 包含 `subscriptionId`、`deviceId`、`streams`、`intervalMs: 600`。`subscriptionId` 只在当前 WebSocket 连接有效；断线后 B 端重连并重新订阅。

`unsubscribe` 的 `params` 只包含 `subscriptionId`。网关确认后不得再向该订阅发送数据事件。重复取消不存在的订阅返回 `SUBSCRIPTION_NOT_FOUND`。

### 3.4 `selectReplay`

选择并启动录播。实时和录播通过 `mode` 区分，事件结构保持不变。

```json
{
  "protocolVersion": "1.0",
  "messageType": "request",
  "requestId": "6a60efc9-cf92-44d1-b0bb-f64746cb43a1",
  "action": "selectReplay",
  "params": {
    "recordingId": "demo-001",
    "subjectId": "SUBJECT-001",
    "playbackRate": 1.0
  }
}
```

`playbackRate` 允许 `0.5`、`1.0`、`2.0`，缺省为 `1.0`。网关不得以“尽快发送”替代指定倍率；若后续需要快发模式，必须以新的协议版本扩展。播放结束发送 `event: "replayEnded"`，其中包含 `recordingId`、`deviceId`、`subjectId` 与结束时间。

## 4. 流名称、BLE 映射与算法映射

### 4.1 可订阅流

| 流 | 含义 | 默认频率 | 数据来源 |
| --- | --- | --- | --- |
| `algorithm.eeg` | 脑电频段、质量、睡眠、放松度、愉悦度、注意力、心流 | 算法结果更新时，最多每 600 ms | 本地算法 `appendEEG`/`appendSCEEG` |
| `algorithm.hr` | 心率、HRV、压力、和谐度、激活度 | 算法结果更新时，最多每 600 ms | 本地算法 `appendHR` |
| `eeg.raw` | 原始 EEG 字节分组 | 每 600 ms | BLE EEG 通知 |
| `hr.raw` | 原始 HR 字节分组 | 每 600 ms | BLE HR 通知 |
| `status` | 连接、佩戴、电量、信号状态变化 | 状态变化时；连续订阅时最多每 600 ms | BLE 与网关状态机 |

网关只发送被订阅的流。未订阅 `eeg.raw`/`hr.raw` 时，不得在算法流中夹带原始数据。

### 4.2 BLE 输入规范

下表基于 [Enter-Biomodule-BLE-PC-SDK](https://github.com/Entertech/Enter-Biomodule-BLE-PC-SDK) 的 `FlowtimeCollector`。这是当前首期设备适配配置；新头环型号必须新增设备 profile，不能复用本表而猜测 UUID 或帧格式。

| BLE 特征 | UUID | 单次通知 | 网关规范化字段 |
| --- | --- | --- | --- |
| EEG | `0000ff31-1212-abcd-1523-785feabcd123` | 20 个无符号字节，SDK 以 `>20B` 解包 | `eeg.raw` |
| HR | `0000ff51-1212-abcd-1523-785feabcd123` | 1 个无符号字节，SDK 以 `>B` 解包 | `hr.raw` |
| 佩戴状态 | `0000ff32-1212-abcd-1523-785feabcd123` | 1 个无符号字节；当前 SDK 将 `0` 映射为已佩戴 | `status.wearState` |
| 电量 | `00002A19-0000-1000-8000-00805F9B34FB` | 1 个无符号字节；SDK 做百分比换算 | `status.batteryPercent` |

网关必须原样保留 EEG/HR 原始字节后再交给算法。对于当前双通道 Flowtime profile，一个 600 ms EEG 窗口应为 **50 个通知 × 20 字节 = 1000 字节**；HR 算法窗口为 **3 个 1 字节通知**。这与算法 SDK 的 `appendEEG`/`appendHR` 默认 0.6 秒触发设计相对应。若实际包数不符，网关必须标记 `valid=false` 和 `invalidReasons`，不得用填零、截断或拼接相邻窗口的方式伪造完整数据。

单通道 `appendSCEEG` 的字节数、设备 profile 与采样率尚未由本项目头环确认，因此 v0.1 只定义其算法输出字段，不允许在没有 profile 的情况下发送 `eeg.raw` 或声明数据有效。

### 4.3 本地算法输出结构

下表映射 [AffectiveCloud-Algorithm-SDK](https://github.com/Entertech/AffectiveCloud-Algorithm-SDK) C++ 实时结构：`EEGAffectiveRes`、`SCEEGAffectiveRes`、`HRAffectiveRes`。原算法字段名采用 camelCase 输出；数值范围与单位以算法 SDK 的验收结果为准，未验证前不在北向协议中臆定为 0–100。

| 北向字段 | 算法来源 | 说明 |
| --- | --- | --- |
| `algorithm.eeg.wave.left/right` | `EEGTriggerRes.eeglWave` / `eegrWave` | 双通道脑波数组；仅订阅 `algorithm.eeg` 时可发送 |
| `algorithm.eeg.wave.single` | `SCEEGTriggerRes.eegWave` | 单通道脑波数组 |
| `algorithm.eeg.bandPower` | `eegAlpha/Beta/Theta/Delta/Gamma/LowBeta/HighBetaPower` | 频段能量；单通道不包含 low/high beta 时置 `null` |
| `algorithm.eeg.quality` | `eegQuality` | 算法输出的脑电质量值 |
| `algorithm.sleep` | `SleepTriggerRes` | `updated`、`degree`、`state`、`stage`、`spindle` |
| `algorithm.relaxation/pleasure/attention` | `EEGAffectiveRes` | 双通道实时情感结果；单通道当前仅有 `relaxation` |
| `algorithm.flow` | `FlowTriggerRes` | `meditation` 与 `meditationTips` |
| `algorithm.hr` | `HRTriggerRes` | `value` 与 `hrv` |
| `algorithm.pressure/coherence/arousal` | `HRAffectiveRes` | 心率相关情感结果 |

完整版历史报表（如 `getEEGReport`、`getSleepReport`）不属于 v0.1 实时北向流；若 B 端需要，应在后续版本新增分页/文件下载接口，避免把全程数组反复塞入 600 ms 消息。

## 5. `data` 负载格式与示例

### 5.1 原始数据格式

`eeg.raw` 使用以下对象。`bytesBase64` 是 BLE 接收顺序的完整原始字节，不进行数值缩放或字节序转换；`windowStartMs`/`windowEndMs` 由网关记录。

```json
{
  "eegRaw": {
    "encoding": "base64",
    "sampleFormat": "u8",
    "packetBytes": 20,
    "packetCount": 50,
    "byteLength": 1000,
    "windowStartMs": 1785800000000,
    "windowEndMs": 1785800000600,
    "bytesBase64": "..."
  },
  "hrRaw": {
    "sampleFormat": "u8",
    "packetCount": 3,
    "values": [72, 73, 72]
  }
}
```

`sampleFormat: "u8"` 指的是传输前的单字节无符号整数，不代表最终生理量。B 端若需要解释原始数据，必须使用双方确认的头环解析规范，而不能从本协议推断通道布局或采样率。

### 5.2 算法数据格式

```json
{
  "algorithm": {
    "eeg": {
      "wave": { "left": [0.12], "right": [0.09], "single": null },
      "bandPower": {
        "alpha": 1.23,
        "beta": 2.34,
        "theta": 0.98,
        "delta": 0.76,
        "gamma": 0.41,
        "lowBeta": 0.88,
        "highBeta": 1.46
      },
      "quality": 96.0
    },
    "sleep": {
      "updated": false,
      "degree": 0.0,
      "state": 0,
      "stage": 0,
      "spindle": 0.0
    },
    "relaxation": 48.0,
    "pleasure": 51.0,
    "attention": 72.0,
    "flow": { "meditation": 0.0, "meditationTips": 0.0 },
    "hr": { "value": 72, "hrv": 0.0 },
    "pressure": 0.0,
    "coherence": 0.0,
    "arousal": 0.0
  }
}
```

`sleep.stage` 仅在算法已经产出有效睡眠阶段时使用：`0=WAKE`、`1=NREM1`、`2=NREM2`、`3=NREM3`、`4=REM`。睡眠是否产生新结果由 `sleep.updated` 表示；在 `updated=false` 时，B 端不得把该周期视为新增睡眠判定。

## 6. 实时、录播与状态事件

- 实时数据的 `mode` 为 `live`；录播数据为 `replay`。B 端必须以该字段区分两类数据，不能仅以 `recordingId` 推断。
- `sequence` 在实时与录播中均按 `deviceId` 递增。录播的 `timestampMs` 表示录制时数据的原始时间；发送时刻由 WebSocket 到达时间体现，不能覆盖该值。
- 发生 BLE 断连、重连、佩戴、电量或算法运行状态变化时，向订阅了 `status` 的连接发送 `event: "status"`。状态事件需含完整 `status` 对象而非仅差量，便于 B 端重连后的状态恢复。
- 录播期间若无真实头环连接，`connectionState` 可为 `replaying`，不得伪造为 `connected`。

## 7. 错误与限流

失败响应使用以下统一格式：

```json
{
  "protocolVersion": "1.0",
  "messageType": "error",
  "requestId": "fa3af4d9-1dc1-436d-af45-5855d3994fe7",
  "error": {
    "code": "DEVICE_NOT_CONNECTED",
    "message": "Headband is not connected.",
    "retryable": true,
    "details": { "deviceId": "HEADBAND-001" }
  }
}
```

| 错误码 | 含义 | 可重试 |
| --- | --- | --- |
| `UNAUTHENTICATED` | 未鉴权或令牌失效 | 否，需重新鉴权/连接 |
| `FORBIDDEN` | 鉴权成功但无设备或录播权限 | 否 |
| `UNSUPPORTED_VERSION` | 协议版本不支持 | 否 |
| `INVALID_REQUEST` | 缺少字段、字段类型错误或枚举值错误 | 否 |
| `DEVICE_NOT_FOUND` | `deviceId` 未配置 | 否 |
| `DEVICE_NOT_CONNECTED` | 请求实时数据但头环未连接 | 是 |
| `STREAM_NOT_AVAILABLE` | 流不支持、算法未启用或设备 profile 不匹配 | 否，需调整请求或配置 |
| `ALGORITHM_NOT_READY` | 原始数据不足以产生算法结果 | 是 |
| `REPLAY_NOT_FOUND` | 指定录播不存在或无权限 | 否 |
| `SUBSCRIPTION_NOT_FOUND` | 订阅不存在或已随断线释放 | 否 |
| `RATE_LIMITED` | 请求频率或订阅数超过部署限制 | 是 |
| `INTERNAL_ERROR` | 未预期网关错误 | 是 |

v0.1 默认限制为每连接最多 4 个订阅、每设备每连接最多 1 个相同流订阅、单条 JSON 负载最大 256 KiB。超限时返回 `RATE_LIMITED` 或 `INVALID_REQUEST`；不得静默丢弃事件。具体上限可在部署配置中收紧，但不能放宽到破坏 B 端的验收假设而不通知对方。

## 8. 联调验收

1. B 端能够通过 WSS 建连、完成鉴权、调用 `getStatus`，并正确处理证书校验失败与鉴权失败。
2. 请求 `getLatest` 时只返回所请求的算法字段；未产生算法结果时返回 `valid=false`，不以零值冒充结果。
3. 订阅连续流后，验证每组数据为 600 ms，双通道 EEG 为 50 个 20 字节 BLE 包/1000 原始字节，HR 为 3 个字节；窗口不完整时验证错误状态与 `valid=false`。
4. 验证 `unsubscribe`、WebSocket 断开和重连后不会残留旧订阅；验证 Ping/Pong 超时可释放连接。
5. 验证头环断线、重连、未佩戴、电量变更、算法异常和服务端重启均生成可处理的状态或错误。
6. 验证录播使用同一 `data` 结构、保留 `mode=replay` 与原始时间戳，并按 `0.5x`、`1x`、`2x` 正确节奏回放。
